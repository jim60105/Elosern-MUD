# Design: One command card for actor switching and skill draft progress

## Context

See `proposal.md` for motivation and the batch contract in `../combat-ratio-mitigation/batch.md` for complete coverage, order and conflicts. Current frame-resolvers keep one CombatMenu model; active card/stage/cross-side proposals own the future presentation and warning contracts.

Inspected boundaries are listed in the proposal Impact section. These are observed starting points; all new behavior below is proposed, with no runtime result claimed. The approved 2026-10-15 document explicitly amends the base engine §6.3 where subtraction, allied autonomy and individual allied flee conflict.

## Goals / Non-Goals

This change owns one command card for actor switching and skill draft progress. It reuses existing deterministic state owners and exact protocol conventions. Required behavior is defined by its complete delta files. There is no new LLM dependency, compatibility path, data migration, shared inventory, companion equipment-management UI or physical proficiency progression. Detailed stage geometry remains owned by the existing UI batch.

## Decisions

Use one `combat.actor` frame within the mounted centered card and retain its 264px*S width/anchor/formation clearance. Actor rows use server allied order, display name/token, commandable reason and confirmed/needs-selection text. A compact current-actor/progress line and a Change member/back path occupy existing card rows/detail slots; do not resize/reposition the shell or alter stage geometry. Choosing an actor queries combat.actor_choices with session/revision/actor, then opens the same root/category/group/scale/target flow from canonical choices; do not optimistically show the previous actor catalog. Commanded actor ID, focused target ID and account puppet ID are separate state. SELF lighting/confirmation binds commanded actor including a companion, never the controlled portrait. Actor switch drops unconfirmed local skill/scale/target selection and cancels local warnings without deleting confirmed server entries. Revisiting an entry selects its actor and permits replacement. After a nonfinal accepted selection, choose the first required actor still needing a command; keep all actors reachable, including already selected. The last confirmation dispatches the same combat.command and server determines resolution, with no whole-party submit screen. Preserve actor-bound cross-side warnings and all target checks/digits/pointer paths. During playback keep existing lock and never replay pending intent. On invalidation show member reasons and retain valid progress; reconnect reconstructs server-confirmed entries and starts at first missing actor, never auto-fills or resubmits. This change owns actor and skill UI; item/tactical rows become live through change 14, which is required for assembled acceptance. Add keyboard/pointer and screen-reader status coverage without introducing visual redesign.

## Risks / Trade-offs

- [Shared boundary changes] -> Implement only after declared prerequisites, integrate earlier deltas and callsites, and use the batch matrix to serialize overlapping files. No obsolete alias or duplicate implementation remains after cutover.
- [State or capability changes after selection] -> The shared rules boundary repeats authoritative validation; invalid drafts and normal mid-round invalidation follow different documented semantics.
- [Unproven arithmetic, persistence or UI behavior] -> Tasks include focused independent assertions and actual evidence where owned here. A selected constant alone is not measured balance and a fixture-only UI is not runtime acceptance.
- [Estimate depends on existing patterns] -> Scope is bounded to the listed owner and 7 hours includes its focused tests/docs/integration. Required downstream behavior is owned explicitly in the batch rather than silently deferred.

## Migration Plan

Pre-release clean cutover only. Implement code, callsites, fixtures, exact schemas and affected canonical requirement annotations together for this slice. No old/new compatibility parser, stored-data migration or deprecated entry path is added. Rollback uses an ordinary revert of the implementation change; proposal authoring performs no rollback, merge, apply or archive. The assembled client/server cutover is accepted only after change 18.

## Verification and documentation ownership

If the canonical slug changes, migrate every affected annotation. Update existing affected documentation, both player command documents for syntax/context changes, and focused schema/fixture mirrors for transport changes. Run the focused tests and `uv run --locked python -m tools.contract_gate` during implementation; logging changes also require observability lint and focused event tests. Complete managed browser and traceability-evidence execution stay CI-owned.
