# Design: Combined player/enemy encounter and skill-budget calibration

## Context

See `proposal.md` for motivation and the batch contract in `../combat-ratio-mitigation/batch.md` for complete coverage, order and conflicts. Existing human calibration records actual seeds0-3/200-round probes separately from historical projected tables and forbids unsupported universal encounter claims.

Inspected boundaries are listed in the proposal Impact section. These are observed starting points; all new behavior below is proposed, with no runtime result claimed. The approved 2026-10-15 document explicitly amends the base engine §6.3 where subtraction, allied autonomy and individual allied flee conflict.

## Goals / Non-Goals

This change owns combined player/enemy encounter and skill-budget calibration. It reuses existing deterministic state owners and exact protocol conventions. Required behavior is defined by its complete delta files. There is no new LLM dependency, compatibility path, data migration, shared inventory, companion equipment-management UI or physical proficiency progression. Detailed stage geometry remains owned by the existing UI batch.

## Decisions

Extend the existing human-combat calibration boundary, using real objects/kit/restrictions, fixed seeds0-3 and a 200-round bound with simulation markers suppressing growth, unlock and reward drift. Run bounded representative early and higher-tier player/enemy encounters in both damage directions with explicit whole-party scripted commands through the draft facade (scripts supply actual chosen commands, never allied autonomous provider fallback). Measure basic attack, representative physical skills, magic controls, bypass, conditional multipliers, max-HP riders, authored scales and multi-strike. Record coefficient × critical × weapon factor × strike-count budget and defenses/Defend/Dodge effects, costs, rejects, defeats, retreats, losses, all-standing, unfinished, round medians and estimator-versus-settlement parity. Include Taunt choice constraints without presenting it as a forced attack. Compare initial K40/0.35/25 and initial real weapon values to selected values; keep or tune only with recorded evidence. If observed combinations require adjustment, author bounded relevant skill/equipment/combat values here and update their owning data tests; no global skill weakening or new progression rule. Preserve enemy defensive/evasive skills and no-new-enemy-basic-tactics restriction. Historical projected tables remain separately qualified; no universal high/calamity promises. A failed fixture/restriction probe blocks completion until diagnosed.

## Risks / Trade-offs

- [Shared boundary changes] -> Implement only after declared prerequisites, integrate earlier deltas and callsites, and use the batch matrix to serialize overlapping files. No obsolete alias or duplicate implementation remains after cutover.
- [State or capability changes after selection] -> The shared rules boundary repeats authoritative validation; invalid drafts and normal mid-round invalidation follow different documented semantics.
- [Unproven arithmetic, persistence or UI behavior] -> Tasks include focused independent assertions and actual evidence where owned here. A selected constant alone is not measured balance and a fixture-only UI is not runtime acceptance.
- [Estimate depends on existing patterns] -> Scope is bounded to the listed owner and 7 hours includes its focused tests/docs/integration. Required downstream behavior is owned explicitly in the batch rather than silently deferred.

## Migration Plan

Pre-release clean cutover only. Implement code, callsites, fixtures, exact schemas and affected canonical requirement annotations together for this slice. No old/new compatibility parser, stored-data migration or deprecated entry path is added. Rollback uses an ordinary revert of the implementation change; proposal authoring performs no rollback, merge, apply or archive. The assembled client/server cutover is accepted only after change 18.

## Verification and documentation ownership

Use synthetic fixtures for independent behavior expectations and the existing real-data calibration boundary for authored roster evidence. Register added/moved Evennia tests and browser methods exactly once in the appropriate shard manifest; annotate tests with canonical `<capability>.<requirement-slug>` IDs generated by the project traceability tooling. If the canonical slug changes, migrate every affected annotation. Update existing affected documentation, both player command documents for syntax/context changes, and focused schema/fixture mirrors for transport changes. Run the focused tests and `uv run --locked python -m tools.contract_gate` during implementation; logging changes also require observability lint and focused event tests. Complete managed browser and traceability-evidence execution stay CI-owned.
