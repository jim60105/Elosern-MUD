# Spec Delta

## Purpose

Exercise the real changed server-to-browser synchronization path with deterministic functional evidence for deltas checkpoints multipart delivery and bounded recovery.

## ADDED Requirements

### Requirement: Changed synchronization paths have actual browser functional acceptance
Focused managed-browser scenarios SHALL exercise committed graphical/text actions through the production coordinator, real socket and production reducer/view. Assertions SHALL cover changed-only deltas, fresh checkpoints, oversized atomic delivery and bounded complete recovery without production test-only protocols.

#### Scenario: Real action sequence follows expected publication kinds
- **WHEN** the focused graphical/text movement combat and skip sequence executes
- **THEN** wire frames baseline/target revisions and browser committed data follow delta/checkpoint rules and results follow complete publications

#### Scenario: Real oversized bytes adopt atomically
- **WHEN** production validated snapshot and delta publications exceed the applicable intact frame ceiling
- **THEN** bounded general parts cross the real socket and expose one complete adopted state with every frame within its limit

#### Scenario: Real missed baseline recovers all eager data
- **WHEN** one actual publication is withheld before a later delta/result arrives
- **THEN** mutations lock one sync repairs the full eager state and no mutation is replayed

#### Scenario: Real failed repair stays usable as text
- **WHEN** the single repair is corrupted before explicit retry/reconnect
- **THEN** automatic sync does not loop graphical controls stay locked and text input/output remains usable

#### Scenario: Checkpoint repairs omitted candidate
- **WHEN** a test-scoped publication deliberately omits one changed eager candidate before a real checkpoint
- **THEN** the fresh checkpoint restores that canonical field without relying on the old baseline

### Requirement: Synchronization verification excludes performance claims
Verification SHALL retain functional tests and actual changed-path smoke while omitting performance measurements, benchmarks, profiling, latency comparisons and no-stutter claims. Byte-bound assertions SHALL validate protocol resource policy without implying measured workload or responsiveness.

#### Scenario: Functional evidence states its limit
- **WHEN** the synchronization acceptance report lists observed focused test and smoke results
- **THEN** it reports functional behavior and concrete blockers without measured latency or no-stutter assertions
