## Why

The version-1 desktop shell is fully wired (pointer activation, plugin-contract keydown, drawer focus retention, narrative markup, and the minimap lattice all landed in `webclient-shell-usability-fixes`), but the surface a player actually sees still disagrees with the approved layout-and-interaction design (the owner's desktop mockup, `.superpowers/brainstorm/1320174-1785662962/content/layout-interaction-design.html`, which itself implements the ink-night visual language of `2026-08-02-webclient-ui-design.md`): the palette uses a brighter vermilion and different panel colors than the mockup; the header shows a raw mode label instead of location and uses a plain text connection state instead of the green dot; the action dock lacks the mockup's vermilion frame, guidance line, and grid-button look; submenus render as full-width rows instead of the mockup's button grid plus a side detail pane; status shows numbers without the mockup's gauge bars; and six interaction defects remain — Enter inside the drawer textarea sends nothing unless the drawer was opened with `/`, the send button is visibly misaligned, exploration submenus offer no way back for a pointer user, the GoldenLayout tab strip labels panels with meaningless raw component names such as "header", the unread marker is a cryptic red pill that also renders as an empty pill when nothing is unread, and the vermilion accent has never been audited against the approved design language. All are browser-side presentation defects in landed code — no server payload, adapter, presenter, or deterministic rule is implicated.

## What Changes

- **Adopt the approved desktop palette and visual language.** The mockup's exact color families replace the current tokens: near-black page `#0d0d0c`, panel surfaces `#151513` / `#1b1a17` / `#211c18` / `#171715`, warm borders `#514c43` (dim `#3c3933`, art `#5b574f`), warm paper `#e5e0d5` (dim `#aaa395`, cursor `#d4c9b5`), the deep seal red `#a9322a` replacing `--elm-vermilion: #e05c3a`, HP/warning reds `#b3483e` / `#b97c73`, the new ok-green connection color `#709676`, the art placeholder gradient `#273028 → #73593e`, and the portrait gradient `#756b61 → #292722`. The existing focus-ring token becomes a lighter vermilion tuned to stay visible on both the ink surfaces and the seal-red button fill. The narrative and headings move to a serif face (per design doc §5.2 "serif typography may be used for narrative and headings"); controls keep a legible UI face. This resolves the vermilion question: the mockup (the owner's current design intent) specifies the deeper seal red, so the token changes and the audit records the decision. The seal-red audit splits the token by role — the deep seal red (`#a9322a`, ≈2.9:1 on ink) is restricted to fills, borders, and large/bold text and symbols, while small red text on dark surfaces uses the text-safe warning/HP tokens (`#b97c73` / `#b3483e`) — and a repository contract test (following the existing source-scan pattern) fails if dark-surface small-text CSS ever uses the deep seal-red token or its raw hex.
- **Redesign the shell header.** The header bar (mockup: `#171715`, border `#514c43`) shows the game title on the left; on the right, the **current location** (from the synced status panel), the **world date/time** (existing clock payload), and the **connection state as a green dot + label** ("● 已連線", ok-green `#709676`; non-ok state keeps a shape+border pairing, never color alone). The raw "模式：exploration" label is removed — mode is already self-evident from the dock content, and the mockup (matching design doc §5.1: "game title, location, world date/time, and connection state") has no mode field.
- **Style the action dock as the mockup's command surface.** The dock gains the mockup chrome: a 1px seal-red frame (`#211c18` surface), a guidance line naming the shortcuts ("方向鍵選擇・Enter 確認・Esc 返回・/ 開啟指令", dim 11px), and **grid buttons** — equal-width cells with the focused button on the seal-red fill with a `▶` glyph prefix (a shape indicator, so focus never relies on color alone), unfocused buttons bordered `#514c43`, disabled buttons dimmer (`#3c3933` border, `#716d65` text) while staying focusable for their explanation. Submenus follow the combat mockup's split: a **button grid on the left and a detail pane on the right** (dock-level `≈1.35fr / 0.9fr`) that names the focused item, its availability, and the next key action ("Enter → 選擇目標"). The keyboard router's existing grid geometry (`menu.grid`/`gridCols`, already implemented and Node-tested but unused by any menu) is exercised for the first time; the root exploration menu keeps a seven-column row (7 entries when Quests/Inventory are available — owner decision — fewer when a capability is absent), exploration submenus use a 2-column grid, and the combat root/submenus and the services/creation/character submenu item lists adopt the same grid + detail split as the mockup. The router also gains a repeated-Space suppression guard (held Space must not repeatedly toggle AREA candidates), and the shared row renderer wires every disabled cell's reason to a programmatically associated description element (`aria-describedby`), readable in the detail pane or visually hidden, so the disabled-reason association contract holds at every navigation depth including the root. For odd-count 2-column grids the final cell (the back cell) sits bottom-left, reachable by the router's wrap-around, by `focusItemByKey`, and by pointer.
- **Enter in the drawer field always sends, however the field was focused.** `elosern_ui.routeKeyboard` routes Enter/Escape to the drawer only while `drawer.isOpen()`, and clicking directly into the field never sets that flag, so the field is dead under the mouse until `/` or a free-form dialogue opens it. Treat the drawer field itself as the open drawer whenever it is the keydown target: Enter without Shift sends exactly one command through the existing single drawer-owned send path, Shift+Enter inserts a newline, Escape closes and restores action-dock focus, and the plugin contract still claims exactly the events the router consumed. Remove the vestigial `form-control` class from the textarea (Bootstrap is not loaded by this page). The command input area stays a permanent bottom component (owner exception), keeping the current focus semantics: a send from the input area leaves focus in the input area, and a send from a dock button leaves focus in the button panel — focus stays where the player acted, so consecutive same-kind actions need no pointer interaction.
- **Fix the misaligned send button.** `.inputfieldwrapper` is `position: relative` with the button absolutely positioned at `right: 0; height: 100%`, while the field uses `calc(100% - 2.25rem)` against a 2rem button — and neither child has `box-sizing: border-box`, so the 1px borders overflow the wrapper and the field/button leave a 0.25rem ragged gap. Replace the absolute-position width arithmetic with a flex row: the wrapper becomes a flex container, the field grows (`flex: 1`), the button keeps a fixed 2rem width, and both children adopt `box-sizing: border-box` so borders stay inside the wrapper. Hover/focus styling is unchanged.
- **Every exploration submenu gains a final back row.** The DOM-independent exploration menu model adds an enabled "返回上一層" row as the last cell of the move, look, interact, wait, target, and keyword submenus (never to the root), flagged `goBack`; the exploration dock handles it — routed through the existing pointer/keyboard submit gate — by popping exactly one router frame and re-rendering the parent's cells, so pointer users get the same backtracking the keyboard gets from Escape (owner exception: the back button is kept even though the mockup does not draw it). The back row is placed last to match the services dock's established cancel-last convention and to keep each submenu's primary action in its existing first cell. In the same fix, the dock learns to keep its rendered cells matched to the router's current frame at every depth: today an intermediate-depth Escape (e.g. look → target → Escape) leaves the dock showing the deeper menu's rows while the router navigates the parent — a violation of the existing "renders exactly the keyboard router's current menu frame" contract.
- **Remove the GoldenLayout tab strip.** The layout config sets `settings.hasHeaders: false`, so the raw `componentName` titles ("header", "narrative", "art", …) stop rendering altogether. Panels are self-identifying by content — and now by explicit panel headings ("角色狀態", "附近地圖") where the mockup draws them. The redesigned header bar stays, as does every required component. Dead `.lm_header`/`.lm_tab`/`.lm_title`/`.lm_close_tab` overrides are removed from `goldenlayout.css`.
- **Make the unread marker self-explanatory.** The marker becomes a labeled control — "↓ N 則新訊息（點擊返回最新）" — rendered as a real button with border, hover, and focus-ring states, kept sticky at the top of the narrative, hidden entirely when the count is zero (today an empty pill always sits on top of the log), and announced through a `role="status"`/`aria-live="polite"`/`aria-atomic="true"` wrapper so the live-region contract is preserved. Clicking it still jumps to the bottom and clears the count, as does scrolling to the bottom; keyboard activation moves focus to the narrative pane so focus never vanishes into a hidden element.
- **Add the mockup's gauge bars and panel headings.** The status panel gains the "角色狀態" heading and HP/MP/SP gauge bars with the mockup's fill colors (HP `#b3483e`) — numeric text stays (the theme requirement keeps "resource values SHALL include numeric text"). The minimap panel gains the "附近地圖" heading and the mockup's panel styling while keeping the landed lattice. The art panel's truthful placeholder adopts the mockup's green-brown gradient with the scene label at bottom-left, and the contextual portrait overlay gains the mockup's 2px seal-red frame.
- No backward-compatibility shim or stored-layout migration ships: the project is unreleased, and the old tab strip, dead send button, cryptic marker, trappable submenus, and off-design palette are removed outright. Layout wrapper version stays 1 (the wrapper schema is unchanged; `hasHeaders` is a default-config field, and unknown/malformed stored wrappers already reset to the approved default).

## Capabilities

### New Capabilities

- None.

### Modified Capabilities

- `webclient-desktop-shell`: Four requirements change. "The WebClient loads a local desktop GoldenLayout shell" gains the no-tab-strip contract (components are identified by content, never by GoldenLayout tab titles). "Required desktop surfaces remain visible and usable" gains the header contract (game title, current location, world date/time, connection state with an ok-green indicator) and the action-dock chrome contract (seal-red frame, guidance line naming the shortcuts, grid-button rendering with shape-marked focus and dim disabled cells). "The command drawer preserves ordinary text control" gains the always-send-on-Enter contract: focusing the drawer field by any means makes the drawer ready to send, Enter without Shift sends exactly one message, Shift+Enter inserts a newline, and focus after a send stays where the player acted (input sends keep input focus; dock sends keep dock focus). "Narrative output remains the authoritative text surface" gains the labeled-marker contract: the unread indicator is a labeled control that names its jump action and is hidden when there is nothing unread. "Theme and controls remain accessible" gains the approved palette families (deep seal red, ok green, warm paper, charcoal surfaces) and serif narrative/headings, keeping the pairing rule that focus and status never rely on color alone and that disabled reasons stay programmatically associated with their controls.
- `webclient-exploration-menu`: "The exploration dock is keyboard-first and re-homes the service submenus" gains the back-navigation contract (every exploration submenu ends with a back row that returns to the parent menu; the dock's rendered cells match the router's current frame at every depth; Escape pops exactly one level) and the mockup rendering contract (the dock renders its root as an equal-width button row and its submenus as a button grid beside a detail pane, with the guidance line naming the shortcuts).
- `webclient-combat-menu`: Implementation/visual only — the combat dock adopts the mockup's root-row and skills-grid-with-detail-pane layout; no requirement text changes (the spec governs the keyboard hierarchy and adapters, not the visual layout).
