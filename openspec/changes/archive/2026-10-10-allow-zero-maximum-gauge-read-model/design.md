# Design

## Context

The status/character read model validates every gauge through `world/rules/status_query/readers.py:_require_gauge`, which raises `StatusQueryError` when `int(round((base + mod) * mult)) <= 0`. The monster data model deliberately produces gauges whose maximum is zero: threat-tier bands carry zero MP/SP, and balance-approved variant profiles (e.g. `ridge_burrow_hare` 掘巢型, live individual #236) author `mp: 0, sp: 0`, used verbatim per `world/rules/traits.py` (`initial_trait_config_for_variant`, lines ~214-241). Consequently `web/gm/readers/monsters.py:detail` sees `build_status_read_model` / `build_character_read_model` raise, and `web/gm/readers/_sections.py:compute_sections` degrades 資源 / 狀態與增益 / 屬性 to `source_unavailable`. No reader test caught it because `SYNTH_MONSTER_VARIANTS` fixtures all carry `mp > 0`.

Verified during proposal (grounds the decisions below):

- The deterministic core already tolerates zero gauges: Evennia's `GaugeTrait._enforce_boundaries` clamps to `min((base+mod)*mult, value)` with no positivity requirement, `DeterministicGaugeTrait` inherits it (rounding to int), `trait_config_for_values` builds `base: 0, rate: 0` gauges, and `restore_gauges_to_full` sets `current = max = 0`. Combat-adjacent zero-maximum paths already fail soft and are test-pinned: the flee predicate guards a non-positive maximum against division, `state_reactions` loss-fraction derivation yields 0 for a non-positive maximum, and `preview_skill` disables skills whose target's HP is zero.
- The GM reader path divides nothing: `characters.resources_section` renders `current` with unit `"/ {maximum}"`, `traits_section` renders `f"{current} / {maximum}"`, and `_gauge_breakdown` decomposes `base + equipment_total == maximum` arithmetically — with base 0, mod 0, mult 1 the zero gauge yields a zero row with zero layers (an `mp +N` cap on worn gear would raise the existing "not explained by worn equipment caps" error, which is correct: a zero gauge with an attributed ceiling is exactly the drift the reader must keep failing on).
- The Vue clients already guard division: `webclient-app/components/vitals.js:gaugeRatio` returns 0 for `maximum <= 0` (test-pinned for `maximum: 0` in `webclient-app/tests/data/vitals.test.js`), `admin-app/components/GmMeter.vue` uses `max > 0 ? … : 0`, and `admin-app/lib/format.js` ratio formatting returns "—" for a zero denominator. The GM portal monster sections are plain ledgers with no meters at all.
- One wire validator disagrees with the relaxation: `web/webclient/presentation/character.py` trait-row validation requires `max` within `minimum=1`, so the version-5 `character` panel would reject a gauge row whose payload the relaxed read model now produces (its gauge-row contract is `effective == max`, `current <= max`). The `status` presenter itself has no positivity check and the client mirror reads `maximum` unbounded.
- `combat_panel.py` participant validation keeps `hp_maximum >= 1`: a living combat participant with a zero HP maximum cannot engage (the engage path's liveness checks already reject it), and a zero-HP monster is already handled by the combat view tests (`test_combat_view.py` pins `base 0 / current 0` monsters rendering). HP specifically never legitimately has a zero maximum: no tier band or approved profile zeroes HP, only MP/SP. Out of scope to relax, and relaxing it would weaken the wire guard.

## Goals / Non-Goals

**Goals:**
- A stored gauge whose computed maximum `int(round((base + mod) * mult))` is exactly `0` with stored (or defaulted) `current` `0` reads through the shared read model as valid state, so every GM and player surface consuming it renders `0 / 0` rows. Acceptance is defined purely on the computed maximum plus the existing per-field type and `current` bounds — no new positivity check is added on the individual modifiers (`base: 1, mod: 0, mult: 0.4` rounds to a zero maximum and reads as `0 / 0` exactly like the sanctioned `base: 0` shape; a `mult` that rounds a gauge to zero is displayable at the gauge reader, but the character model still fails it at breakdown attribution — see D4).
- Every genuinely corrupt gauge — negative computed maximum, nonzero current on a zero maximum, `current > maximum`, type violations — keeps failing closed with `StatusQueryError` exactly as today.
- The webclient `character` wire validator stops rejecting the zero-maximum rows the relaxed read model legitimately emits; no payload schema change.

**Non-Goals:**
- No change to gauge construction, regen (`rate = maximum × 1% = 0` for free), the equipment ceiling sync (`sync_equipment_gauge_limits` writes `mod = caps`, which already agrees with `_gauge_breakdown`'s attribution), combat costs/clamps, or possession routing.
- No relaxation of the combat-panel `hp_maximum >= 1` wire bound (see Context) and no schema-version bumps.
- No compat layer or migration: the relaxation only widens accepted reads — every previously accepted state stays byte-identically accepted, zero-maximum gauges with valid current become newly accepted, and negative computed maxima plus every existing type/current-bound violation remain rejected — so no stored data changes meaning.

## Decisions

**D1 — Accept zero-maximum at the reader, not at each call site.** `_require_gauge` becomes: after the existing type checks, compute `maximum`; raise when `maximum < 0`; keep `current` defaulting to `maximum` when unset (so an unset-current zero gauge reads `0/0`, matching GaugeTrait's own "full" default); keep the existing `current < 0` and `current > maximum` bounds — which then already reject a nonzero current on a zero maximum. Alternative considered: special-case monsters in the GM reader (a monster-only lenient path). Rejected: it forks the fail-closed contract that gm-runtime-state depends on, and the character panel/text status consume the same builder. The check "maximum == 0 requires current == 0" needs no new code: it is exactly `current > maximum`.

**D2 — Relax only the character-panel trait-row `max` bound, to `minimum=0`.** `web/webclient/presentation/character.py:_validate_trait_row` changes `maximum = _require_int(value, "max", minimum=1, …)` to `minimum=0`; the paired invariants (`effective == max` for gauge rows, `current <= maximum`) stay, so a wire row claiming `max: 0, current: 3` is still rejected at the boundary. Alternatives: (a) dropping `max` to null for zero gauges — rejected, it destroys the gauge-row identity contract and the drawer's layer-attachment agreement (`use-status-drawer-status.js` matches `trait.max === resources.maximum`); (b) leaving the validator strict — rejected: the same read model also feeds the text `inventory`/`status` views and any future surface that serializes trait rows, and a validator stricter than its own producer turns valid stored state into an unavailable panel with no diagnostic.

**D3 — Combat surfaces keep their positivity guards.** `combat_panel.py` `hp_maximum >= 1`, the flee predicate, and `state_reactions`' non-positive-maximum fail-safe stay exactly as they are: they defend arithmetic (division, percentages) and liveness semantics, not display. The read-model relaxation does not flow into them (they never called `_require_gauge`).

**D4 — Breakdown accepts the sanctioned zero row without special-casing; its attribution checks stay authoritative.** With D1, `_gauge_breakdown` sees `gauge.maximum = 0`, `base = 0`, `mod = 0`, `mult = 1` for the sanctioned shape: `mult != 1` still raises (so a zero achieved via a zero/fractional multiplier — accepted by the gauge reader alone — still fails the whole character-model build at breakdown attribution, exactly as it does for a positive gauge; the relaxation is display-state acceptance, not an attribution bypass), `_equipment_layers` contributes nothing, `equipment_total != mod` / decomposition-agreement checks pass at zero, and `_validated_row` only validates layers (none). No code change; a test pins the sanctioned zero maximum decomposing to a bare base-0 row so a future layer rule cannot silently start rejecting it.

**D5 — Tests carry the contract via traceability.** Fixtures must stop being mp-positive-only: the GM monster reader tests gain a zero-MP/SP synthetic variant (mirroring the sanctioned profile shape) asserting the three shared sections render with `0 / 0` rows. `world/rules/tests/test_status_query` gains zero-maximum-pass and negative-maximum-fail cases on both builders. Each new/changed main-spec requirement (post-sync IDs under `webclient-status-presentation` and `gm-runtime-state`) gets a `@covers_requirement`-annotated behavior test per `docs/development/spec-test-traceability.md`. Existing tests pinning the old rejection (the `_require_gauge` `<= 0` wording is asserted only through behavior — `test_status_read_model.test_missing_gauge_fails_closed` and `test_character_read_model` field/bounds cases remain valid; the literal-message string "non-positive maximum" is pinned nowhere in tests, verified) are extended, not weakened.

## Risks / Trade-offs

- [A stored zero-maximum gauge with nonzero current (drift) becomes rejectable only via `current > maximum`] → Same `StatusQueryError`, just a different message; behavior (fail-closed) is unchanged and pinned by a test.
- [Some consumer divides by a gauge maximum outside the audited set] → Audited: all `_require_gauge` consumers are `status.py`, `character.py`, `breakdown.py` (no division); clients guard zero (`gaugeRatio`, `GmMeter`, `format.js`); `status_query` `GaugeValue` flows only into those surfaces. Combat never passes through the read model. A regression test runs a zero-maximum entity through the full GM monster detail and webclient status/character presenters.
- [A future writer stores `base: 0` with a fractional or negative `mult` (a "zeroed" gauge)] → the gauge reader accepts whatever `int(round((base + mod) * mult))` computes to 0 or above with a consistent `current`, because it validates the computed maximum, not the modifier signs (`base 0, mod 0, mult -1` reads as `0 / 0`); the character model still fails such a gauge at `_gauge_breakdown`'s `mult != 1` attribution rule, and any combination computing to a negative maximum fails everywhere. Accepted posture: the gauge reader's job is stored-resource display; attribution strictness stays where it already lives.
- [GM readers AST contract forbids writers; the new fixture must not create state] → Fixture follows the existing `SYNTH_MONSTER_VARIANTS` construction path, only with `mp=0, sp=0`.

## Migration Plan

Single coordinated deploy: reader relaxation + wire-bound relaxation + tests land together. No data migration, no rollout ordering, no rollback data concern (accepting more reads is reversible by reverting the two validation comparisons).
