# Proposal: square-face-rect-contract

## Why

The 臉部框選 modal advertises a 「方形裁切預覽(1:1)」 and the gallery design (2026-09-08 §1/D9/§6) names square avatar crops as the goal, yet nothing in the stack enforces a square: the modal drags and resizes at any aspect ratio (its one ↘ handle moves `w` and `h` independently), its "1:1" preview in fact preserves the raw rect's aspect, and `validate_face_rect` bounds only the unit square — any positive `w`/`h` combination stores. Players therefore mark non-square boxes that the square avatar frames silently letterbox differently from what they drew.

## What Changes

- **BREAKING** The stored `face_rect` contract gains a square rule: a card's rectangle must be *pixel-square* — `w × image_width` and `h × image_height` agree within one pixel — enforced at the single art-API validator `world/art/gallery.py::validate_face_rect` wherever the image's pixel size is known: card append, face-rect update, the generation-request seam, and the seed path. Player-submitted rects must be square *as dispatched on the player's screen pixels*, which for the non-square portrait canvas means `w ≠ h` is legitimate (`w = h × image_height / image_width`), so squareness can be checked only against the image size, never as `w == h`.
- **BREAKING** The ten-key card contract becomes an eleven-key contract: each card gains `image_size`, the pixel size of the card's stored image, recorded at append time from trusted provenance — the actual decoded size of the bytes the worker encoded for `generated` cards, a Pillow decode of the copied bytes for `seed` cards (`GeneratedImage.width/height` are only the *request* dimensions and are not trusted). It is a stored fact of the image itself, not an environment-driven generation knob, and it is the reference `validate_face_rect` checks squareness against. Client-side square-locking makes the server-side reject path exceptional, and no rect is ever adjusted — a violating submission is refused verbatim.
- **BREAKING** The card default rectangle becomes image-aware and pixel-square: a card written without an explicit rect is filled with `default_face_rect(image_size)` — the shared upper-half anchor squared against that card's image (on 768×1024: `{x:0.25, y:0.06, w:0.5, h:0.375}`, a 384×384 px box). There is **no value-equality exemption** anywhere: any rect validated against a known image size, including a replayed legacy default constant, must be pixel-square. The pinned `DEFAULT_FACE_RECT` constant itself is unchanged and remains the presentation anchor for card-less assets (classic assets, size-unknown fills, fallback-map gaps), where `default_face_rect` on a square size equals it exactly. Automatic generation stops passing the constant explicitly (`face_rect=None`), so auto cards take the fitted default.
- **BREAKING** The gallery wire contract and its mirrored legacy validator follow: gallery rows keep their exact key set (no `image_size` on the wire — the payload schema admits no size), but the server-computed 預設臉框/自訂臉框 chip can no longer be re-derived from the literal default constant — it is authored against the card's recorded `image_size`, which never crosses the wire; the presentation validator and its exact mirror in `web/static/webclient/js/elosern/protocol/panels/art.js` accept either face chip without literal re-derivation (dual-direction parity tests stay green).
- The 臉部框選 modal square-locks its geometry: drag-to-move unchanged; drag-to-resize and each numeric edit re-derive the other dimension from the loaded image's `naturalWidth`/`naturalHeight`, so the box is square *on screen* (pixel-space) at all times and the 1:1 preview label becomes true (the preview crop becomes square, and its stale 「保留原始比例」 note is reworded). 儲存框選 is disabled until the image has actually loaded (a failed load stays disabled), so the client never squares geometry against a guessed aspect.
- **BREAKING** `FALLBACK_FACE_RECTS` are re-authored to squares: each keeps its current head-height vertical span on the 864×1536 committed images and grows symmetrically (transparent-background widening crops no figure pixels; the 8 px overhang on `man` is the max) — a contract test decodes each committed default and asserts squareness per file.
- The design document `docs/superpowers/specs/2026-09-08-character-gallery-art-design.md` is amended in place (§3.1 face_rect row, §6, and an addendum to the D9 decision line) to record the square constraint and the recorded-pixel-size provenance rule.
- Test suites updated on both sides (Vitest face-geometry suite re-authored for square-locked helpers; Python validator/card-contract/seed/fallback/action tests), with `@covers_requirement` retargeted to the amended and new requirements.

## Capabilities

### New Capabilities

_None — every behavior lands in an existing capability._

### Modified Capabilities

- `art-gallery-model`: the face-rect requirement gains the pixel-square rule with no value exemptions and a fitted `default_face_rect(image_size)` fill, and the new `image_size` card-key requirement changes the card contract from ten to eleven keys (`validate_face_rect` semantics, update rejection scenarios).
- `art-gallery-generation`: the generation-request seam gains the square check against the planned render size (bounds known before enqueue) and auto-generation stops carrying the legacy constant explicitly.
- `art-gallery-seed-sync`: the manifest `face_rect` is preflighted pixel-square against the decoded sizes of the subject's eligible images before either manifest field is honored; non-square degrades the manifest whole on the existing diagnostic.
- `art-gallery-resolution`: the presenter validates a resolved card's rect against the card's recorded `image_size` and degrades the malformed case to the fitted default for that card; the payload square guarantee is stated.
- `webclient-gallery-panel`: the row-contract coherence rule relaxes only the face chip — both validators accept 預設臉框 or 自訂臉框 without re-deriving which from the stored rect; row keys are unchanged and carry no `image_size`.
- `webclient-gallery-ui`: the face-rect modal requirement changes — square-locked drag/resize/numeric editing against the image's natural size, a pixel-square dispatched rect, and a genuinely square 1:1 preview.
- `webclient-gallery-management-actions`: the `gallery.face_rect.update` payload requirement changes — in addition to the existing bounds, a submitted rect must be pixel-square against the card's recorded `image_size`, and a non-square submission is rejected with the card unchanged.
- `art-gallery-fallback`: the fallback seam requirement changes — the fixed per-key rectangle map carries pixel-square rectangles for the committed images.
