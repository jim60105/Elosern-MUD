## ADDED Requirements

### Requirement: Runnable Evennia project skeleton
The project SHALL contain an Evennia game directory (Portal + Server) that starts inside the
container and reaches a state where it accepts player connections, structured so that the
directories design doc §3.2 names (`typeclasses/`, `world/`, `commands/`, `web/`) exist and are
ready for later changes to populate.

#### Scenario: Server starts inside the container
- **WHEN** the container starts and runs `evennia start --log`
- **THEN** both the Portal and Server processes reach a running state, and log output is visible on
  the container's stdout

#### Scenario: Player can connect
- **WHEN** a telnet client connects to port 4000, or a browser opens the webclient on port 4001,
  after the server has started
- **THEN** the connection succeeds and the default Evennia login/welcome screen is presented

#### Scenario: Directory layout matches the design
- **WHEN** the game directory is inspected after initialization
- **THEN** `typeclasses/`, `world/`, `commands/`, and `web/` exist at the locations design doc §3.2
  specifies, ready to receive the empty-stub subpackages (`world/lore/`, `world/rules/`,
  `world/quests/`, `world/ai/`, `world/imports/`, `world/art/`) that later changes populate

### Requirement: First-run database initialization is a runtime action, not a build-time artifact
The SQLite database SHALL be created and migrated against a mounted volume at runtime, not baked
into the container image. A profile-gated one-shot bootstrap service SHALL migrate a fresh
database and interactively create Account #1 before the normal service first starts. The normal
startup script SHALL continue to apply pending migrations idempotently on later starts.

#### Scenario: Fresh volume is initialized by the bootstrap service
- **WHEN** the one-shot bootstrap service runs against an empty database volume
- **THEN** it applies the migrations, interactively creates Account #1, and produces a usable
  database file in the mounted volume

#### Scenario: Bootstrap credentials are ephemeral
- **WHEN** the operator supplies the initial Account #1 password through the interactive bootstrap
  terminal
- **THEN** the password is absent from image layers, Compose environment values, and the long-lived
  service container configuration

#### Scenario: Normal startup applies later migrations
- **WHEN** the normal service starts against a bootstrapped database volume
- **THEN** the startup script idempotently applies pending migrations before running
  `evennia start --log`

### Requirement: Secret settings are never baked into the image
Evennia's generated `server/conf/secret_settings.py` (or equivalent secret key material) SHALL NOT
be present in the built container image's layers.

#### Scenario: Image contains no secret key
- **WHEN** the built image's layers are inspected
- **THEN** no secret key file generated by Evennia's initialization is present in any layer
