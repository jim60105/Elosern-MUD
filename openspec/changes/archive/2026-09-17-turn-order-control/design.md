## Decisions

### D1 — Action provisioning is a count, skip-at-zero stays the pinned leg

`run_round`'s zero-lock leg stays first but reads the matched rules' per-rule bundles (already public via `matched_combat_modifiers`): ANY matched zero-action rule skips the turn (origin-blind over rule OUTPUT, then chance-resolved per D4), so a co-existing `+1` grant can never probabilistically or arithmetically unlock a certainty — this closes the generic-merge hole where `paralysis (0) + grant (+1)` merged to 1 and a 15%-chance lock could probabilistically unlock a paralyzed combatant (a real bug class the wave introduces: before the wave, no positive row had a consumer, so the merge never mattered). An entity with no matched zero rule computes `count = int(merged.get("actions_per_turn", 1))` from the shipped generic merge (untouched — no cross-key awareness enters `_merge_adjustments`). `count` is clamped to a hard loop maximum (`_MAX_ACTIONS_PER_TURN = 3`, load-independent constant, a runaway-bundle fuse: any declared bundle beyond it provisions 3 and the fuse is documented, not silently honoured). The provider-call body becomes an inner `for _ in range(count)` at the SAME sequence position; before every slot the shipped liveness predicate (fled / knocked-out / hp≤0) is re-evaluated, so a combatant defeated or KO'd mid-round by an earlier actor's strike loses the remaining slots — no provider call, no event. Each slot is one ordinary provider interaction with the shipped semantics: a `None` request for a slot means "no action for that slot" and the loop moves to the next slot (matching the existing per-key `continue` shape — a provider that has run out of targets simply spends its remaining slots as no-ops, exactly as a 1-action monster returns None today). ItemUseRequest slots ride `resolve_item_use` verbatim; the journal/notification sinks are the same round's sinks. The whole round stays ONE outer transaction (the session's existing boundary): the requirement wording makes the round transaction invariant explicit rather than newly introduced. Rationale for clamping over rejecting: the bundle is a merge of unrelated rules; a `ValueError` inside round resolution would abort a combat round over an authoring sum — the fuse degrades loudly-documented instead, and the catalog's authored row (one rule granting +1) never approaches it.

### D2 — Positional ops are declarative marker data, folded at the loop boundary

Mechanics never mutate the initiative list from inside effect handlers (a staged effect cannot know the loop's cursor, and an apply-time list mutation would be invisible to rollback and to `action_preview`). Instead:

- Buff definitions gain `round_order: {action: <verb>}` — `MARKER_VOCABULARY`-style closed load validation (`advance_to_head`, `retreat_to_tail`), an optional `BuffDefinition` field beside `marker`, shape fail-closed, inert when no round consumes it.
- The reaction `then` vocabulary gains `mark_order_op:<buff-definition-key>`: holder-gated (a `physical_hit` + `buff_active` rule), validates the named key at load and at dispatch (must be a live definition carrying `round_order`), and its action APPLIES that definition to the event SOURCE (for the static_ward micro-rung: the melee attacker gets the `round_order: retreat_to_tail` marker). Distinct from `apply_buff_to_source` only in the extra load-time `round_order` presence check — kept as a separate verb so the load validator can fail closed on a key lacking the clause (the ignite verb stays open for plain debuffs; static_ward's rung wants the guarantee).
- `run_round`'s fold: the loop iterates over a local list. Before each combatant's turn it scans the not-yet-acted tail for live `round_order` marker instances (one deterministic read per remaining key, definitions via `BUFF_DEFINITIONS`, instances via the shipped active-instance read), collapses same-key ops (last-pushed-instance-wins by apply order; advance beats retreat on an exact same-instance tie is unreachable — one key one action verb), and relocates: `advance_to_head` moves the key to the first position of the tail still to act; `retreat_to_tail` moves it after the current tail end. Keys already acted this round are untouchable (silently ignored — 「本回合」 semantics); keys absent from the sequence (fled/dead pre-round) are silent no-ops, the `first_actor` precedent. Ops apply to the local snapshot only — `roll_initiative` output identity, next round re-rolls clean, and rollback never sees sequence state (the sequence was never a durable surface).
- The 神格 tail-push (thunder_apotheosis's own cast hits targets and pushes them) is NOT an effect-handler mutation either: the catalog mounts it as a damage `EffectPolicy(audience=ENEMIES)` whose hit riders apply a `retreat_to_tail` marker row to struck targets (the `apply_buff`-per-audience shape), and the fold picks the still-unacted victims up before their slots. A target that already acted this round is unaffected — the lore line 「本回合行動順序被推到最後」 prices exactly the still-to-come.

Rejected: a `reorder` parameter on `run_round` (a caller-side seam cannot serve reactions firing mid-resolution); an effect handler mutating `order` (staging/rollback violation, preview divergence); a full keyed priority queue (out of scope — the shipped flat d100+agility scoring stays the sole round-open authority).

### D3 — `mark_order_op` dispatch is apply-time best-effort, fold-time authoritative

The reaction dispatch runs inside the strike's commit (like `apply_buff_to_source` verbatim): it applies the marker instance. It emits no order mutation itself; `run_round`'s next fold reads it. An op applied AFTER the affected key already acted is a no-op by D2's acted-key rule — the same code path handles both "victim hasn't acted yet" (relocated) and "already acted" (nothing), no branches by caller.

### D4 — The 15% action-loss gate: declared `chance` on the lock rule (option (a))

The condition engine (`rulebook/schema.py:57-66`) is pure-state AND with zero probability vocabulary, and the ratified rule-table discipline keeps `evaluate_combat_modifiers` a documented pure read — so probability CANNOT live in the condition engine, and a closed once-per-hit marker (option (b)) would ship static_ward's 「15% 機率」 as a deterministic lie. Decision: the narrow declared-chance field —

- `combat_modifiers.yaml`'s `then` grammar gains optional `chance: <int 0-100>` legal ONLY alongside `actions_per_turn: 0` (load-validated fail-closed everywhere else — no chance on agility rows, no chance without a lock). Resolution reads the table's per-rule MATCHED bundles (`matched_combat_modifiers`, already public and status-display-consumed), NOT the merged fold: any matched zero-action rule WITHOUT a declared chance SHALL force the certain skip (a co-existing chance — e.g. ward micro-stun on a paralyzed combatant — can never probabilistically unlock a certainty); otherwise the MAXIMUM chance among matched zero rules decides (the elevation-ladder fold: 15 under 30 merges to 30 by domination, order-independent). The merged bundle keeps its shipped generic fold untouched — the generic `_merge_adjustments` has no cross-key awareness and gains none.
- The ONLY consumer is `run_round`'s skip leg: a chance-decided zero rolls exactly one seeded `roll_d100()` per gated combatant per round at the combatant's turn — roll ≤ chance → the shipped `action_skipped` event (its `data` records `{"chance": n, "roll": r}` — replayable through the existing event-log surface); roll > chance → the combatant acts normally. The roll happens inside the round transaction exactly where the skip decision already lives; a rolled-back round consumes it with everything else. The matched-bundle read is still origin-blind (it inspects rule output keys, never rule identity — the shipped no-origin-branch pin holds).
- `action_preview` / `action_preview.py:169` unchanged: it keeps its shipped merged-bundle `== 0` gate and stays roll-free (its no-randomness requirement holds — it never sees the chance roll). Its known advisory divergence from resolution: a chance-locked holder merges to `0` and previews forbidden until the winning dice act (false-forbidden), and a lock+grant co-match merges positive and previews enabled while resolution skips (false-enabled) — both ride the shipped preview-is-advisory / resolution-is-authoritative posture verbatim; no preview code changes.
- The catalog re-homes the micro-rung: flicker's 「觸發率提升」 is a second authored rule row at a higher `chance` (data, not a code ladder).

Determinism argument: seeded `roll_d100` is the same dice seam every shipped settlement (to-hit, resist, flee) already uses; recording the roll in the event data makes the outcome reconstructable from the log, exactly the `disengage_attempt` optional-roll convention.

### D5 — Vocabulary is element-agnostic and inert

`round_order`, `mark_order_op`, `chance`, and the count-consumption leg contain zero element or skill keys. At ship time ZERO live rows use them (the two dev-era lightning illusion rows die with the catalog change), so every existing golden/pin stays byte-identical: every shipped bundle has `actions_per_turn ∈ {absent, 0}`. Tests ride synthetic buff/registry rows per the ratified discipline.

## Risks / Trade-offs

- **Provider-loop × ItemUseRequest:** a 2-action combatant may use an item as its first slot and an action as its second — legal, priced by the lore's 「額外行動機會」 (an opportunity, not a spell-only slot); the journal sink already covers multi-entity item journals within one round.
- **`_merge_adjustments` addition can over-provision:** two +1 rules from different sources fuse-clamp at 3 (D1) rather than error; documented, and no shipped or planned row stacks two grants.
- **Fold read cost:** one active-instance scan per not-yet-acted key per turn (O(n²) per round on roster-sized n — n is combatant count, tiny; same order as the existing per-turn `evaluate_combat_modifiers`).
- **The chance roll lives in the round loop, not the rule engine:** two places "read the same table." Mitigated by the narrow legality (chance only rides a lock-zero) and the single named consumer; the rule table stays declarative data, which is what the constitution's modifier-table capability is for.
- **Retreat-to-tail after an already-retreated key:** repeated `retreat_to_tail` folds keep pushing back (last-op-wins relocates); no oscillation risk because advance ops originate from the holder's own cast (one per round per buff refresh).
