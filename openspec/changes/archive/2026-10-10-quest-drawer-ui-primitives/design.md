# Design

## Context

The approved prototype (`docs/design/quest-drawer-redesign/QuestDrawerPrototype.vue`) inlines every piece: the top tabs, the rail, the gems, the glyph paths, and a compact copy of the rank card. Production components must come from shared units. `components/dock-icons.js` is the client's single glyph table (24×24 stroke paths, `aria-hidden` beside text). The rank block lives inside `GuildCounter.vue` together with its `.elosern-root` skin rules in `styles/app-shell.css`. Storybook renders game stories under `.elosern-root` (`.storybook/preview.js`). The component-coverage manifest is frozen and pinned by the showcase evidence tests.

## Goals / Non-Goals

**Goals:**
- One tab primitive serves both the horizontal first level and the vertical second level, so focus, tooltip, and badge behavior is identical.
- Pixel parity with the prototype for the tab, gem, and glyph visuals.

**Non-Goals:**
- No generic tooltip system for the rest of the client. The tooltip is internal to `IconTabs` until another consumer needs it.

## Decisions

1. **`IconTabs` API.** Props: `tabs` (`[{ key, label, glyph?, count?, hot?, disabled?, reason?, locked?, dim?, mark?, controls? }]`), `modelValue`, `orientation` (`horizontal` | `vertical`), `ariaLabel`. It emits `update:modelValue` only when the selection changes, and a scoped `icon` slot receives the tab. Each tab is a `button` with `role="tab"`, `aria-selected`, an `aria-label` built from `label` (Decision 3), and `aria-controls` when the tab carries a `controls` panel id. The tablist carries `aria-orientation`. The roving `tabindex="0"` sits on the selected tab (or the first tab when nothing matches) and follows arrow-key focus; when focus leaves the list it returns to the selected tab. Disabled tabs use `aria-disabled="true"` rather than native `disabled`, so they stay focusable and their reason is reachable. Clicking or pressing Enter on a disabled tab does nothing. The reason is wired with `aria-describedby` to visually hidden text. `reason` is not limited to disabled tabs: a selectable tab may carry one too (for example a locked grade's 尚未開放 or the player's own grade), and it is shown and described the same way. Selection follows activation, not focus: arrow keys move focus, and Enter or Space selects. With six or seven tabs, automatic activation would re-render the list on every keystroke.
2. **Tooltip placement by orientation.** Vertical tabs show the tooltip to the right, horizontal tabs below. The tooltip shows on `:hover` and `:focus-visible`, never steals pointer events, and shows `label`, plus ` · reason` whenever the tab carries a `reason`. A pure-CSS `::after` approach is enough. The prototype's `data-tip` rules show the exact geometry.
3. **Badges.** The badge renders only when `count > 0`. It is ink and gold by default; `hot` is seal-red with a glow. The tab's accessible name includes the count (`label（count）`) whenever `count` is a finite number, zero included, so the badge is never color-only.
4. **Locked and dim.** `dim` lowers icon opacity (an empty category). `locked` adds the `lock` glyph as a corner mark and a dimmer icon. Both stay selectable, because the consumer shows an explanatory empty state. `mark` draws the small gold "this is yours" dot.
5. **`GradeGem` materials as data.** The F→S material ladder lives in `components/grade-materials.js` as a map from grade key to CSS custom properties (`--gem-hi`, `--gem-lo`, `--gem-rim`, `--gem-ink`, `--gem-inner`), with values copied from the prototype. Unknown keys get the iron (F) material. The component is decorative (`aria-hidden`) unless `label` is passed. The letter always renders, so meaning never depends on material.
6. **Verbatim extraction.** `GuildRankCard.vue` receives the services `guild.rank` object as `rank` and emits `exam_request` with the same `{action_id, payload: {target_rank}}`. Its root is the `.guild-counter__rank-card` element (crest, rank text, merit, meter, status, exam block), which is exactly the compact card the prototype hosts in the counter list column. The `guild-counter__section guild-counter__rankblock` wrapper and its 公會等級 heading stay in `GuildCounter.vue`, because they are the counter's section chrome; the `data-top-rank` attribute moves from that wrapper onto the card root, and the card root gains `data-testid="guild-rank-card"`. Every other `guild-counter__*` class name and data-testid is kept, so existing tests and browser selectors keep matching. The `.elosern-root .guild-counter*` skin rules in `styles/app-shell.css` never target the rank card's classes. A class rename now would churn browser tests twice: the old surface is deleted in `quest-drawer-guild-board-tab`. The two literal durations map to tokens by role: the meter fill's `400ms` becomes `--motion-slow` (400ms, the vitals-fill token), and the exam button's `150ms` control feedback becomes `--motion-fast` (120ms, the control-feedback token).
7. **Glyph naming.** New keys are prefixed by role (`quest_book`, `guild_counter`, `quest_in_progress`, `quest_completed`, `quest_failed`, `cat_gather`, `cat_defeat`, `cat_escort`, `cat_explore`, `cat_emergency`, `track_flag`, `reward_copper`, `reward_merit`, `reward_item`, `deadline`, `lock`), with the prototype's path data. The prototype's `ICONS` map supplies every path except `lock`, which the prototype drew as a CSS box; `lock` is drawn new at the set's weight (shackle plus body). `cat_gather` copies the prototype's 採集 leaf path. The prototype rendered every glyph with round caps and joins, so every new key carries `stroke-linecap` and `stroke-linejoin` `round` in `STROKE_ATTRS`; stroke width stays the consumer's choice, as for the existing keys.

## Risks / Trade-offs

- [Manifest pinning churn] → the new titles are added to `PREVIOUS_MANIFEST_KEYS` / family constants exactly the way `World/LettersPanel` joined, keeping the frozen-set assertions meaningful.
- [Visual drift from the prototype] → task 4.2 compares the Storybook screenshots side by side with the `Design/QuestDrawerRedesign` stories at 1451×790 and 1920×1080.

## Visual review (task 4.2)

The Storybook captures of `Core/IconTabs`, `World/GradeGem`, and `World/GuildRankCard` were compared with `Design/QuestDrawerRedesign` at 1451×790 and 1920×1080 with `agent-browser`. Measured geometry matches the prototype at both sizes: rail tabs 60×58 px (79.4×68.8 at 1920×1080), grade rail tabs 52 px tall, top tabs 64×48 px with 28 px glyphs, rail glyphs 26 px, badges 18 px, and rail gems 34 px (45 px at 1920×1080). In a real browser, Enter and Space each select once with no synthesized click, a disabled tab takes focus and shows `label · reason` in its tooltip, and it never selects. The intentional deviations:

- **Lock mark.** The prototype drew the locked-grade corner mark as a CSS box. `IconTabs` draws the `lock` glyph instead, per Decision 4, so the mark matches the glyph set.
- **Gem inner rims scale.** The gem's 2px and 3px inner rims and 3px corner radius are written as `calc(<n>px * var(--ui-scale))`, as the tasks require for every size. At the 1451×790 reference they are identical; above it they grow with the rest of the gem.
- **Exam button timing.** The rank card's exam button transition moves from a literal 150ms to `--motion-fast` (120ms), per Decision 6.
- **Tooltip clipping is the host's concern.** The tooltip is an `::after` that overflows the tab (right of a vertical tab, below a horizontal one). A host that puts a rail inside a scrolling or `overflow: hidden` box clips it; the drawer changes must leave the tooltip's side unclipped, as the prototype does.
- **Tooltip is not dismissible.** The CSS tooltip shows on hover and keyboard focus and cannot be dismissed with Escape (WCAG 1.4.13). The tab's accessible name and its `aria-describedby` reason already carry the same text, and the client targets desktop pointers only, so this stays a known gap until a shared tooltip exists (a Non-Goal of this change).
