## Goals / Non-Goals

**Goals:** one shared fail-closed save gate for all fourteen domain verbs and raw batches; narrow owner adapters to existing rules; transport contracts sufficient for client forms; contextual controls with truthful save notices and refreshed results; complete synthetic behavior/contract coverage.

**Non-Goals:** repairing detected fault catalogues, adding any further verb, authoring source through the portal, experience/combat-result dedicated verbs, raw model SQL or narrative editing, typeclass changes, arbitrary code, new audit persistence, new player commands, AI-service requests, game-client/OOB integration, a second inventory model, new retention or restore policy. S1–S5 contracts change only at the explicitly listed S6 extension seams.

## Decisions

### 1. Server-owned coordinator and closed owner registry

Use `server/console/snapshot_policy.py` for baseline/status/manual-save integration, `server/console/raw.py` for raw writes, and a small shared execution/registry boundary under `server/console/` for named dispatch, action evidence and operation outcomes. Register a fixed mapping of verb names to named APIs in the four owner `gm.py` modules. No client-provided import paths or reflection dispatch. `web/gm/console_api.py` parses JSON shape, invokes that boundary and converts results/errors. The existing raw route branches by HTTP method: GET retains the S3 reader, POST forwards to the console raw execution path.

Alternatives rejected: web field writers violate ownership; putting all verbs in `world/rules/gm.py` steals quest/map/narrative ownership; duplicating save checks per endpoint risks ungated writes. Shared coordination is sequencing, not ownership of game fields. Keep the registry/errors/results small and explicit rather than introduce a generic RPC/action framework.

The static console contract must understand existing legitimate S4 prompt-reload and S5 save calls: they remain allowed for their purposes. New console calls are restricted to the registered four owner APIs/raw boundary through the coordinator. Continue to forbid direct model/Attribute writes in web transports. The reader-only AST contract remains scoped to `web/gm/readers/`, unchanged and stronger than a whole-app blanket ban that would incorrectly forbid S6 dispatch.

### 2. Gameplay-thread execution handoff and lock order

Every console operation executes on the gameplay reactor, never on the Django request thread. `server/console/execution.py` owns one handoff seam: the coordinator passes it a single synchronous callable that reads the boundary tick, validates, runs the owner transaction with its compensation and returns the outcome plus the post-attempt tick. In the running server the seam is `twisted.internet.threads.blockingCallFromThread(reactor, callable)`: the callable runs on the reactor, its result returns to the web thread, and a synchronous exception re-raises in the web thread. When the reactor is not running (unit tests, management commands) the seam runs the same callable inline on the calling thread, mirroring the landed `drain_synchronous` convention in `world/art/worker.py`; tests substitute the seam to script deterministic interleavings.

Rejected alternative: a console-only mutex. It cannot exclude reactor-owned gameplay, and the reused writers are not safe across it (pre-transaction inventory planning, per-call clock objects, snapshot-then-restore compensation), so a web-thread call could lose a committed player change. Rejected too: spanning a database transaction or lock across the handoff (it would cover file I/O), and any new global game lock (the reactor already is the single gameplay writer).

Consequences fixed here:

- Snapshot and other file I/O never enter the handoff: the pre-save is created on the requesting web thread before the mutation callable, so no blocking backup or art mirror runs on the reactor and no owner transaction spans one. The pre-save completes fully — including art-gate release and retention pruning — before the handoff, so the web thread never waits for the reactor while holding the art gate that reactor-thread publishers need.
- The boundary tick that drives the save decision is read inside the same callable as the mutation, so no player advance can interleave between the check and the write. Status keeps the landed non-creating read.
- Lock order is fixed and acyclic: (1) the process-local coordination lock in `server/console/snapshot_policy.py`, taken nonblocking and held outermost, on web threads only; (2) beneath it S5's `_snapshot_lock`/`_restore_lock`, taken nonblocking by `create_snapshot` on the web thread and released before any handoff; (3) the reactor handoff, whose callable takes only ordinary game-state and handler locks and never the coordination lock, the S5 snapshot locks or the art gate (the landed art gate is always taken before the queue/gallery locks). No owner verb or raw write may re-enter the coordinator, so a web thread waiting on the reactor can never be part of a cycle. No new lock, timeout or retry is introduced.
- Liveness and re-entry: the seam switches on the reactor's running state, and tests substitute the runner so deterministic mode never depends on that check. While the gameplay loop runs, the request thread hands off and waits; when it does not run at all (unit tests, management commands, or the window while the server is shutting down) the same callable runs inline, because no concurrent gameplay exists to serialize with — the landed S5 pre-save refusal still applies there while a restore is pending. A handoff attempted from inside a handoff cannot be serialized on the loop it already occupies and therefore refuses with `snapshot_failed` instead of blocking, which the rule that no owner verb or raw write re-enters the coordinator already forbids structurally. The blocking wait itself stays unbounded by design: the handed callable is pure game-state work with no I/O, so a single-operator console needs no timeout that could abandon a committed write.

### 3. Snapshot decision, baseline and ordering

Keep `baseline_tick: int | None` in process memory, initially None. Status uses `read_world_clock`, never `get_world_clock`; a missing clock reports null tick and cannot enable a write, and write attempts return `target_not_found` rather than creating a clock in a reader. The normal game startup supplies the clock. Console execution and manual-save entry serialize through the one nonblocking coordination lock of decision 2, nested over S5's own nonblocking snapshot lock.

Contention is answered, never queued. A console request that cannot take the coordination lock, or whose `auto_intervention` snapshot meets S5's `save_in_progress`, refuses with `snapshot_failed` and a recorded reason: baseline and game state stay unchanged and nothing is written. Manual-save entry uses the same coordination boundary but keeps S5's delivered contention contract — an attempt that cannot take the coordination lock or S5's snapshot lock returns the existing `save_in_progress` refusal (HTTP 409) and is never queued behind a console operation. No retry, poll or wait-for-turn is added to either path.

Represented tick. The baseline and the saves page must describe the world a save actually contains. `server/saves/snapshot.py` therefore gains one snapshot-scoped reader that opens the copied database read-only (the stdlib `sqlite3` pattern of `server/saves/inventory.py:applied_migrations`) and reads the persisted world-clock tick out of that copy: the persistent world-clock Script's `tick` Attribute, whose `db_value` is a base64-encoded pickle the reader decodes and unpickles, treating an absent or undecodable value as no represented tick. It derives the in-game date with the existing calendar computation. That reader — not the metadata callable's clock key — becomes the manifest's `clock` source and the console baseline's source, so a gameplay advance between the backup and metadata collection can no longer make a save claim a tick it does not hold; `world_metadata`'s live clock read leaves the save path, and its live player summary stays an informational field that is never used as a baseline. The reader stays injectable so the deterministic S5 tests keep their seam: their synthetic copy carries no script attributes, so they inject the represented tick, and the two landed assertions that read the injected metadata clock move to that seam. A copied database without a world clock yields no represented tick: the baseline becomes None (fail-closed, the next console write takes a save) and is never guessed from live metadata.

Execution sequence:

1. Access/CSRF/method checks and transport-shape/name validation precede dispatch; rejected transport or unknown verbs take no save and no game write.
2. Take the coordination lock nonblocking. If it is unavailable, refuse as above; nothing further is attempted and no game state is touched.
3. First handoff: read the boundary tick on the gameplay thread and compare it with baseline. No baseline or any difference (not just greater-than) needs a save, so the callable returns that decision without mutating; an equal tick needs no save, so the same callable continues into step 5.
4. The pre-save `create_snapshot("auto_intervention", label)` runs on the web thread outside the game transaction, so it holds committed pre-operation state and a rejected operation cannot roll it back. If it fails, preserve baseline, return `snapshot_failed`, record the failure and never call a writer; S5 owns failed-file cleanup and its facade exception evidence. A second handoff then runs the operation, reading a fresh boundary tick at its start.
5. The handed callable invokes the owning validated operation or raw batch as one synchronous reactor operation covering validation, the owner transaction, live-state compensation and the post-attempt tick read that measures the operation's own clock advance. Record whether a real save completed even if the operation rejects; a successful save followed by refusal is a real undo point, not a failed snapshot.
6. Once the transaction and any compensation have settled, the baseline becomes the represented tick of the save that gated this operation plus the clock advance this operation itself applied — measured inside the callable as the post-attempt tick minus the tick read at its start, and therefore zero for a rejected operation and for every verb that does not advance time. When no save was required, the baseline is the unchanged baseline plus that same advance. The post-attempt tick serves that measurement, the response payload and the action evidence; it is never adopted as the baseline, so a live read that gameplay advanced past the save's represented tick can never be absorbed.
7. Emit `gm_action` with real outcome and return a state payload for the relevant surface. No successful event precedes durable operation completion.

A successful manual save initiated by the S5 page uses the same coordination boundary, wraps the existing S5 call and sets baseline from the snapshot-backed represented tick — never a later live read, and None when the copy carries no clock. Failure, including contention, leaves baseline unchanged. Do not reset for list/download/delete or `auto_restore`; restart after restoration naturally starts with None. No baseline storage/migration or scan of historical saves.

Alternative rejected: snapshot every write produces redundant saves; using wall time misses the approved in-game policy; an old persisted baseline could suppress the first process-start undo point; a blocking or queued coordination lock would silently replace S5's delivered fail-fast contention with queueing. Status is advisory: confirmation fetches it, actual POST reevaluates policy. No client baseline is trusted. Console/manual serialization does not promise an all-world pause of player activity; the baseline capture must not hide player time progressed outside its operation boundary.

### 5. Atomic raw batches and S3 round-trip

POST raw body is `{"operations": [<operation>, ...]}`. Each operation has `op` plus exactly its fields:

- `set_attr`: `key`, optional `category` (string or null, default null), `value` (JSON).
- `del_attr`: `key`, optional `category` with the same default.
- `add_tag` / `remove_tag`: `key`, `category` (string or null).
- `set_location`: `value` as `{"$ref":"#123"}` (with optional S3 `typeclass`/`key` display metadata) or null to clear location.

Use Evennia Attribute/tag handlers and location storage inside one owner transaction. Prevalidate the complete batch shape and recursively decode references before game-state writes. `$ref` resolves its identifier, never trusts optional display metadata. Reject malformed/missing references and `$unserializable` display markers; arbitrary ordinary JSON dictionaries remain dictionaries. Preserve array order and JSON primitive types. There is no deserialization of executable Python, arbitrary import or eval.

No rule/invariant check is added: raw location does not call movement settlement or repair party/pins/dialogue; this is deliberately distinct from teleport. Transaction/handler cache invalidation must make rollback visible to subsequent live reads, not just a freshly queried ORM row. Attributes/tags/location are editable; components/typeclass/creation date stay inspection-only. Do not interpret an unconvertible S3 marker as a supported raw value.

Alternative rejected: direct model patching would bypass Evennia handlers/caches; multiple independent POSTs for a batch violate approved all-or-nothing behavior; a generic editable tree would imply that every displayed field is writable.

### 6. Routes, envelopes and outcome projection

Register protected GET `/gm/api/console/status` before the variable POST `/gm/api/console/<verb>` route. `status` is reserved, not a callable verb. Extend the existing raw route's method dispatch instead of creating competing URL patterns. Preserve API fallback JSON and method `Allow` behavior.

- Status success data: `{"tick": <int|null>, "baseline_tick": <int|null>, "will_snapshot": <bool>, "snapshot": {"taken": false, "save_id": null}}` (a required minimum, not an exhaustive payload). With a missing live clock, `tick` is null and `will_snapshot` is true; the UI cannot submit and the server fails closed, and status itself creates nothing.
- Write success: `{"ok": true, "data": {"target": <identity>, "state": <updated projection>, "snapshot": {"taken": <bool>, "save_id": <id|null>}}}`.
- Write failure: `{"ok": false, "error": {"code": <code>, "message": <zh-TW>}, "snapshot": {"taken": <bool>, "save_id": <id|null>}}`. Snapshot metadata is an additive sibling of the existing error, never a replacement envelope. Preflight/access failures have no completed snapshot; missing metadata means no save, not fabricated saved state. Preserve metadata on the GM API error object so failure presentation can acknowledge a completed undo save.

Errors: 404 `unknown_verb`, `registry_key_not_found`, `target_not_found`; 400 `invalid_argument`, `target_kind_mismatch`, `raw_edit_invalid`; 500 `snapshot_failed`, whose zh-TW message distinguishes a failed save from a save or console operation already in progress so a retryable busy condition is not read as an internal fault; unexpected operation failures use `internal_error` (500) and facade exception evidence. Add these console message entries, including `internal_error`, to the existing response map rather than assuming a generic fallback exists. Extend its error helper with optional snapshot metadata while preserving every existing caller's envelope. Access/CSRF/method codes retain existing behavior. GET raw retains S3 `object_not_found`/`kind_mismatch`; raw POST target lookup uses console `target_not_found`, and a write attempted while no world clock exists reports that same code. A failed raw reference is `raw_edit_invalid`, not a partially successful batch. Registry/owner validation details use stable codes and zh-TW messages; do not expose English exception prose or branch on prose.

Reuse existing authoritative read projections after completed mutation. For normal entity verbs return the target's applicable updated section/detail; raw returns its S3 raw representation; spawn returns the new monster plus affected room identity; quests return the owner's quest section; memory returns effective record/history/generation; clock returns world tick/date; delete returns `{"deleted": true, "dbref": <identity>}` and an affected room identity if available. Do not turn a successfully committed deletion into a read-not-found failure. A post-commit projection failure must not pretend the write rolled back: return the actual successful operation identity/snapshot with a localized state-section error and allow the normal manual read refresh.

## Risks / Trade-offs

- Tick-only baseline misses player changes without elapsed time → retain the approved limitation explicitly; do not add change hashes or per-action snapshotting.
- Snapshot and operation are separate boundaries, so the baseline tracks the save's represented tick plus the console's own advance → never a live post-operation read that gameplay may have advanced past the save's content.
- A mirror created or deleted inside the operation must survive late failure like any other surface → reuse the landed deleted-instance flush and contents-cache reconciliation, and assert live contents caches, not only reloaded rows.
- The handoff blocks one web worker until the reactor callable returns → keep that callable pure game-state work with no file I/O or user interaction, and never take the coordination, snapshot or art locks inside it.
- Snapshot and game-state transactions are different boundaries → preserve a completed save even if the writer rejects; metadata/logging distinguish save success from operation success.
- Evennia handlers, traits and live registrations cache state beyond ORM rollback → reuse established compensation and test the same live instances as well as reloaded rows, especially inventory, movement/deletion, raw edits and clock settlement.
- Current inventory representation differs from the design's rationale prose → use existing repeated-key canonical storage and owner-equipped-removal synchronization; no new inventory subsystem.
- Existing memory APIs update effective fields → tests assert immutable original content/provenance, not incorrect whole-row immutability.
- A stale confirmation may predict the wrong save choice → status is advisory and POST policy is authoritative; display returned metadata.
- Raw edits can knowingly leave game invariants broken → permanent bypass warning, whole-batch rollback on failure and S5 undo; do not add unapproved raw rule validation.
- A new interface can inadvertently bypass readers/access or duplicate game UI → keep URL resolver, web writer/reader AST and token-import contracts, and reuse the landed GM component layer only.

## Migration Plan

No data migration or compatibility path is required. Implementation lands the owner operations, shared snapshot/raw execution and contextual surfaces together, replacing only the obsolete method/navigation restrictions. The one S5 change outside S6's own modules is the provenance of the manifest clock, which is read from the copied database; no manifest field, format or migration changes. Ordinary save behavior, GET/recall inspection, player rules, authored source and game bundle remain unchanged. Operator undo restores the real S5 pre-intervention save through the existing shutdown/pre-start restore workflow, not in-process field rollback of a successful operation. Proposal delivery itself creates only this change's artifacts on master; it does not apply, archive, alter source or touch the stale S5 branch/worktree.
