## 2. Choice-point core state machine (DOM-independent)

- [x] 2.1 Create a DOM-independent transition module (e.g. `web/static/webclient/js/elosern/choicepoint_logic.js`) exporting a pure reducer `nextChoicePointState(previous, committedSuggestions)` over the finite states `absent | generating | ready`, where `committedSuggestions` is the validated `{status, cards}` object (or the sentinel `none` when the committed `context_actions` panel is absent, `kind !== "exploration"`, or carries no suggestions section): generating→generating and ready→ready are no-ops; generating→ready replaces; any other transition — ready/generating → degraded, unavailable, `none`, or an unknown status — goes to `absent`. No `document`/`window`, no store access, deterministic.
- [x] 2.2 Unit-test the transition table with hostile fixtures: generating→generating, ready→ready, each elimination path (degraded, unavailable, combat kind, missing panel, unknown status), and idempotence of repeated identical commits.
- [x] 2.3 Wire the store subscription (`subscribe` in `web/static/webclient/js/elosern/protocol.js`, post-`commitPresentation` notifications): on each notify, read `getState().panels["context_actions"]`, extract `suggestions`, run the reducer, and invoke the render adapter (§3) on each state change; a `beginTransport` notification (panels cleared) at any time resolves to `absent` **synchronously on that same notification**, so a ready block from a retired epoch is removed before any new snapshot arrives (never waits for `ui_sync`).
