# Design

## Context

See `proposal.md` for motivation. This is a proposal-only corrective follow-up to the five archived minimap changes and thirteen archived world-map changes, not a new map design. The architectural authority is `docs/superpowers/specs/2026-07-29-ai-mud-engine-design.md`, especially D3, D16 and the read-only presentation boundary. Current `openspec/specs/` contracts take precedence over archived plans. The two 2026-10-22 parent designs explain intent; archived `compute-minimap-auto-scale-projection`, `label-minimap-exits-and-gateways`, `publish-world-map-panel` and `redesign-map-drawer` explain approved refinements.

Static inspection confirms the relevant seams. `MapLattice.vue::stubHitBoxes` joins arrow and unleadered-label boxes. `minimap_projection.js::spreadExits` defaults to diameter 20 while renderer geometry reserves `GATE_FOOTPRINT = GATE_ARCH_R + 2`; `ringGrid` begins at 10 m. `map_quest_destinations.py::_room_world_cell` omits tagged ordinary rooms and reads the `InstanceRoom.origin_room` autocreating property. `world_map_geometry.current_point` already uses read-only instance-origin access and tagged place registrations. The protocol reducer retains same-epoch on-demand map bodies and clones them on publication; `use-map-drawer.js` requests on open while `MapDrawer.vue` can render a retained body. Thus object identity and an arbitrary newer store revision cannot prove a fresh map response. These are source observations, not claims that regression tests were executed.

## Goals / Non-Goals

**Goals:** Correct the six named boundary failures with existing components and regression owners. Keep local movement tied to the exact committed descriptor and preserve canonical enclosing-place semantics without adding coordinates to interiors. Make opening freshness explicit while preserving viewport memory.

**Non-Goals:** No new wire fields, protocol versions, server discovery state or request mechanisms. No changes to room typeclass default behavior across the engine. Do not alter geographic registries, content, partition output, balance, movement rules or clock semantics. No compatibility path, migration or resurrection of deleted overlay code.

## Decisions

### D1. Disjoint stub hit regions own only the stub

Always return the compact arrow box as the native button's base hit region and a separate label box, independent of `label.leader`. Reuse the existing separated-label child/positioning and pointer-event pattern already used for leadered labels. The wrapper and empty rectangle between those regions must not intercept the SVG exit beneath. Keep the existing full accessible name and single native button, with the Space propagation protection; do not synthesize an extra keydown click. A pointer hit on either stub region uses the original stub action; a visible street hit uses the street action. Preserve `exit_ref`, `destination` and `current_node` through the real movement boundary and keep the island's blank-canvas opener out of actionable activation. Changing only z-index would exchange one interception defect for another and is rejected.

### D2. Share the canonical enclosing-place lookup, preserving both position contracts

Extract the existing ordinary-room tag resolution from `world_map_geometry.current_point` into a small read-only helper in the existing shared `map_quest_destinations.py` owner, then use it from both world geometry and `_room_world_cell`. This module already owns canonical cell resolution and does not depend on world geometry, avoiding a cycle. The helper reads `PLACE_REGISTRY`, deduplicates matching `settlement_key` values, requires exactly one enclosing anchor and resolves its cell from `ANCHOR_GEOGRAPHY_REGISTRY`. Several place tags naming the same anchor are valid; conflicting anchors, missing registrations/geography and genuinely unlocatable rooms return `None`.

Use a shared one-level instance-origin unwrapping helper in the same owner, reading `room.attributes.get("origin_room")`. Missing, null or another-instance origins remain unknown; no recursive graph walk, guessed exit traversal or new room property is needed. Use this safe path for actor origins and bound-instance destinations, and retain the current world-position path's safe origin behavior. A live bound instance keeps `room:<dbref>` identity even when its world cell is unknown.

Keep TerrainRoom and GridRoom branches ahead of ordinary Room handling. Do not replace `world_node_point` with the cell resolver. World current-point geometry still uses the existing wilderness cell-centre offset and physical settlement transform, while commission destinations and area external bearings retain their approved anchor-cell semantics. Registered ordinary interiors use their enclosing anchor cell, with the existing +0.5 world-display offset only at the world-geometry boundary. Do not grant the interior a grid/wild node ID or coordinates. Retain possession's owner quest log with the controlled actor's position.

### D3. One pure source for painted marker geometry

Move the existing marker-size declarations needed by projection and renderer into one small pure geometry module in `lib/`, consumed directly by projection, `use-map-lattice-geometry.js` and `MapLattice.vue`. Migrate all affected imports; keep no re-export alias. Include gateway arch/feet extent and stroke reservation from the existing glyph rather than authoring an unrelated second clearance constant. Keep unrelated rendering/layout constants in their current owner.

Extend overlap checks to pairwise ordinary/gateway footprints derived from each exit's actual painted state. The projection remains pure and both `LocalMap.vue`'s precomputed projection and the geometry composable's fallback use the same policy by construction. Maintain symmetric spreading about the circular mean with the existing ±20-degree cap and deterministic ordering. Keep radial distance and current centre unchanged; exits outside collision groups retain exact bearings. The two gates at (-120,800)/(120,800) with level 1000 must clear at their painted feet, as must a feasible mixed gate/ordinary pair. Arbitrarily crowded groups cannot be promised full clearance inside the cap; preserve the cap and deterministic finite behavior. A blanket diameter increase for all exits is rejected because it would perturb unaffected ordinary bearings.

### D4. Scale-derived bounded ring candidates

Keep the existing ring mantissas, maximum count, minimum radius and minimum radial gap. Derive the first candidate decade from the finite positive `dMin` rather than a hardcoded 10 m floor, and derive the useful upper decade from the positive span and existing finite distance ceiling. Bound the exponent iteration explicitly for the valid input domain; reject zero/nonfinite candidate distances before mapping. Deduplicate candidate distances, then keep the current in-span-first ordering and canvas/readability filters. Do not allocate geometry proportional to metres.

The 1 m equal-distance case must consider 1 m and retain its ring at the unchanged equal-distance radius 66. Keep 80/1200 m mixed compression mapped through the same mapper, with finite separated rings and truthful labels. Existing zero/no-distance handling must stay finite and must not invent a positive span. Changing the compression formula, level ladder or unrelated mutable constants is unnecessary.

### D5. The drawer owns opening freshness; the reducer owns publication identity

Add local per-map committed-publication metadata to `protocol/store.js`, recording the adopted map revision within the current generation/epoch. Update it only when `commitPresentation` adopts that logical map body, including the completed multipart path. A retained same-epoch cache, unrelated snapshot, action-result notification or clone does not advance that map's publication mark. Reset marks with the existing map/session retirement paths. Expose the metadata through `stores/elosern/view.js`; it is client-internal state, never part of a wire body or serializer.

`use-map-drawer.js` owns an opening token, scope-request identity and per-opening world baseline readiness. Capture the current world publication mark when dispatching the opening's world request, including a first switch from area. Qualify only that opening's request ID in the same generation/epoch after a successful result and complete available world adoption matching the result's declared presentation revision. Require a world publication newer than the captured mark. A partial transfer or unrelated revision cannot qualify. Handle result-before-body and body-before-result symmetrically through existing settlement/lock rules. An earlier opening's late reply may update the normal same-epoch cache but cannot qualify the new opening's own request. Failed or unavailable responses use existing loading/unavailable presentation, never a false ready baseline or automatic retry.

Pass baseline readiness/opening identity through `AppClient.vue` to the data-free `MapDrawer.vue`; hold the world view at the existing loading/unavailable boundary until its fresh opening response qualifies. The first eligible render establishes knowledge silently. Keep the ready state for the rest of that opening, rather than hiding/remounting on every busy refresh, so a real committed discovery after baseline still reaches the mounted `WorldMapView.vue` and reveals once. Carry the existing epoch and effective motion inputs; retire pending frames/announcement tokens on close/session retirement. Preserve per-tab view and selection memory separately and retain it when the world view is first mounted after refresh. Tab remounts silently baseline already presented knowledge and cannot replay effects.

Keep requests active-scope-only, once per committed move, never while closed. Do not clear unrelated map caches, add polling or create a retry queue. Global cache deletion, prop object-reference comparison and a broad `busy` rendering guard are rejected: they either lose valid memory, mistake clones for publications or suppress genuine open discoveries.

### D6. Parent status is completion documentation

During apply, first replace the stale world-map parent status with an accurate statement that its original thirteen changes are integrated and this named corrective follow-up is pending. Likewise correct the minimap parent's obsolete full-map follow-up statement and link the pending corrective change while retaining its five-change completion history. Only after all corrective acceptance is satisfied, update both status/follow-up lines to record the completed correction with evidence references. This proposal does not edit either parent now and does not label the correction implemented. Preserve historical design sections as the pre-cutover baseline and do not rewrite archived tasks or evidence. All new technical prose is English; canonical Traditional Chinese game terms remain unchanged.

## Risks / Trade-offs

- Publication/result ordering or cloned map bodies could accept stale knowledge. Use per-map committed revision plus current opening/request/session identity, with integrated ordering regressions.
- A geometry extraction could introduce Vue dependencies or stale aliases. Keep the shared footprint owner pure and migrate all imports directly in the same implementation unit.
- A broad location refactor could lose physical world positioning or create interior coordinates. Share only canonical enclosing-place and safe-origin helpers; keep grid/wilderness world transforms unchanged and test unknown/ambiguous controls.
- Overlap clearance cannot satisfy arbitrarily dense groups within a fixed angular cap. Prove feasible gateway/mixed cases while retaining bounded deterministic behavior for saturation.
- Persisted-state assertions can themselves autocreate the value. Use handler presence and database-backed snapshots before any property access.

## Migration Plan

Deploy the correction as one normal unreleased-project code update with unchanged wire shape and no persisted-data migration. Follow dependency order in `tasks.md`: shared origin reads before presenter regressions, shared marker geometry before projection/renderer integration, publication metadata before drawer freshness, then documentation completion. Rollback uses the normal release/code rollback; there is no repair command or compatibility fallback.
