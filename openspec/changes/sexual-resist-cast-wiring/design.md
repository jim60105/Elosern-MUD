## Context

`world/rules/action.py`'s `ActionResolver.resolve()` runs a fixed pipeline: `_step1_ownership` →
`_step2_resource_check` → `_step3_targeting` (returns the resolved `targets: list[Any]`) →
`_step4_capability` → `_step5_effect_resolution` (dispatches each `skill.effects` string to a registered
handler prefix, passing the *same* `targets` list to every handler) → `_step6_resource_deduction` /
`_step6_skill_practice` / `_step6_combat_kill_xp` → `_step7_build_event_log` (turns every staged
`PendingEffect` into `EventEntry` rows via `_entries_from_effect`, keyed by a `|`-delimited description
prefix looked up in `_ENTRY_TEMPLATES`) → the `_EVENT_EFFECT_PLANNERS` pass → `_commit`.

A sexual act's `SkillDef.effects` list (built by `_act_family()`) is always exactly
`["pleasure:<key>", "sexual_counter:<key>", *("sexual_event:<name>", ...)]`. `_handle_pleasure_effect`
and `_handle_sexual_counter_effect` each independently call `participants(actor, targets)`
(`world/rules/sexual_act_effects.py`) against the *same* `targets` parameter `_step5_effect_resolution`
hands them — they do not communicate with each other, and nothing between them can currently change what
one handler sees based on what another handler decided.

`resist_verdict(actor, resister, *, rng=roll_d100)` (`world/rules/sexual_resist.py`) is a pure,
side-effect-free two-party contest: no `Battlefield`, no entity mutation, no lazy-trait materialization
(verified — it reads through `evaluate_combat_modifiers_no_create`/`build_no_create_condition_context`
throughout). It returns a `ResistVerdict(resisted, auto_comply, roll, actor_score, resister_score)`.
`_scan_sexual_coercion` (`world/rules/combat_session.py`, already shipped) already scans every
`EventLog` in a combat round for `kind == "sexual_resist"` entries and already loops correctly over
multiple such entries per round (its own test suite proves this via `test_multiple_forced_entries_
each_apply_their_own_penalty`), so it is already compatible with an `AREA` cast producing one entry per
target — this proposal only has to produce that shape, not change the consumer.

## Goals / Non-Goals

**Goals:**
- Give `resistible=True` acts a real resist contest at cast time, using `resist_verdict()` unmodified.
- Emit exactly the `EventEntry(kind="sexual_resist", data={"resisted": bool, "auto_comply": bool, "roll":
  int | None})` shape `_scan_sexual_coercion` already documents, so `B6b`'s code needs zero changes.
- Exclude a successfully-resisting target from the act's pleasure/counter/event effects without touching
  `_handle_pleasure_effect`, `_handle_sexual_counter_effect`, or `_handle_sexual_event`.
- Support `AREA`-target resistible acts (not yet shipped, but already proposed by `sexual-catalog-shame`)
  by resolving one independent contest per target.
- Keep the change fully additive to every already-merged capability's contract: no edit to
  `sexual_resist.py`, `combat_session.py`, `_builder.py`, or any catalog module.

**Non-Goals:**
- The out-of-combat cast path (`cast_settlement.py`/`commands/action.py`) — that is
  `sexual-resist-out-of-combat`'s explicitly deferred territory, unaffected by this change.
- Any change to `resist_verdict()`'s contest formula, affinity table, or auto-comply thresholds — `B6a`'s
  territory, already correct and already tested.
- Any change to how `_scan_sexual_coercion` applies its affinity penalty, snapshots roster relations, or
  wraps its transaction — `B6b`'s territory, already correct and already tested, and already written
  against exactly the contract this proposal produces.
- New catalog content. No `sexual_acts/*.py` module changes; `sexual-catalog-shame`'s three
  `resistible=True` `AREA` acts remain that proposal's own scope to implement.
- A structural registry-load-time invariant forbidding `resistible=True` on a `TargetSpec.SELF` act. No
  shipped or proposed act combines the two (verified: every `resistible=True` act across landed and
  proposed catalogs is `SINGLE` or `AREA`), so this proposal defends against the combination at the
  wiring layer (D-2) rather than adding a validator to `_builder.py`, which `B4` owns and which this
  proposal does not touch.

## Decisions

### D-1: A new pre-effect-resolution step, not a new effect-string prefix

A resistible act's resist outcome must be known *before* `_step5_effect_resolution` runs, because it
changes what `targets` the pleasure/counter/event handlers should see — but effect-string handlers
(`_EFFECT_HANDLERS`) are dispatched independently per string in `skill.effects`, with no shared mutable
state between them and no way for one handler's outcome to filter another's input. Adding a
`sexual_resist:<key>` effect string (auto-generated by `_act_family()`, dispatched like `pleasure:`) was
considered and rejected: it would require editing `_builder.py` (out of scope, `B4`'s territory) and
would still face the same ordering problem, since `_step5_effect_resolution` has no mechanism for an
earlier handler's return value to filter a later handler's `targets` argument.

Instead, this proposal adds one new private step function, `_step4b_sexual_resist_gate(request, skill,
targets) -> tuple[list[Any], list[PendingEffect]]`, called from `ActionResolver.resolve()` between
`_step4_capability` and `_step5_effect_resolution`:

```python
def _step4b_sexual_resist_gate(
    request: ActionRequest,
    skill: SkillDef,
    targets: list[Any],
) -> tuple[list[Any], list[PendingEffect]]:
    act = SEXUAL_ACT_REGISTRY.get(skill.key)
    if act is None or not act.resistible:
        return targets, []
    surviving: list[Any] = []
    pending: list[PendingEffect] = []
    for target in targets:
        if target is request.actor:
            surviving.append(target)
            continue
        verdict = resist_verdict(request.actor, target, rng=roll_d100)
        pending.append(_resist_pending_effect(target, verdict))
        if not verdict.resisted:
            surviving.append(target)
    return surviving, pending
```

`resolve()` calls this once, right after `targets = _step3_targeting(...)`, and immediately **rebinds**
the same `targets` name to the gate's filtered return value — `targets, resist_pending =
_step4b_sexual_resist_gate(request, skill, targets)` — rather than introducing a second, long-lived
`filtered_targets` variable. Every step from that point on (`_step5_effect_resolution`, and
`_step6_combat_kill_xp`, which reads `targets` too) then unambiguously sees the same post-resist list, and
there is no `targets`-vs-`filtered_targets` name pair for a future edit to accidentally pick the wrong one
of. `_step6_combat_kill_xp` is unaffected either way in practice — no sexual-act `SkillDef` ever declares a
`damage:`-family effect — but rebinding removes the ambiguity structurally instead of relying on that fact
staying true. Both `_handle_pleasure_effect` and `_handle_sexual_counter_effect` are unmodified and
automatically receive the post-resist target list, because both already derive everything from the
`targets` parameter they are called with. The step's own `PendingEffect` list (one per contested target,
never for the actor) is prepended into `pending` alongside the handler-produced effects, so it flows
through `_step7_build_event_log` exactly like any other staged effect.

For a non-sexual-act skill (`SEXUAL_ACT_REGISTRY.get(skill.key)` is `None`) or a `resistible=False` act,
the function returns `(targets, [])` unchanged — zero behavioral change, zero performance cost beyond one
dict lookup, for every one of the other ~110 skills in `SKILL_REGISTRY` and every non-resistible sexual
act.

**Alternative considered**: filter inside `_handle_pleasure_effect`/`_handle_sexual_counter_effect`
themselves (each independently calling `resist_verdict()` per participant). Rejected: `resist_verdict()`
would then run twice per target per cast (once in each handler), rolling the dice twice and potentially
producing two different verdicts for the same contest within one cast — a correctness bug, not just
inefficiency. Computing the verdict once, before either handler runs, and threading the *result* (a
filtered target list) into both is the only shape that guarantees one dice roll per target per cast.

### D-2: The actor never resists their own act; `resistible=True` × `TargetSpec.SELF` cannot occur today

`_step3_targeting`'s `SELF` branch synthesizes `candidates = [request.actor]` when the caller passes no
explicit targets, so for a `TargetSpec.SELF` skill the actor *is* the sole entry in `targets`. The gate
above explicitly special-cases `target is request.actor` to skip the contest and always keep the actor —
defensively correct even though no shipped or proposed act currently combines `resistible=True` with
`TargetSpec.SELF` (verified against every landed and proposed catalog act: `combat_tease`,
`partner_caress`, and `partner_hand_hold` — the three currently-shipped `resistible=True` acts — are all
`SINGLE`; `sexual-catalog-shame`'s three proposed resistible acts are `AREA`). Without this guard, a future `SELF` act
mistakenly marked `resistible=True` would have its caster roll a resist contest against themselves,
`_affinity_term`'s `isinstance(resister, NPC)` check would return `(0.0, False)` for a `PlayerCharacter`
actor-as-resister, and the ordinary `d100` contest would run — not a crash, but nonsensical: a caster
could "successfully resist" their own solo act and have it excluded from their own effects, silently
breaking `D-4`'s self-pleasure invariant. Guarding at the wiring layer, not adding a `_builder.py`
validator, keeps this proposal's footprint to `action.py` alone per its stated file ownership.

### D-3: `EventEntry(kind="sexual_resist", ...)` is built the same way `damage`/`roll` already are

`_entries_from_effect` already builds a non-effect-handler `EventEntry` this way: the `damage` branch
parses a `|`-delimited `PendingEffect.description` (`"damage|{target}|{raw_roll}|{hit_flag}|{amount}"`)
and constructs a `roll`-kind `EventEntry` *and* a `damage`-kind `EventEntry` from the same staged effect.
This proposal follows the identical shape for `sexual_resist`, mirroring the `disengage_attempt` branch's
`"none"`-sentinel convention for an optional field:

```python
def _resist_pending_effect(target: Any, verdict: "ResistVerdict") -> PendingEffect:
    roll_field = "none" if verdict.roll is None else str(verdict.roll)
    return PendingEffect(
        target,
        f"sexual_resist|{_entity_key(target)}|{int(verdict.resisted)}|"
        f"{int(verdict.auto_comply)}|{roll_field}",
        frozenset(),
        lambda: None,
    )
```

`apply()` is a no-op (`lambda: None`): `resist_verdict()` has already executed by the time this
`PendingEffect` is constructed (the dice roll and every state *read* it performs already happened during
`_step4b_sexual_resist_gate`, before `_commit()` runs), and the verdict mutates no entity state — the
`PendingEffect` exists solely so the verdict becomes a logged, replayable `EventEntry`, exactly as
`combat_kill_xp`/`knocked_out_mark`'s already-`()`-returning branches show `_entries_from_effect` already
tolerates zero-entry and non-mutating pending effects as ordinary shapes.

Two changes to `_entries_from_effect` are both required, and the first is a hard prerequisite for the
second, not an independent nicety: `_entries_from_effect`'s very first line is `if len(parts) < 2 or
parts[0] not in _ENTRY_TEMPLATES: raise ValueError(...)` — a guard that runs *before* any `elif kind ==
...` branch is ever reached, and whose raised `ValueError` `_step7_build_event_log` converts into
`RejectedAction(RejectReason.EVENT_LOG_CONSTRUCTION_FAILED)`, rejecting the *entire* cast. So:

1. `_ENTRY_TEMPLATES` gains one new key, `"sexual_resist"`, mapped to a template string that does **not**
   interpolate `{data[roll]}` directly (`roll` is `None` for an auto-complied verdict, and Python's
   `str.format` would render the literal text `"None"` into the log rather than omitting it) — a
   roll-agnostic phrasing is used instead.
2. `_entries_from_effect` gains one new `elif kind == "sexual_resist":` branch, splitting
   `"sexual_resist|{target}|{resisted}|{auto_comply}|{roll}"` (`kind`, `target`, plus three trailing
   `values`, not four — `resisted`, `auto_comply`, and `roll` are the only fields after `kind`/`target` are
   consumed by `_entries_from_effect`'s shared unpacking) into `data={"resisted":
   bool(int(values[0])), "auto_comply": bool(int(values[1])), "roll": None if values[2] == "none" else
   int(values[2])}` — the exact three keys `_scan_sexual_coercion` reads (`entry.data.get("resisted")`,
   `entry.data.get("auto_comply")`), plus `roll` for narrative/audit purposes only.

Without step 1, every resistible-act cast would raise `ValueError` inside `_step7_build_event_log` and
reject outright — the exact self-defeating "`event_log=None`, `sexual_resist` entries can never be
produced" outcome D-4 explicitly reasons against achieving. Tasks §2 orders the `_ENTRY_TEMPLATES` edit
immediately before the parsing-branch edit for this reason, and tasks §3.2 requires a full-pipeline test
(cast a resistible act through `ActionResolver.resolve()` end to end, not just a unit test of the parsing
branch in isolation) that would fail loudly if step 1 were ever dropped.

The entry's `target` field carries `_entity_key(target)` (`str(target.key)`), matching
`_scan_sexual_coercion`'s `battlefield.roster.get(entry.target)` lookup exactly.

### D-3a: Two existing `sexual-act-seeds` tests need a compliant-roll mock to stay deterministic

`combat_tease` is not the only currently-shipped `resistible=True` act: `world/skills/sexual_acts/
partner.py` also declares `partner_caress` and `partner_hand_hold` as `resistible=True`, and — unlike
`combat_tease`, whose `participant_counters=()` means its target is never credited anything — both declare
`participant_counters=("duo_act_count",)`, so a resisting target's `duo_act_count` credit is exactly what
this proposal's gate withholds. `world/skills/sexual_acts/tests/test_seed_acts.py::
test_partner_seed_increments_duo_act_count_on_both_participants` casts `partner_caress` and asserts
`self.target.sexual.duo_act_count == 1` unconditionally, with no `roll_d100` mock — once this wiring
lands, that assertion depends on a real, unmocked dice roll and becomes intermittently flaky. Tasks §4.1
updates this test to `patch("world.rules.action.roll_d100", ...)` with a value forcing `resisted=False`
before this change lands, using the same D-6 mocking convention every other determinism-sensitive test in
this proposal's own suite uses. `partner_hand_hold` shares the identical `resistible=True` /
`participant_counters=("duo_act_count",)` shape but has no existing test asserting its target's counter,
so no existing test needs updating for it — noted here so a future reader does not need to re-derive why
only one of the two partner seeds required a fix.

### D-4: Resource cost, time cost, and practice XP stay unconditional on resist outcome

The original source design (`2026-08-15-sexual-act-system-overview-design.md` D-5) frames a successful
resist as "wastes the actor's turn," describing a single-target, binary-outcome mental model that predates
this system's actual shipped shape: `_step6_resource_deduction`, `_step6_skill_practice`, and
`_step8_time_cost` all run unconditionally today, for every skill, regardless of whether any effect
handler's targets end up empty — nothing in the current pipeline ties action-economy cost to
per-target effect success, and no existing mechanism could branch it per-target for an `AREA` cast where
some targets resist and others do not (there is no notion of "the turn" being partially wasted).

This proposal does not add one. The cast still consumes the actor's declared resource cost, still costs
`_step8_time_cost`'s time, and still grants skill-practice XP even when every target resists — only the
resisting target's own pleasure/counter/event effects are withheld. This reading is *consistent with*,
not a departure from, `D-4`'s existing self-limiting invariant: the actor's own pleasure gain from
`act.actor_pleasure_ratio` is likewise never gated by resist outcome (see below), so an actor who
repeatedly forces an unwilling target still accumulates their own pleasure and still spends real
resources on every attempt — the anti-abuse property the original design wanted from "wastes the turn" is
delivered by the unconditional actor-side cost and pleasure gain, not by a turn-skip mechanic this
proposal would have to invent from nothing.

**Alternative considered**: reject the whole action (`ActionResolver.resolve()` returns
`ActionResult.rejected(...)`) when every target resists, mirroring how `_attempt_flee`'s failure state
works. Rejected: a rejected `ActionResult` carries no `EventLog` (`ActionResult.rejected(reason, detail)`
sets `event_log=None`), so a fully-resisted cast would never reach `_step7_build_event_log` and could
never emit its `sexual_resist` entries — directly defeating this proposal's own purpose. The cast must
succeed (commit) so its resist outcome can be logged; only the resisted target's *effects* are withheld.

### D-5: The actor's own pleasure/counter effects are never resist-gated

`_handle_sexual_counter_effect` already applies `act.actor_counters` to `actor` unconditionally, driven by
the acting entity, not by `targets` membership; `_handle_pleasure_effect`'s actor entry comes from
`participants(actor, targets)`, which always prepends `actor` regardless of what `targets` contains
(`participants([], actor)` returns `[actor]` even for an empty list). Because `_step4b_sexual_resist_gate`
only ever *removes* entries from `targets` (never adds the actor, never removes them, per D-2), the
actor's own participation in `participants(actor, targets)` (post-rebind, D-1) is unaffected by any resist outcome
— confirmed by re-reading `participants()`'s implementation, not merely assumed. A fully-resisted
`combat_tease` (its one target refuses) still credits the actor's `hostile_act_count` and still applies
the actor's own `ratio=0.4` pleasure share; only the target's `pleasure`/counter credit is withheld.
Likewise, a fully-resisted `partner_caress` still credits the actor's own `duo_act_count` and `ratio=0.5`
pleasure share (`act.actor_counters` and the actor's own `participants()` entry, both D-5-protected) even
though the target's `duo_act_count` — a `participant_counters` credit — is withheld (D-3a). This
is the intended reading of D-4 ("every act applies pleasure to the actor"), not an incidental side effect
this proposal introduces.

### D-6: `roll_d100` is imported at module level in `action.py` and passed explicitly, matching `combat.py`'s existing testability convention

`resist_verdict(actor, resister, *, rng: Callable[[], int] = roll_d100)` binds its default `rng` value
*once*, at `sexual_resist.py`'s definition time — a caller that invokes `resist_verdict(actor, target)`
without an explicit `rng=` gets that frozen default, which `unittest.mock.patch("world.rules.sexual_
resist.roll_d100", ...)` cannot intercept (patching a module attribute after the fact does not retroactively
change an already-bound default-parameter value). `world/rules/combat.py` already solves this exact
problem for its own `roll_d100()` calls by importing the name at module top (`from world.rules.dice import
roll_d100`) and calling it as a bare name inside function bodies; its test suite
(`test_combat_party.py`) patches `"world.rules.combat.roll_d100"` — the *consumer* module's own binding,
looked up fresh on every call because it is a plain name reference inside a function body, not a default
parameter.

This proposal follows the identical convention: `action.py` gains a top-level `from world.rules.dice
import roll_d100`, and `_step4b_sexual_resist_gate` calls `resist_verdict(request.actor, target,
rng=roll_d100)` explicitly, passing `action.py`'s own module-level name at the call site (looked up fresh
every call, not frozen). Tests needing a deterministic outcome patch `"world.rules.action.roll_d100"`,
exactly mirroring `test_combat_party.py`'s existing pattern for `world.rules.combat.roll_d100`. This is a
one-line import plus an explicit keyword argument — not a new abstraction — and keeps the project's
stated cross-cutting testing obligation ("every contest and every random delta takes an injectable RNG,"
overview doc §5.3) satisfied at the call site that actually needs to be mocked.

### D-7: `AREA` resist-gating reuses the identical per-target loop `_scan_sexual_coercion` already exercises

`_step4b_sexual_resist_gate` iterates `targets` unconditionally — it does not branch on `skill.target_spec`
at all. For a `SINGLE` act (`combat_tease`, and any future one), `targets` has exactly one entry, so the
loop runs once. For an `AREA` act (`sexual-catalog-shame`'s three proposed acts), `targets` may hold
several entities, and the loop calls `resist_verdict()` once per entry, staging one `sexual_resist` entry
per target — the same "N targets, N independent contests, N independent affinity-penalty candidates"
shape `_scan_sexual_coercion`'s own `test_multiple_forced_entries_each_apply_their_own_penalty` already
proves the consumer handles correctly. No `TargetSpec`-specific branch is needed in this proposal's own
code; genericity falls out of iterating `targets` as given.

One participant-count interaction follows from this without any code change:
`compute_pleasure_gain`'s crowd multiplier (`sexual_act_effects.py`'s `EffectsConfig.participant_
multiplier`) is computed once per cast from `count = len(participants(actor, targets))` — since a
resisting target is excluded from `targets` before that count is taken, a partially-resisted `AREA` cast
against, say, two targets where one resists yields `count = 2` (actor + one complying target) rather than
`3`, changing the crowd-multiplier tier from `"3+"` to `"2"` for the actor and the remaining target's own
gains. This is an emergent, not separately implemented, consequence of D-1's filtering happening before
`_handle_pleasure_effect` runs — noted here so a future reader does not mistake it for an oversight (see
Risks).

## Risks / Trade-offs

- **[Risk]** `test_seed_acts.py` casts all three currently-shipped `resistible=True` acts
  (`combat_tease`, `partner_caress`, `partner_hand_hold`), and this proposal makes each cast's effective
  outcome depend on a real dice roll for the first time. A first pass over this proposal (caught by
  rubber-duck review, not by the original analysis) incorrectly claimed `combat_tease` was the *only*
  shipped resistible act and that no existing test needed updating. → **Mitigation**: re-audited every
  `resistible=True` act's existing assertions, not just `combat_tease`'s. `test_combat_tease_increments_
  hostile_act_count_on_actor_only` and `test_self_cast_rejection_credits_no_counters_on_either_seed`
  assert only `actor.sexual.hostile_act_count` (an `act.actor_counters` credit, D-5: never resist-gated)
  and `target.sexual.hostile_act_count` (always `0` regardless, since `combat_tease` declares
  `participant_counters=()`) and `result.outcome == "success"` (D-4: resist-gating never rejects the
  action) — genuinely unaffected, no fix needed. But
  `test_partner_seed_increments_duo_act_count_on_both_participants` asserts `partner_caress`'s *target's*
  `duo_act_count` (a `participant_counters` credit, which resist-gating withholds on a resisted target)
  with no roll mock — this one genuinely becomes flaky and is fixed by tasks §4.1 per D-3a. Tasks §5
  re-runs the whole suite as a regression gate rather than trusting this analysis alone.
- **[Risk]** A future catalog act could ship `resistible=True` with `TargetSpec.SELF`, which D-2's guard
  silently neutralizes (the actor never resists their own act) rather than rejecting at registry-load
  time. → **Mitigation**: disclosed as a known soft spot rather than silently handled; a future proposal
  that owns `_builder.py` (`B4`'s territory) can add the structural invariant if this combination is ever
  actually shipped. No current or proposed act needs it.
- **[Risk]** `_step4b_sexual_resist_gate` adds one `SEXUAL_ACT_REGISTRY.get(skill.key)` dict lookup to
  every single skill cast in the game, not only sexual acts. → **Mitigation**: a dict `.get()` is O(1) and
  negligible next to the rest of the pipeline's per-cast work (multiple `evaluate_combat_modifiers` calls,
  DB attribute reads); no measurable performance concern, and the alternative (checking `skill.category is
  SkillCategory.SEXUAL_ACT` first to short-circuit the lookup) adds a second attribute read for no
  measurable benefit.
- **[Risk]** The crowd-multiplier interaction (D-7) means a partially-resisted `AREA` cast yields a
  *smaller* pleasure gain for the actor and every complying target than an unresisted cast against the
  same target count would have. A player could perceive this as the game "punishing" them for a target's
  refusal. → **Mitigation**: this is the direct, correct consequence of `participants()`'s existing,
  unmodified crowd-multiplier formula being fed a smaller true participant set — not a new formula this
  proposal invents — and is consistent with the multiplier's own intent (a "crowd" of people who actually
  participated). Not treated as a defect.

## Migration Plan

Additive only: two new private functions (`_step4b_sexual_resist_gate`, `_resist_pending_effect`), one
new `_entries_from_effect` branch, one new `_ENTRY_TEMPLATES` key, and two new top-level imports, all
confined to `world/rules/action.py`, plus one determinism fix to an existing test assertion in
`world/skills/sexual_acts/tests/test_seed_acts.py` (D-3a). No schema, rulebook, or registry change. Zero
released users; no backward-compatibility concern applies. Rollback is a plain revert of the two changed
files — no data migration in either direction, since `resistible` was already a validated, already-stored
field this change is the first to read.

## Open Questions

None for this proposal's own scope.
