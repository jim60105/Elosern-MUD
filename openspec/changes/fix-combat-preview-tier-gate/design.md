## Context

`world/rules/action_preview.py::_skill_wide_failure` (`:74-119`) is the single choke point behind `preview_skill` (`:190-222`) and `revalidate_submission` (`:225-293`). It mirrors `ActionResolver` step-1 ordering — ownership/kind/out-of-combat, then divine-arts gate, then resources and the remaining capability checks — but omits the elemental spell-tier gate that `ActionResolver._step1_ownership` applies (`world/rules/action.py:229-240`). Every presentation and submission surface consumes the two preview functions: `combat_view._build_skills` (`world/rules/combat_view.py:313`), the Telnet `combat actions` command (`commands/combat.py:100-116`, rendering `可用` at `:115`), the WebClient combat panel (`web/webclient/presentation/combat_panel.py:390-425`, emitting `enabled` at `:398`), the WebClient cast adapter (`web/webclient/actions/combat_actions.py:203`), and the combat-session facade `submit_player_action` (`world/rules/combat_session.py:857-866`). The facade rejects only when the advisory preview says disabled; otherwise it calls `ActionResolver.preflight()` (`:874-880`), which applies the tier gate and rejects with `UNKNOWN_SKILL` (`action.py:229-240`) — hence the misleading "spell available, then rejected as unknown" flow.

The reachable payload is a valid import: `firestorm` is 術師-tier (30 MP, AREA), `MAGIC_TIER_THRESHOLDS["術師"] == 16` (`world/rules/progression.py:70-72`), so `magic_level=15` with no affinities yields `floor(15 × 1.0) == 15` and fails; declaring the fire affinity yields `floor(15 × 1.1) == 16` and passes (`progression.py:115-146`). The existing preview tests never detected the gap because their fixture sets `magic_level.base = 30` and previews `fire_ball` (`world/rules/tests/test_action_preview.py:25-31,49`), a 學徒-tier spell (14 MP) whose threshold is 0 — it passes the gate at any level.

The parallel change `fix-npc-policy-cast-gate` introduces the shared predicate `world.rules.progression.can_cast_skill(entity, skill) -> bool` (its design D1, tasks 1.1): pure, side-effect-free, returning `True` when `spell_tier_for(skill)` is `None`, else `can_cast_spell_tier(entity, skill.element.key, tier)`, converting any `ValueError` to `False`. It also rewires the resolver's inline block to consume that predicate (its design D2), so after both changes land the resolver, both AI policies, the preview, and submission revalidation all share one gate implementation.

## Goals / Non-Goals

**Goals:**
- Preview and submission revalidation reject an owned, affordable, over-tier elemental spell with the same `UNKNOWN_SKILL`/skill-key shape as authoritative preflight, so Telnet and WebClient never advertise a spell the resolver rejects and no submission reaches preflight only to be turned away.
- One gate call at the preview choke point; zero per-surface edits in the command, view, panel, adapter, or facade.
- Preview stays frozen and side-effect-free, and the predicate is consumed, never redefined (the shared predicate and its single-consumer contract belong to `fix-npc-policy-cast-gate`).
- Parity tests cover below-threshold, affinity-boundary, mastery-override, direct-ownership-override (conferred mastery does not count), malformed fail-closed, revalidation parity, and the shared combat view's disabled descriptor.

**Non-Goals:**
- Redefining or extending `can_cast_skill`; changing the predicate's semantics or signature (owned by `fix-npc-policy-cast-gate`).
- Changing `ActionResolver`, `run_round`, AI policies, import validation, `RejectReason`, commands, or the WebClient wire schema.
- Adding per-surface logic to `commands/combat.py`, `combat_view.py`, `combat_panel.py`, `combat_actions.py`, or `combat_session.py` — they inherit the fix from the preview choke point.
- Rejecting over-tier skills at import time (a supported character may legitimately own a spell a future mastery unlocks).

## Decisions

**D1 — One predicate call in `_skill_wide_failure`, mirroring resolver step-1 ordering.** Insert `if not can_cast_skill(actor, skill): return RejectReason.UNKNOWN_SKILL, skill_key` between the out-of-combat check (`action_preview.py:91`) and the divine-arts gate (`:92-95`), the exact position the tier gate occupies in `_step1_ownership` (`action.py:224-241`). The skill definition is already resolved at that point (`:85`), and both `preview_skill` and `revalidate_submission` route through this one helper, so the fix is a single production edit plus a docstring update. *Alternative considered:* adding the check inside each of `preview_skill`/`revalidate_submission` separately — rejected, that reintroduces the duplicate-gate drift the sibling change's D1 explicitly eliminates.

**D2 — Rejection shape parity: `(RejectReason.UNKNOWN_SKILL, skill_key)`.** The preview already emits this exact shape for unowned skills (`action_preview.py:87`), and after `fix-npc-policy-cast-gate` D2 the resolver rejects unmet and malformed gates with `UNKNOWN_SKILL, request.skill_key` (no `ValueError` detail). `player_messages.rejection_message` never interpolates `detail` (`player_messages.py:67-74`), so the player-facing message is unchanged; `combat_view` maps the reason to `reason_code="unknown_skill"` (`combat_view.py:327`), which the WebClient renders as a disabled skill.

**D3 — Fail-closed without new exception handling.** `can_cast_skill` converts `ValueError` to `False`, so `_skill_wide_failure` needs no `try/except`; a malformed elemental spell (bad MP cost band, unknown element) reports disabled exactly like the resolver rejects it. Preview remains side-effect-free by construction: the predicate is a pure read of `owned_keys()` and traits, never writes, rolls nothing, and materializes no lazy handler — the existing `test_preview_has_no_side_effects` (`test_action_preview.py:69-85`) stays green as the regression guard.

**D4 — All surfaces inherit through the two choke points; no surface edits.** `build_combat_view` (Telnet + WebClient), the adapter revalidation, and the facade revalidation all consume `preview_skill`/`revalidate_submission`, so the gate flows everywhere with zero changes in `commands/`, `world/rules/combat_view.py`, `world/rules/combat_session.py`, or `web/`. No command key, alias, syntax, or wire-schema change, so `docs/game/commands.md`, `docs/game/command-reference.md`, and `tests/test_command_docs.py` are untouched.

**D5 — Parity tests with a tier-gated fixture.** Extend `test_action_preview.py` with an under-tier helper (`magic_level.base = 15`) and `firestorm` ownership so the scenarios exercise the gate: below-threshold disabled (preview == revalidation == preflight rejection), pass-side boundaries enabled (fire affinity at 15 and pure numeric 16, both `floor == 16`), `fire_mastery` in `owned_keys()` enabled, conferred-only mastery (`db.skill_grants = [ConferredSkillGrant(...)]`, mirroring `test_progression.py:442-453`) still disabled, and malformed fail-closed via a `patch` on the predicate's `spell_tier_for` call site. The existing `test_preview_parity_with_preflight` deliberately keeps `fire_ball` — its purpose is resource-detail parity, not the tier gate, and the new tri-surface test carries the tier-gate parity. Add one `test_combat_view.py` case asserting the descriptor carries `enabled == False` and the `unknown_skill` reason code (this covers both the Telnet `可用` line and the WebClient `enabled` field, which share `SkillDescriptorView`), with the fixture explicitly lowered to `magic_level == 15` and `mp >= 30` so the assertion is about the tier gate rather than the human baseline (magic 30) passing it. New tests carry `covers_requirement` only where the main-index identifier already exists; for the modified `action-resolution-pipeline` requirement the existing identifier `actionresolution-exposes-shared-side-effect-free-action-preview` is unchanged by the edit, so annotations stay valid immediately.

## Risks / Trade-offs

- [Risk] The gate check changes the preview's rejection ordering when several failures coincide; a test asserting a specific reason for an entity that is simultaneously over-tier and resource-starved would see a different first reason. → Mitigation: the ordering mirrors `_step1_ownership` exactly, and existing preview tests use gate-passing skills (`fire_ball`, `wind_blade`, non-elemental skills), so no existing assertion changes outcome; tasks re-run the full `test_action_preview.py` and `test_combat_view.py` suites.
- [Risk] This change is unbuildable until `fix-npc-policy-cast-gate` lands (the predicate does not exist yet). → Mitigation: proposal.md and design.md state the dependency and pin the exact API (`can_cast_skill(entity, skill) -> bool`, fail-closed); tasks.md task 1 names the sibling change explicitly; implementation order is enforced by the sibling's design D1/D2 and this change's task 1.
- [Risk] A future surface could bypass the preview choke points and reintroduce the drift. → Mitigation: the delta requirement binds preview and submission revalidation to the shared predicate; the sibling change's `element-mastery` requirement already binds the resolver and AI policies to it, so all gate consumers are contractually tied to one helper.
- [Trade-off] An over-tier spell that previously looked castable now shows as disabled with "unknown skill" feedback. That message is unchanged and misleading in isolation, but it is now consistent with authoritative preflight, and the player-facing message is the same one used for an unowned skill — no new message surface is introduced.

## Migration Plan

No data migration: the gate is a pure cast-time query, never a stored fact. No schema change, no command-surface change, and no player-facing documentation change. The change lands after `fix-npc-policy-cast-gate`, which owns the shared predicate this change consumes.
