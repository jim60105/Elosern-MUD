# Design: Exactly-once complete-draft ordinary rounds and rollback

## Context

See `proposal.md` for motivation and the batch contract in `../combat-ratio-mitigation/batch.md` for complete coverage, order and conflicts. The enclosing transaction in combat_session/rounds.py already spans resources/effects, session metadata and terminal settlement, with item journals and Evennia cache snapshots.

Inspected boundaries are listed in the proposal Impact section. These are observed starting points; all new behavior below is proposed, with no runtime result claimed. The approved 2026-10-15 document explicitly amends the base engine §6.3 where subtraction, allied autonomy and individual allied flee conflict.

## Goals / Non-Goals

This change owns exactly-once complete-draft ordinary rounds and rollback. It reuses existing deterministic state owners and exact protocol conventions. Required behavior is defined by its complete delta files. There is no new LLM dependency, compatibility path, data migration, shared inventory, companion equipment-management UI or physical proficiency progression. Detailed stage geometry remains owned by the existing UI batch.

## Decisions

Use the existing single deterministic writer with an authoritative session/revision compare-and-consume inside `transaction.atomic`; serialize competing confirmations before re-reading durable state. Do not rely on a process-local used flag, preflight snapshot or browser in-flight lock for concurrency safety on SQLite. The final edit is persisted before entering round resolution so a failed round keeps the accepted complete draft recoverable. Re-read and preflight all commands within the serialized round transaction; invalid entries return reselection without AI/upkeep. Store a durable consumed-revision receipt tied to session and revision, including terminal completion, outside the soon-cleared active session as needed in the commander-owned session outcome record. Duplicate/stale requests return a safe prior-committed/stale result without executing effects. Supply each allied selected request once; enemy provider remains unchanged. Compute initiative once. Preserve capability gates and authored in-round order operations; command entry order has no priority. Normal final target invalidation consumes the opportunity with no retarget, costs or item consumption; valid miss retains ordinary costs. All effects, resources, mirrors, quest/practice/affinity changes, metadata, revision/draft consumption, clock and terminal aftermath belong to the outer transaction and existing cache journals. Extend restoration to drafts, tactical state and any new receipt. Keep ordinary six-second accounting once and post-commit notifications/events only.

## Risks / Trade-offs

- [Shared boundary changes] -> Implement only after declared prerequisites, integrate earlier deltas and callsites, and use the batch matrix to serialize overlapping files. No obsolete alias or duplicate implementation remains after cutover.
- [State or capability changes after selection] -> The shared rules boundary repeats authoritative validation; invalid drafts and normal mid-round invalidation follow different documented semantics.
- [Unproven arithmetic, persistence or UI behavior] -> Tasks include focused independent assertions and actual evidence where owned here. A selected constant alone is not measured balance and a fixture-only UI is not runtime acceptance.
- [Estimate depends on existing patterns] -> Scope is bounded to the listed owner and 7.5 hours includes its focused tests/docs/integration. Required downstream behavior is owned explicitly in the batch rather than silently deferred.

## Migration Plan

Pre-release clean cutover only. Implement code, callsites, fixtures, exact schemas and affected canonical requirement annotations together for this slice. No old/new compatibility parser, stored-data migration or deprecated entry path is added. Rollback uses an ordinary revert of the implementation change; proposal authoring performs no rollback, merge, apply or archive. The assembled client/server cutover is accepted only after change 18.

## Verification and documentation ownership

Use synthetic fixtures for independent behavior expectations and the existing real-data calibration boundary for authored roster evidence. Register added/moved Evennia tests and browser methods exactly once in the appropriate shard manifest; annotate tests with canonical `<capability>.<requirement-slug>` IDs generated by the project traceability tooling. If the canonical slug changes, migrate every affected annotation. Update existing affected documentation, both player command documents for syntax/context changes, and focused schema/fixture mirrors for transport changes. Run the focused tests and `uv run --locked python -m tools.contract_gate` during implementation; logging changes also require observability lint and focused event tests. Complete managed browser and traceability-evidence execution stay CI-owned.
