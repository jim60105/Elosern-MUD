# Design: limbo-one-way-city-gates

## Context

Authoritative design: `docs/superpowers/specs/2026-09-04-onboarding-removal-one-way-limbo-design.md` §4 and §7/§8 (approved). Evennia fact established by the design doc: `Exit` is an independent persisted object — `create_object(Exit, ...)` creates exactly the one direction you ask for; there is no automatic reverse pairing (`@dig`'s convenience is a builder command, not the API). The current bridge in `world/maps/bootstrap.py` nonetheless creates both directions: `_ensure_exit(limbo, south_gate, **EXIT_TO_CITY)` **and** `_ensure_exit(south_gate, limbo, **EXIT_TO_LIMBO)` (constants 「南門」/「王都」「城門」 at :125 and 「離開王都」/「回虛境」 at :129). The one-way 虛境 semantics require the reverse half to disappear from both code and databases, and the planned race-based starting cities require the bridge to scale to N cities without per-city code.

This change is the gate slice only — but after verification against master it owns **both** one-way layers: the forward-only/pruned exit surface AND the 虛境-entry hard gate. Corrected assumption (amended design doc §4): the original §4 claimed `typeclasses/rooms.py` already carries an `at_pre_object_receive` "Characters never move into Limbo" gate; verified false — the repo's `Room` is a bare `pass` class and that behavior exists only in upstream Evennia documentation examples, not in this repository or its installed 6.1.0 defaults. The gate is a gap this change implements. The sibling change `remove-onboarding-tutorial` owns the onboarding deletion, birth-in-虛境, and relocate removal; the files stay disjoint (the sibling never edits `rooms.py`) and either may land first.

## Goals / Non-Goals

**Goals:**
- Make the 虛境→city bridge forward-only: sync creates/keeps exactly one exit per registry row pointing 虛境→gate, and deletes every exit pointing into 虛境 on every run.
- Introduce `world/maps/city_gates.py` as the sole authored source of city gates, shaped for N cities (one row per city) while carrying exactly one row (`capital_altoria`) today.
- Preserve the existing idempotent converge semantics (pre-existing exits reconcile key/aliases in place; repeated sync is a no-op; missing rooms degrade to `log_warn` + skip, never raise).
- Implement the two-layer one-way guarantee and test both layers: forward-only creation/pruning (layer 1) plus a NEW 虛境-entry hard gate admitting no character into 虛境 by any move path (layer 2), converging the 虛境 room onto it in `sync_limbo()`.
- Observability per facade convention: snake_case event ids, `context` dicts, named imports from `world.observability`.

**Non-Goals:**
- Race→city routing at character birth (other cities do not exist; YAGNI per design doc §2).
- Any change to `typeclasses/rooms.py` beyond adding the new `LimboRoom` hard-gate typeclass. Out of scope entirely: the onboarding subsystem (sibling `remove-onboarding-tutorial`), `STARTER_EPITHET` (the title-system change), and the 南門→wilderness gate plus 虛境 slate/stele teaching content (explicitly not done, design doc §10).
- Migration scripts or cleanup shims for old databases — pruning happens as the synchronizer's own declarative convergence.

## Decisions

**D1 — Registry module `world/maps/city_gates.py`.** Exactly the shape of design doc §4: a `@dataclass(frozen=True, slots=True) class CityGateDef` with `map_id: str`, `gate_xyz: tuple[int, int, str]`, `exit_key: str`, `exit_aliases: tuple[str, ...]`, plus `CITY_GATE_REGISTRY: MappingProxyType` built once with one row `capital_altoria` (gate xyz `(2, 0, "capital_altoria")`, key 「南門」, aliases `("王都", "城門")`). Frozen dataclass + `MappingProxyType` is the repo's immutable-registry convention (mirrors `WILDERNESS_ENTRY_REGISTRY`). Adding a city = adding a registry row; `sync_grid()` already loops rows, so no code change. Rejected alternatives (both cited from the design doc §2): **(a)** embedding the bridge declarations in the xyzgrid city map data — 虛境 is not an xyzgrid room, and a cross-system bridge exception would force the xyzgrid synchronizer to understand a concept it should not own, widening the change surface; **(b)** reusing the `WildernessGateExit` provider protocol — that protocol exists for dynamic wilderness cell generation, while a city entry needs a static one-way ordinary `Exit`; reuse would be over-engineering.

**D2 — `sync_grid()` rewrite is per-row, reusing the existing helpers.** After `grid.spawn()`: locate the 虛境 room by `LIMBO_KEY` (existing warn-and-return `bootstrap_grid_limbo_room_missing` path unchanged); then for each `(map_id, CityGateDef)` in `CITY_GATE_REGISTRY`, resolve `grid.get_room(row.gate_xyz).first()`; a missing gate room logs `log_warn("bootstrap_grid_gate_missing", context={"map_id": …, "xyz": …, "action": "skip_gate_row"})` and skips **that row** while other rows proceed; otherwise `_ensure_exit(limbo, gate, key=row.exit_key, aliases=row.exit_aliases)` — the same idempotent converge semantics as today (create if absent, rewrite key/aliases in place if drifted). `EXIT_TO_CITY` and `EXIT_TO_LIMBO` constants are deleted (the registry row replaces the former; the latter is gone); the reverse `_ensure_exit` call is deleted. The `SOUTH_GATE_XYZ` constant stays — other consumers (wilderness provisioning, tests) reference it.

**D3 — Declarative pruning, not a migration shim.** After the ensure pass, `sync_grid()` iterates the 虛境 room's contents-side graph for exits whose `destination` is the 虛境 room and deletes each, logging `log_info("bootstrap_grid_exit_pruned", context={"exit_key": …, "exit_dbref": …, "source_room_key": …, "action": "enforce_one_way_gates"})` per deletion. The design doc §4 classifies legacy 「離開王都」/「回虛境」 exits as dirty data and explicitly labels this prune — unlike all other legacy residue in the removal, which dev-databases handle by reset — as "the synchronizer's declarative convergence over its own exit surface, symmetric to `_ensure_exit`, not a backward-compat shim". Spec-wise the requirement is permanent ("every sync deletes every exit whose destination is 虛境"), so any future hand-built or bug-restored reverse exit converges away on the next start; the behavior is a standing invariant, not a one-time cleanup. Implementation note: search persisted exits by destination (e.g. `Exit.objects.filter(db_destination=limbo)` — the exit objects live at the city-side rooms, so scanning only `limbo.exits` would miss them), deleting each with the event.

**D4 — Two-layer one-way guarantee; layer 2 is newly implemented here.** Layer 1: forward-only creation + D3 pruning, so the authored exit graph has no 虛境-destination edge. Layer 2 (NEW): a hard gate making one-way-ness independent of the exit graph — even a hand-built reverse exit or a forced `move_to` cannot deliver a character back. **Corrected assumption:** the design doc originally stated this gate "already exists" in `typeclasses/rooms.py`; verification on master proved the premise false (`Room` is a bare `pass` class; "Characters never move into Limbo" traces to upstream Evennia documentation examples, not to this repo and not to installed 6.1.0 `DefaultRoom`). The amended design doc §4 marks it a gap to implement, and this change implements it.

Implementation, grounded in the installed Evennia 6.1.0 source (`evennia/objects/objects.py`): `DefaultObject.move_to` calls `destination.at_pre_object_receive(self, source_location, move_type=…, **kwargs)` as abort hook #3 of the universal move pipeline (documented sequence at `objects.py:1221-1231`, invoked at `:1279`) — it fires for ordinary exit traversal, `moveto`/teleport-style `move_to`, and every other `move_to` path; returning `False` aborts the move and the character remains where it was. That is the deterministic seam the amended §4 asks to pick between ("在 `at_pre_object_receive` 與 lock 兩者中選確定性較高者"). **Decision: option (a) — a dedicated `LimboRoom(ObjectParent, DefaultRoom)` typeclass in `typeclasses/rooms.py`** overriding `at_pre_object_receive`: reject when the arriving object is a character and its account is not a superuser — emit a zh-tw localized refusal to the arriving character via `msg` before returning `False`; every other arrival defers to `super()`. **Rejected alternative (b) — destination-side `get`-lock permission:** in 6.1.0 the `move_to` pipeline performs no room `get` lock check itself (lock enforcement lives in the calling commands — exit traversal checks access on the *exit*, not the destination room), so a lock-only gate leaves `move_to`/teleport paths unguarded and makes the invariant depend on every caller remembering to check; the hook is path-complete and strictly stronger. Superuser bypass follows the repo's own builder convention (`typeclasses/exits.py:163-166` treats `is_superuser` as the admin escape hatch); without it admins could not `@tel` into 虛境 for debugging — NPCs/items are not the guarded class (characters only, per spec). **Convergence:** `sync_limbo()` rewrites the located room's typeclass in place (`room.swap_typeclass("typeclasses.rooms.LimboRoom", clean_attributes=False, no_default=True)`, guarded so an already-converged room is a no-op), the same declarative-convergence philosophy as D3 pruning — zero migration; fresh boots (Evennia creates the starting room as plain `Room`) and existing dev databases both end converged.

**D5 — Observability events follow the facade convention.** Two ids: `bootstrap_grid_gate_missing` (warn; per-row degrade, context `map_id`/`xyz`/`action`) and `bootstrap_grid_exit_pruned` (info; context names the deleted exit and the enforcing action). Named imports `from world.observability import log_info, log_warn`; stable snake_case English ids; `tools/observability_freeze.json` is shrink-only and today carries no bootstrap bridge ids, so this change is freeze-neutral-to-growing-only-in-the-sanctioned-direction — `tools.observability_lint check` violations must not grow. The old single-site `bootstrap_grid_south_gate_missing` warn is subsumed by the per-row event.

**D6 — Tests anchor on the new requirement ids.** Extend `world/maps/tests/test_bootstrap.py` (or a focused sibling module under `world/maps/tests/`, which stays inside the `world.maps` shard prefix of `.github/evennia-shards.json` — any new module is registered in exactly that one shard): forward exit idempotently converges key/aliases across repeated sync; a reverse exit seeded before sync (or surviving a sync) is deleted by the next `sync_grid()` with the prune event; 虛境's exit set equals the registry rows after sync; a registry row whose gate room is missing warns and is skipped while other convergence proceeds. Layer-2 coverage in `test_limbo_room.py`: after `sync_limbo()` the room is `LimboRoom`; a non-superuser character is refused by BOTH ordinary exit traversal into 虛境 and a forced `move_to` (location unchanged, zh-tw refusal received — the real seam, no aspirational claims); a superuser arrival succeeds; a second `sync_limbo()` performs no re-swap and preserves key/alias/description. `@covers_requirement` anchors use ids resolved at apply time via `uv run --locked python -m tools.spec_traceability list`; the existing 「離開王都」-asserting tests in `test_limbo_room.py`/`test_bootstrap.py` are rewritten to the forward-only surface, never deleted while their (renamed) requirements survive.

**D7 — First-gate-traversal home re-anchor (home policy).** Verified facts: `server/conf/settings.py` defines no `DEFAULT_HOME` override, so Evennia's stock behavior applies — a character's `home` is its creation location, which after the sibling's birth-in-虛境 is the 虛境 room; and `CmdHome` is a live contract (`commands/tests/test_localized.py:130-134` pins 「還是家最溫暖」 + relocation). Left alone, the one-way threshold plus the layer-2 hard gate would make `home` a one-way ticket into a room that refuses its own owner — a broken UX the design doc's one-way semantics imply but never resolve. **Decision (user-approved direction): the first traversal of a registry city gate by a character whose `home` is the 虛境 room re-anchors `character.home` to the arrival gate room.** Guards: the write fires only when (a) the traversal succeeded, (b) the destination room is a `CITY_GATE_REGISTRY` gate room (its grid coordinate matches a row's `gate_xyz`), and (c) the character's current `home` IS the 虛境 room — so later traversals re-entering a gate room, and future multi-city gates for an already-anchored character, never overwrite a non-Limbo home. **Seam: `after_successful_movement` in `typeclasses/exits.py`** — the shared movement-completion boundary every exit lineage already converges on for charge/record/follow, so the re-anchor covers ordinary traversal and any future exit typeclass with one hook site, sits strictly after success (a failed/compensated traversal never re-homes), and lands in the same commit as the sibling's deletion of the `observe_room_entry` call (additive, non-overlapping hunks). **Writer placement: NEW `world/rules/city_gates.py::reanchor_home_on_gate_arrival(character, destination)`**, called from the boundary with the same deferred-import discipline the other rule calls use. Rationale vs the alternatives: `world/rules/movement_settlement.py` is the settlement-atomicity capability's compensation surface (snapshot/restore of exactly its named fields — a home write there would invite "compensate the home too" coupling the policy forbids: the re-anchor is unconditional once movement succeeded); `world/rules/dialogue.py`/`guild.py` are unrelated owners; a rules-side module mirroring the maps-side registry name keeps gate semantics in one pair of files and satisfies the repo's single-writer rule (persisted-attribute writes live in `world/rules/*`, typeclasses stay thin callers). `world/maps/city_gates.py` stays a pure frozen-data module — the rules helper reads it for the coordinate match. No command surface changes: `CmdHome` is stock behavior with a corrected `home` value, so `docs/game/commands.md` / `docs/game/command-reference.md` need no edit.

## Risks / Trade-offs

- [Prune deletes a legitimate non-authored object an admin placed pointing at 虛境] → Accepted: the invariant is authored-declarative — nothing may lead into 虛境, and layer 2 (D4) would refuse the entry anyway; the `bootstrap_grid_exit_pruned` info event names every deletion so the action is never silent.
- [Registry grows and a row's `gate_xyz` drifts from the city map data] → Per-row `log_warn` + skip (D2) degrades loudly without blocking other rows; the row-scenario test pins the behavior, and the xyzgrid spawn of the city itself is independent of gate rows.
- [Landing order vs `remove-onboarding-tutorial`] → Either order works, with one nuance corrected from the first draft: since D7 this change DOES touch `typeclasses/exits.py`, which the sibling also edits (deleting the `observe_room_entry` call inside the same helper). The hunks are additive and non-overlapping — if both changes are in flight, the integration owner lands them in one pass. Before the sibling lands, the relocate step still moves fresh characters to the South Gate (their `home` stays the creation-location 虛境 room), the guard tutorial never used the return exit, and the D7 re-anchor fires for those relocated characters on their first gate traversal as well — so pruning changes nothing observable for the guard flow; after the sibling lands, the fresh character born in 虛境 leaves via the forward 「南門」 gate. The full-flow integration test (birth → traversal → `home`) is easiest post-c1 and is sequenced as task 4.11. File-ownership declaration lives in proposal Impact: `bootstrap.py` + `world/maps/tests/` exclusive to this change; `at_server_startstop.py` and `.github/evennia-shards.json` exclusive to the sibling.
- [Deleting `EXIT_TO_CITY` breaks an external importer] → Verified grep surface (excluding worktrees): beyond `bootstrap.py` itself, the ONLY surviving importer is `world/rules/tests/test_map_knowledge_integration.py:80-87` (`test_limbo_bridge_records_grid_node`, which builds the bridge from `EXIT_TO_CITY["key"]`/`["aliases"]`). Task 4.12 rebuilds that bridge fixture from the `CITY_GATE_REGISTRY` row (or the synchronized real exit), preserving the `map-knowledge::arrival-recording-happens-only-at-existing-successful-arrival-seams` coverage anchor. The registry row is the sole replacement, matching the clean-cutover rule (no aliases kept).
- [Home re-anchor races with a concurrent teleport or double-triggers via companion movement] → The write is a single guarded attribute set inside the already-serialized traversal path (`after_successful_movement` runs per traversing object), and guard (c) — `home` must still BE the 虛境 room — makes every trigger after the first a no-op; the dedicated tests pin first-traversal-writes / second-traversal-inert.
- [Prune query performance on every boot] → Single indexed `db_destination` filter against the 虛境 room once per sync; on converged databases it returns zero rows.
- [`swap_typeclass` on the starting room disturbs attributes or running state] → Called with `clean_attributes=False` and `no_default=True`, and only when the room's current typeclass is not already `LimboRoom`; the sync's own idempotency test asserts a second run rewrites nothing and the room keeps its key/alias/description.
- [Hard-gate hook accidentally blocks legitimate non-character flow (e.g. an admin `@tel`ing an item to 虛境)] → The hook guards characters only and defers everything else to `super()`; the superuser bypass keeps builder/debug access; the refuse-path test pins exactly which arrivals abort.
