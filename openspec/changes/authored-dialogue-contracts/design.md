# Design

## Context

Observed shape.py has only KeywordResponse(keyword,response) and DialogueDefinition(greeting,responses), both frozen. Lore registry must never import rules. This change supplies a complete pure data API and validators without switching live tables; runtime cutover is the next change.

## Goals / Non-Goals

**Goals:** Immutable reusable scenes and complete typed topic declarations. Deliver this runnable slice and its acceptance within one engineer-day.

**Non-Goals:** Unowned runtime/content work, compatibility migrations, new game effects and per-line server stepping.

## Decisions

## Shared contract v1 (proposed APIs, authoritative for this batch)

These are proposed interfaces, not claims about current implementation. Later designs reference this section and implement only their named fields. Python lore stays registry-only; world/rules owns dialogue/session/effects and world/narrative owns reading records. No executable scripts, per-line server cursor, new quest effects, compatibility adapter or data migration.

### Immutable declarations

Add `world/lore/scenes.py` with frozen `Speech(speaker: Literal["actor","host"], text: str)`, `Narration(text: str)`, `Scene(scene_id: str, revision: str, lines: tuple[Speech | Narration, ...])`. IDs match `[a-z][a-z0-9_.-]{0,95}`; revisions are explicit nonempty ASCII tokens <=32. Lines are 1..2000 code points and scenes 1..32 lines / <=16000 total code points. Dialogue formal scenes and variants begin with an actor Speech containing a complete utterance; narration and consecutive same-speaker lines are legal thereafter. Opening/guild dynamic service scenes need not begin with actor. No interpolation, executable callbacks, embedded HTML, or choices inside a scene. Text is plain data; existing trusted text-output escaping rules still apply to editable greetings.

In `world/lore/dialogue/shape.py`, add frozen `SceneVariant(variant_id, priority: int, when: Condition, scene: Scene)` and `AuthoredTopic(topic_id, keyword, label, fallback: Scene, variants=(), requires=None, unavailable="hidden", refusal=None, predecessors=(), disclosure="qualified")`; `AuthoredDialogue(greeting: str | None, topics: tuple[AuthoredTopic,...])`. Topic identity is `<dialogue_key>.<ASCII suffix>`, <=96 chars, independent of localized keyword/label, tone and revision. Predecessors are stable topic IDs within the same host definition; reject dangling references/cycles. `disclosure` is `qualified` or `pure_chain`. Pure chains have predecessors, no requires, no effects, and contain only public informational scenes; reject a qualified descendant included in a pure-chain bundle. Qualified descendants remain separate server selections. Select the highest matching integer priority; priorities are unique within a topic; otherwise use the unconditional fallback. Variants alter complete linear wording, not effects or reading identity. Refusal required for visible lock, forbidden for hidden disclosure. Formal topic count <=16 with ALL entries reachable by scrolling the choices surface; retire the old first-four truncation on every authored surface.

`Condition` is the tagged frozen union owned by `world/lore/dialogue/conditions.py`: `All(children)`, `Any(children)`, `RaceIs(race_key)`, `SocialIdentityIs(identity_key)`, `GuildRankAtLeast(rank_key)`, `QuestIs(definition_key, state)`, `AffinityAtLeast(stage_key)`, `Carries(item_key, minimum=1)`, `CompanionPresent(source_kind, source_key)`, `TimePeriod(start_daypart, end_daypart)`, `SkillOwned(skill_key, min_proficiency=None)`, `Exposure(minimum=None, maximum=None)`. Groups have 1..16 children and maximum depth 4; at least one Exposure bound, canonical ordered inclusive comparison. Runtime evaluators arrive in physical/progression slices, with no placeholder evaluator. All declaration keys are validated against the canonical registry in the owning condition slice before shipped conditions use them.

### Context and selection

Add `world/rules/dialogue_context.py::resolve_dialogue_context(actor, host, *, session=None) -> DialogueContext(actor, owner, host, context_id, phase_revision)`. Ordinary player owner=actor. Possession resolves owner through `world.rules.party_scope.resolve_commander(actor)` and validates `is_companion(actor, owner)`, authenticated driving session when supplied, mirrored possession, actor/host co-location, capability, host schedule and host!=actor. Do not trust a client owner/actor id. Guild/quests/reading and host.relations affinity use owner; race/social/skills/inventory/exposure use actor. Companion membership uses owner and presence uses actor.location. Session remains on the ACTING body's existing db.dialogue_session seam. Switching control invalidates that body's conversation instead of resuming it on another body; durable reading is owner-shared.

`world/rules/dialogue.py::select_authored_topic(actor, host, topic_id, *, selection_id, expected_context_id, session=None) -> SceneDelivery` is the sole authored formal/refusal selection path used by command and web adapter. Context is resolved and eligibility rechecked before effects. The existing web action remains `explore.talk_scripted`, with exact payload `{npc_id, topic_id, context_id, selection_id}` for authored topics; generated current-phase topics retain their existing keyword payload and quest-authority seam, selected by server source type (a closed validator union, never two competing authored APIs). Text keyword lookup resolves a stable topic then invokes this same selection function. `selection_id` is <=64 chars, web dispatch request identity reused on transport retry, newly allocated per genuine text command. Repeating a selection id within the current context returns the committed delivery, with no second effect. Reject reuse for another topic. A new deliberate selection may grant existing talk affinity under existing caps; replay and completion never do. Unknown keywords, hidden topics and refusal never grant affinity. Guild 回報 listing is still read-only and the quest-id turn-in stays in the guild service, not an authored reward action.

### Delivery, replay and wire

Frozen `SceneDelivery(delivery_id, selection_id, context_id, actor_id, owner_id, host_id, topic_id, scene_id, scene_revision, phase_revision, kind, lines, updated_tick)` with kind `formal|refusal|opening|service`; all ids JSON-safe scalars, delivery/context ids opaque <=64 chars. Owner identity is server-only and omitted from the wire. `topic_id` is nullable only for opening/service. Context id changes on new host/control/open/phase invalidation, not on an availability refresh. Scene revision identifies exact authored bytes; a session stores the delivered scene snapshot, never a current line cursor. A replay republishes that delivery_id and bytes beginning at line one without selecting again. Reject obsolete context, invalid host, changed phase, or changed actor/control; do not expose stale lines. Variant stays fixed after equipment/condition refresh while context remains valid. Revocation of eligibility alone refreshes choices; previously authorized playback stays fixed. Existing movement/combat/host departure/deletion clear seams retire delivery and choices together while historical attributed transcript remains.

`open_or_refresh_dialogue` remains the sole session writer. The complete schema and extended signature in the review-resolved section below supersede abbreviated session descriptions. Existing generated/freeform calls remain native. Selection effects and session publication share one transaction with cached-Attribute compensation. Existing action-envelope generation/epoch/revision admission rejects obsolete selections; replay and acknowledgement invoke no effects. Generated story effect APIs retain their existing authority and rejection contract.

Bump the dialogue panel from schema_version 2 to 3 across Python and UMD/Vue validators in one runtime change. Exact available top-level fields are `{schema_version,available,kind,host,actor,bond_stage,context_id,delivery,choices,pure_chain,reading_revision,completed_topic_ids,unlock_batch}`. `host` and `actor` each use existing `{identity,display_name,portrait_ref}` contract with `portrait_catalog_key`; numeric affinity never ships. `delivery` is null or `{delivery_id,context_id,topic_id,scene_id,scene_revision,phase_revision,kind,lines}`; line wire forms are `{kind:"speech",speaker:"actor"|"host",text}` or `{kind:"narration",text}`. Existing generated/freeform line presentations become a native one-host-line delivery, without changing model generation or settlement. `choices` are <=16 exact `{topic_id,keyword_id,label,availability,requirement_hint,unread,predecessors,action_payload}` rows. Hidden rows absent, locked rows have no formal scene, open qualified rows have no pre-delivered body until selection. `action_payload` is server-authored exact action payload without selection_id (dispatcher adds request identity); native generated rows use their existing keyword source. `pure_chain` holds only public authorized successor scene descriptors, never effects/qualified bodies. Defaults before owning slices are `pure_chain:[]`, `reading_revision:0`, `unlock_batch:null`, choice unread:false and open/no hint. These defaults describe unsupported optional features, not fake runtime implementations. Client schema_version 2 support is removed. All canonical portraits come from the same committed art snapshot; no client dbid-to-catalog mapping.

### Reading and completion

`world/narrative/dialogue_reading.py` owns the exact review-resolved Attribute schema below, using SQLite first-SQL guarded UPDATE, raw Attribute merge and cache compensation. `reading_for(owner,host_id)` is pure. `complete_delivery(actor,*,delivery_id,context_id,topic_id,scene_revision,session=None)` accepts only a retained formal receipt in current authenticated context and returns `{status:"saved"|"already_saved",reading_revision}`. Refusal, foreign, stale and undelivered claims reject without reading/effects. Variants/revisions never reset stable-topic completion. Pure-chain acknowledgements require saved formal predecessors; successful complete attributed text emission invokes this same service.

Completion receipts persist independently of latest playback, including earlier topics. Keep at most two formal receipts per topic (latest and previous), <=32 receipts for <=16 topics; a third reselection retires the oldest unacknowledged same-topic receipt. Replacing the latest scene does not invalidate another topic completion. New context/phase/control clears these receipts. Delivery-bound duplicates remain idempotent across connections and reconnect. Returning to choices locally may reveal only pure-chain successors, with pending acknowledgements queued predecessor-first. Protected qualified successors wait for server-saved reading and eligibility refresh. Post-commit fan-out uses existing watcher/panel-pusher discipline, resolves connections for the OWNER including a currently possessed actor, and refreshes each connection's own live context without copying another body's scene.

### Availability and notifications

`world/rules/dialogue_conditions.py::evaluate_condition(condition, context)` and `condition_hint(condition)` share declarations and canonical labels. Missing/corrupt authoritative state fails closed with a facade integrity event, no handler materialization. Hints disclose public stage names rather than private affinity numerals. `world/rules/dialogue_availability.py::project_topics(context)` is pure; `refresh_dialogue_availability(owner, *, cause)` runs only from committed deterministic seams. Qualified predecessor completion and requires govern open/hidden/locked. Pure-chain predecessors govern UI reveal and persisted progress only, never effect authorization. The server checks explicit topic IDs even if a forger bypasses UI ordering.

Before notification support, no unlock mutations occur during projection. The notification slice adds narrative-owned `observe_availability(owner, host_id, open_topic_ids, *, initial, context_id)` and `claim_unlock_batch(owner, batch_id)`. At FIRST observation of a host, set ever_open for presently open topics, show their unread markers, and set announced true without popup. A topic observed locked/hidden first, then open later, gets ever_open true and one announcement eligibility while unread. A first observation after a prior persisted locked snapshot counts as later unlock. Read formal topics remain complete through relock/reopen; unread existing topics keep their marker, and ever_open/announced prevent repeat notifications. Tone-only changes do neither. A batch is a bounded owner/host set of newly-ever-open unread topic ids per one committed refresh, stable batch_id <=64; persisted pending batch is claimed once under owner lock before fan-out to current authenticated watchers, so reconnect never replays a popup. Delivery is at-most-once, not guaranteed across disconnect/fan-out failure; markers remain durable. Wire `unlock_batch` is ephemeral only on that live post-commit update, never snapshots/reconnect. Client deduplicates by batch_id in memory, defers until scene returns to choices, never steals focus, drops batches for retired contexts/characters and leaves durable markers intact.

Frontend pending completion exists only in memory scoped by owner character/control context, no localStorage/IndexedDB/service-worker queue. Retry on same-context transport restoration and explicit retry, serialize pure-chain predecessor acknowledgements, and do not claim saved state before a saved/already_saved response. On refresh/tab close/character exit/context invalidation discard pending state. Reconnect without pending memory replays latest delivered scene at line one; saved server reading wins. Persist no line/page cursor.

### Exact context, session and request composition

This section resolves the whole-batch review and is authoritative over abbreviated descriptions above.

`resolve_dialogue_context` is a pure validator/reader whose context_id is nullable before a session exists. It never allocates IDs. `select_authored_topic` accepts expected_context_id: str | None. Non-null must match the existing body/host/control/phase context. Null is admitted only for a direct text/suggestion entry with no live conversation; selection validates all gates and establishes context plus delivery/effects atomically. A null descriptor replayed after a context exists is stale. Text with a matching live host supplies its current context internally; direct text to a new host explicitly retires the old context and establishes the new one in the same transaction. A normal open starts a fresh context, even for the same host. Reconnect retains the existing opening-line context and delivery identity. A no-live-context suggestion descriptor carries null and uses this atomic direct-entry path; it does not require an undocumented preliminary talk_open.

Exact session fields are `{schema_version:1,kind,npc_id,context_id,actor_id,owner_id,control_key,phase_revision,line,line_delivery_id,delivery,selection_receipts,completion_receipts,updated_tick}`. For kind line, line is bounded raw native text, line_delivery_id is a stored opaque ID and delivery is null. For kind scene, line and line_delivery_id are null and delivery is the complete server SceneDelivery. owner_id and control_key never ship. control_key is a server-only bounded encoding of owner dbid, actor dbid, account authority and possession since_tick, checked against lawful current control. phase_revision is the current generated revision or null for static authored hosts.

`selection_receipts` is a <=16 list of exact `{topic_id,selection_id,delivery}` rows, latest per topic, where delivery is the immutable committed SceneDelivery. Existing envelope revision/epoch admission rejects an older request after an intervening selection even if its receipt was replaced. `completion_receipts` is a <=32 list of exact `{delivery_id,context_id,topic_id,scene_revision,phase_revision,kind,predecessors}` rows, at most latest and previous formal receipt per topic. Owner/body/host/control are inherited from the parent session. Refusal/opening/service never enter that list. Public successors use kind formal without a selection receipt or effect. A third same-topic delivery retires only its oldest receipt; delayed A-after-B completion remains valid. Both lists survive reconnect and clear with context retirement.

The exact sole-writer signature is `open_or_refresh_dialogue(character,npc,line: str | None = None,*,delivery=None,context=None,selection_receipt=None,completion_receipts=())`. Omitted context on native line calls means validate/reuse a current same-host context or establish a new one inside this deterministic writer. This writer owns context creation, latest playback replacement and receipt merges. Narrative completion changes only reading state; any session receipt retirement goes through this writer.

Projected authored action descriptors contain exactly `{npc_id,topic_id,context_id}`, with null context only for no-live-context direct entry. They never contain selection_id. `web/webclient-app/stores/elosern/transport.js::dispatchAction` passes this descriptor to the existing envelope builder. `web/webclient/actions/dispatcher.py::handle_ui_action`, after request-id duplicate/stale admission and before action-specific validation, copies the descriptor and injects `selection_id=action.request_id`. Reject a client-supplied selection_id. Projection uses a dedicated pure descriptor validator; the composed four-field payload uses the registered full action validator. Native generated keyword and freeform branches remain separate. This authored composition is an explicit exception to the old byte-identical projected-payload rule. Two deliberate activations have different request IDs; a retry preserves its original ID.

### Exact populated wire and reading storage

The available v3 field set above contains `completed_topic_ids`, a <=16 unique list of saved formal IDs for this owner and host. It is [] before reading-server lands. `pure_chain` is a <=15 list of exact `{delivery,predecessors}` objects. Each delivery uses the exact wire delivery fields above, kind formal and a non-null topic_id, with a retained server completion receipt before its body ships. predecessors is 1..16 unique same-host IDs. Entries are topologically ordered public successors only, with no qualified descendants or effects. The selected primary delivery remains the server replay target; pre-delivered successors do not create a persisted client cursor.

`unlock_batch` is null or exactly `{batch_id,host_id,context_id,topic_ids}`. Batch/context IDs are opaque <=64 ASCII, host_id is a positive safe integer and topic_ids contains 1..16 unique same-host IDs in declaration order. The owner/host batch ID is stable, but each live watcher receives its own current context_id. Owner O with valid contexts C1 and C2 at host 41 receives batch U wrapped as C1 and C2 respectively. Both connections deduplicate/defer U locally; another character of the same account receives nothing. Snapshots and reconnect never contain U.

Exact narrative Attribute storage is `{schema_version:1,revision:int,hosts:{"41":{initialized:bool,topics:{"host.topic_01":{completed:bool,ever_open:bool,announced:bool}},pending_batch:null|{batch_id,topic_ids,created_revision}}}}`. Reading-server introduces this complete shape with initialized false and pending_batch null; unread-notices owns observation. First observation records all declared topics, including hidden/locked ever_open false, sets initialized and marks currently open topics announced without a popup. A later first opening creates a pending owner/host batch. Claim under the owner lock sets announced and clears pending_batch before live fan-out. Merge any newly opening IDs into an existing unclaimed batch under the same lock. There is no unbounded queue or persisted recipient context.

Example: selecting A produces primary D1 and public successor `{delivery:D2,predecessors:[A]}` at C, with completed_topic_ids []. Finishing A queues D1 and can locally reveal D2; qualified Q stays absent. Selecting B records D3 without deleting D1/D2 receipts. Delayed `{delivery_id:D1,context_id:C,topic_id:A,scene_revision:"r1"}` saves A and publishes completed_topic_ids [A] without restarting D3. A later state commit opens Q and claims U; `{batch_id:U,host_id:41,context_id:C,topic_ids:[Q]}` waits until D3 finishes. Reload carries no U and replays D3 at line one with saved [A].

### UTF-8 publication budgets

Additional canonical UTF-8 JSON limits are mandatory: Scene <=8192 bytes, selected delivery plus all public successors <=16384 bytes, complete dialogue panel <=24576 bytes. Validate every authored fallback/variant and worst reachable public bundle before registry publication. No prose truncation or silent successor omission. Dynamic native/service candidates and the complete panel must pass before effects/session settlement; failure is an operational refusal with zero partial effects. Action success.message is a bounded acknowledgement; full prose ships through panel delivery or text emission.

Ordinary envelopes retain 65536 bytes. A snapshot/update carrying an available v3 dialogue panel may use <=98304 canonical bytes only when the same envelope with dialogue removed passes the original 65536 limit and dialogue passes 24576. This dialogue-only allowance reserves publication capacity without relaxing unrelated panel bounds. Runtime updates Python protocol.check_envelope/coordinator full_snapshot and panel_update plus UMD constants/core/store admission in lockstep, including the outer pre-panel byte check. Reconnect uses the same rule. No fragmentation or map-fragment reuse is introduced. Add maximal multilingual chain/reconnect acceptance and oversized pre-effect rejection; all other global string/depth/list bounds remain.

## Whole-batch critique disposition

One independent blocking review examined all 22 original complete artifact sets against the full approved design, without reading the reserved lore file or running code checks. Seven blocking findings were adopted: real misc.js/constants protocol targets; descriptor/request-ID composition; complete persisted context/receipt schema and direct-entry flow; populated public-chain/read/notification shapes; canonical UTF-8 publication budgets; complete conflicting main-spec deltas; and exact committed refresh source hooks. The final remedy splits physical and progression/lifecycle hooks into two additional bounded changes, making 24 proposals. The cross-context notification note was also adopted with recipient-context wrapping and a populated A/B/chain/unlock example. No finding was deferred and no second review was requested, following the one-whole-batch-review assignment. Final strict proposal validations are recorded in the handoff; implementation/browser acceptance remains planned, not exercised.

Strict validation initially exposed the local CLI scenario-identity preservation rule. The deltas retain existing native/invalid-context scenario identities with qualified inputs and add the new authored cases. The version-2 panel requirement is explicitly removed and fully replaced by version 3, preserving unrelated privacy/portrait/unavailable scenarios rather than keeping a misleading first-four truncation contract.
