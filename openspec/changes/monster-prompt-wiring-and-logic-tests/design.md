# Design

## Context

`render_prompt` (`world/prompts/loader.py`) substitutes with a bare `values[token]` lookup: a shipped template that uses a declared token the consumer never supplies raises a plain `KeyError` — not a `PromptUnavailableError` — so the layer's deterministic degrade path cannot catch it and the render crashes at request time. The pre-change registry declared `("description", "display_name", "examples")` for `art.monster_description` while `world/art/subjects.py::monster_description` supplied only `description`: one dead token (`examples`, unwireable and spec-forbidden) and one loaded landmine (`display_name`).

## Decisions

### D1. Supply every allowlisted token; the template owns token selection

`monster_description` always passes both `description=visual.published_appearance_zh` and `display_name=visual.display_label` from the selected `MonsterVisualDeclaration`. The library's standing rule is that a key renders with the tokens it declares (an admin rewrite may drop a token and the surplus value is inert), so allowing `display_name` costs nothing on the render side while supplying it removes the KeyError landmine: the consumer guarantees every declared token has a value, and the template decides which to use. Alternative considered: keep the allowlist at `("description",)` — rejected, because the species' own public display label is exactly the identity the visual registry was built to expose to art prompts, and the user is actively editing `prompts/art.yaml` and wants the name available without a code change. `examples` stays deleted rather than wired: no registry field exists to supply, so it could only ever be the landmine in D1, and the specs forbid the content.

The degrade invariant is unchanged: on `PromptUnavailableError`, `monster_description` returns `published_appearance_zh` alone (no `display_label`, no template text) — the same registry-driven fallback shape the character fallback has.

### D2. Monster prompt data is species identity, not species examples

The two requirements that previously said "public physical appearance only" gain one more admitted field: the *selected species' own* public display label. The forbidden set is unchanged and stays forbidden: threat-tier rank/descriptions, and *multi-species* example lists (the retired `example_monsters_zh` projection). The distinction is the visual registry's own contract: `display_label` names the one declared species; `examples` named several. This keeps D1's allowlist spec-legal instead of contradicting `art-subject-model`.

### D3. Prompt tests assert program logic; shipped wording is not under test

Prompt tests verify code-level contracts only: a key exists and loads, its `PROMPT_SPECS` allowlist and the shipped template's token set are equal in both directions (the existing `test_character_description_placeholder_set_matches_the_template` parity pattern, extended to the monster key), supplied values reach the output and no `{token}` survives, two identical renders are byte-identical, and degrade paths equal the registry projection they claim to equal. Tests MUST NOT assert literal wording of shipped `prompts/*.yaml` text (D4 generalizes the rule to every prompt file, not just `art.yaml`): the deployment owner edits it freely, so such pins are churn, not regressions. Inline fixture templates inside tests MAY keep literal expected renders — a fixture root's text is test-owned — the ban covers only pins against the shipped library. Determinism assertions stay (byte-identity of two renders), pin-free assertions drop (`first == "t_ashfolk, 24 years old."`).

Consequences to enforce in the rework: a monster subject in any test is built from a registered visual key (baseline row such as `goblin`, or a synthetic combat species projected through `adapt_combat_species`), never from a `SYNTH_MONSTER_TIERS` key; the broken-art degrade assertion compares against `get_monster_visual_registry()[key].published_appearance_zh`, never against a tier description; and every inline `art.yaml` fixture drops `{examples}` unless the test's point is that an out-of-allowlist placeholder is a load error (intentional trap fixtures keep a token outside the allowlist, e.g. `{oops}`, not `examples`, since `examples` will be just another unknown placeholder — keeping the existing intentional traps as-is and rewriting the incidental `examples` uses to fixture-valid two-token text).

### D4. The wording-pin ban is suite-wide across every prompt key, not just art

The same file that prompted the complaint (`prompts/art.yaml`) sits beside `narrator.yaml`, `npc_dialogue.yaml`, and nine other deployment-edited files, so the churn-free rule covers every shipped prompt file. The line is what the literal *is*, not which key it names:

- **Banned everywhere:** comparisons of rendered shipped-library output against whole shipped sentences — the `assertEqual(rendered, _SHIPPED_CONSTANT)` verbatim-shipment pattern in `test_verbatim_shipment.py`, the `first == "t_ashfolk, 24 years old."` byte pins, and whole shipped framing sentences like `assertIn("以下是你目前的人物設定", …)` or `assertIn("### 人物定錨\n你是《伊洛瑟恩大陸》中的 艾洛西亞。", …)` in prompt-library-obligation tests. A whole-sentence pin breaks on any wording edit and is exactly the churn class being retired.
- **Kept:** substitution probes on *test-supplied values* (a render called with `scene_sentence="古老森林深處的祭壇"` asserting that value lands — the value is test-owned, the template may reword freely around it), two-render byte determinism, token-parity checks, and short semantic-contract probes — the role/language/fidelity vocabulary an owning main-spec scenario names by words (`正體中文`, `不得虛構`, `僅供靈感`, `伊洛瑟恩大陸`, `必須附帶 display_name 與 title`, `QuestBlueprint` shape). Those pin the meaning the scenario names, not template wording, so they stay wherever their owning scenario's `@covers_requirement` places them, including the few prompt-library suite tests whose main-spec scenario itself names the guidance phrases (`test_shipped_text_carries_token_and_inspiration_guidance`). The ban is on whole shipped sentences and byte-for-byte shipment constants, not on a scenario's own named vocabulary.
- `test_verbatim_shipment.py` retires as a shipment-pinning module: its per-key byte pins become the logic suite (key loads; template-token ↔ allowlist parity where the key declares tokens; supplied values substitute exactly and leave no `{token}`; two renders byte-identical; no shipped-text constant in the test module). Its `LibrarySourceTests` source-of-truth checks (consumer output equals `render_prompt(key, …)`) survive unchanged — those compare the consumer against the library seam, no literal at all.
- The ban reaches the *consumer* suites that render the shipped root, not just `world/prompts/tests/`. `PromptFixture` copies the repo's own `prompts/` into its fixture root, so every `world/art/tests/` description test that composes over the shipped `art.yaml` inherits its exact framing text — and a deployment retune like commit `858e52dc` ("append `standing, rim light on clothes,`" / LoRA tags) breaks them today: `AppearanceDescriptionTests` byte-pins (`test_description_is_byte_identical_with_declared_subkey_order`, `test_empty_appearance_renders_the_pre_change_description`, `test_overlong_appearance_is_capped_to_the_persona_field_bound`'s `removeprefix` of the shipped stem, `test_library_turning_unavailable_mid_render_keeps_the_base`) and `CompositionTests` (`_BASE` equality/startswith, `test_accepted_free_text_is_appended_after_every_field_contribution`'s `endswith`) all fail on framing-text edits alone. The fix is not a refreshed literal: these tests assert *composition* claims (subkey order, exclusion, cap, fallback base, field-order, free-text append), so each writes its own inline `art.yaml` fixture with test-owned wording and asserts the composition claim against that fixture; a small subset of pure library-seam checks keeps the shipped root but asserts only logic (loads, substitution of supplied values, two-render determinism). The composition claim is then template-independent: any framing a deployment adds can neither break it nor fake it.

Acceptance anchor for the whole rule: replaying a wording-only edit like `858e52dc` (append framing tags inside the existing token skeleton of any shipped template) over the fixture-copied root must leave every prompt and art-description test green — the CI-visible proof that wording churn is dead. Only token-set changes (add/remove/rename a `{token}`, or an out-of-allowlist placeholder) may break tests, via the parity/load-error checks.

Scope guard: no delta to the consumer capability specs (`narrator`, `scenario-director`, `npc-dialogue`, `ai-action-options-prompts`, …) — their content scenarios already state the semantic probes in words, and the probes named by those scenarios (`伊洛瑟恩大陸`, `正體中文`, `QuestBlueprint`) are contract vocabulary, not sentence pins. The sweep only relocates prompt-library-obligation probes and deletes whole-sentence/byte pins.

## Risks / Trade-offs

- A shipped template that names `{display_name}` renders the species label into image prompts; this is the intended capability and the label is public art data by registry design.
- Tests can no longer catch a whole-file rewrite of shipped prompt wording; wording quality is a content concern guarded by the semantic probes in the consumer capability tests plus the parity/load/determinism logic suite, which still catch every structural break.
