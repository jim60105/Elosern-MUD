# Design: Party-scope browser retreat/surrender confirmation and cutover

## Context

See `proposal.md` for motivation and the batch contract in `../combat-ratio-mitigation/batch.md` for complete coverage, order and conflicts. The active warning proposal already uses QuestionCard with No initial focus and an inert background; party confirmation reuses that behavior.

Inspected boundaries are listed in the proposal Impact section. These are observed starting points; all new behavior below is proposed, with no runtime result claimed. The approved 2026-10-15 document explicitly amends the base engine §6.3 where subtraction, allied autonomy and individual allied flee conflict.

## Goals / Non-Goals

This change owns party-scope browser retreat/surrender confirmation and cutover. It reuses existing deterministic state owners and exact protocol conventions. Required behavior is defined by its complete delta files. There is no new LLM dependency, compatibility path, data migration, shared inventory, companion equipment-management UI or physical proficiency progression. Detailed stage geometry remains owned by the existing UI batch.

## Decisions

Expose Retreat and Surrender from every member root and actor-selection frame, using one existing party-operation submenu if needed within the card; neither operation requires the selected member to be commandable. Request server prompt data before mutation. Reuse QuestionCard in choices with initial focus No, explicit whole-party scope and consequences (failed retreat consumes all allied turns; surrender has existing defeat/exam consequences), and the server-bound token/session/round. Yes dispatches combat.exit_confirm once; No, close and Escape discard only local prompt data and restore prior actor/menu/selection and server draft unchanged. Make dock/stage controls inert during the dialog, preserve existing cross-side warning ordering, cancel pending cast warning before opening an exit prompt. Invalidate stale tokens on session/round/mode/epoch replacement, disconnect or playback; unrelated same-round resync retains safe prompt state only when token still valid. Apply canonical failure/new-round and terminal snapshots; no invented relocation/heal. Migrate every retired combat.flee/forfeit producer and allied skill-list route to these operations, with no compatibility transport. Confirmed surrender and retreat share server receipt semantics; never retry a stored Yes after reconnect.

## Risks / Trade-offs

- [Shared boundary changes] -> Implement only after declared prerequisites, integrate earlier deltas and callsites, and use the batch matrix to serialize overlapping files. No obsolete alias or duplicate implementation remains after cutover.
- [State or capability changes after selection] -> The shared rules boundary repeats authoritative validation; invalid drafts and normal mid-round invalidation follow different documented semantics.
- [Unproven arithmetic, persistence or UI behavior] -> Tasks include focused independent assertions and actual evidence where owned here. A selected constant alone is not measured balance and a fixture-only UI is not runtime acceptance.
- [Estimate depends on existing patterns] -> Scope is bounded to the listed owner and 5.5 hours includes its focused tests/docs/integration. Required downstream behavior is owned explicitly in the batch rather than silently deferred.

## Migration Plan

Pre-release clean cutover only. Implement code, callsites, fixtures, exact schemas and affected canonical requirement annotations together for this slice. No old/new compatibility parser, stored-data migration or deprecated entry path is added. Rollback uses an ordinary revert of the implementation change; proposal authoring performs no rollback, merge, apply or archive. The assembled client/server cutover is accepted only after change 18.

## Verification and documentation ownership

Use synthetic fixtures for independent behavior expectations and the existing real-data calibration boundary for authored roster evidence. Register added/moved Evennia tests and browser methods exactly once in the appropriate shard manifest; annotate tests with canonical `<capability>.<requirement-slug>` IDs generated by the project traceability tooling. If the canonical slug changes, migrate every affected annotation. Update existing affected documentation, both player command documents for syntax/context changes, and focused schema/fixture mirrors for transport changes. Run the focused tests and `uv run --locked python -m tools.contract_gate` during implementation; logging changes also require observability lint and focused event tests. Complete managed browser and traceability-evidence execution stay CI-owned.
