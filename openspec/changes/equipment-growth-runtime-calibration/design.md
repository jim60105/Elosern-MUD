# Design: Authored shipped weapon values and committed-reload growth evidence

## Context

See `proposal.md` for motivation and the batch contract in `../combat-ratio-mitigation/batch.md` for complete coverage, order and conflicts. Equipment_effects.yaml contains real military and other weapon/armor entries with flat adjustments but no selected weapon factor; existing runtime calibration evidence uses real kit.

Inspected boundaries are listed in the proposal Impact section. These are observed starting points; all new behavior below is proposed, with no runtime result claimed. The approved 2026-10-15 document explicitly amends the base engine §6.3 where subtraction, allied autonomy and individual allied flee conflict.

## Goals / Non-Goals

This change owns authored shipped weapon values and committed-reload growth evidence. It reuses existing deterministic state owners and exact protocol conventions. Required behavior is defined by its complete delta files. There is no new LLM dependency, compatibility path, data migration, shared inventory, companion equipment-management UI or physical proficiency progression. Detailed stage geometry remains owned by the existing UI batch.

## Decisions

Author an explicit initial and selected multiplier for every registered weapon plus per-rarity ceilings in equipment_effects.yaml, with neutral declarations justified for weapons that receive no physical bonus. At least representative real physical weapon upgrades must be nonneutral and demonstrate growth; runtime never computes rarity scaling. Inspect the actual complete registry rather than assume only military swords exist. Use real Evennia construction, ordinary grant/equip rules, committed persistence, cache eviction and fresh reload to compare unarmed/upgrade/armor states. Record engine revision, backend, registry item keys, true stats, chosen factor/defense, fixed roll, baseline and selected output. Prove independent K=40 cases (60→40 at defense20, Defend→26, physical factor1.5→60, magic unaffected). Cover armor monotonicity, occupied nonweapon main hand, offhand fallback/dual wield, below-old-threshold positive marginal growth for an adequate upgrade, magic/healing controls and base-trait/proficiency/affinity invariance. Full encounter balancing and any evidence-supported coefficient changes belong to change17; record these as measurements, never assert K40 is balanced. Amend the historical no-tuning scenario narrowly to permit approved evidence-driven equipment authoring, leaving historical evidence qualified.

## Risks / Trade-offs

- [Shared boundary changes] -> Implement only after declared prerequisites, integrate earlier deltas and callsites, and use the batch matrix to serialize overlapping files. No obsolete alias or duplicate implementation remains after cutover.
- [State or capability changes after selection] -> The shared rules boundary repeats authoritative validation; invalid drafts and normal mid-round invalidation follow different documented semantics.
- [Unproven arithmetic, persistence or UI behavior] -> Tasks include focused independent assertions and actual evidence where owned here. A selected constant alone is not measured balance and a fixture-only UI is not runtime acceptance.
- [Estimate depends on existing patterns] -> Scope is bounded to the listed owner and 6 hours includes its focused tests/docs/integration. Required downstream behavior is owned explicitly in the batch rather than silently deferred.

## Migration Plan

Pre-release clean cutover only. Implement code, callsites, fixtures, exact schemas and affected canonical requirement annotations together for this slice. No old/new compatibility parser, stored-data migration or deprecated entry path is added. Rollback uses an ordinary revert of the implementation change; proposal authoring performs no rollback, merge, apply or archive. The assembled client/server cutover is accepted only after change 18.

## Verification and documentation ownership

Use synthetic fixtures for independent behavior expectations and the existing real-data calibration boundary for authored roster evidence. Register added/moved Evennia tests and browser methods exactly once in the appropriate shard manifest; annotate tests with canonical `<capability>.<requirement-slug>` IDs generated by the project traceability tooling. If the canonical slug changes, migrate every affected annotation. Update existing affected documentation, both player command documents for syntax/context changes, and focused schema/fixture mirrors for transport changes. Run the focused tests and `uv run --locked python -m tools.contract_gate` during implementation; logging changes also require observability lint and focused event tests. Complete managed browser and traceability-evidence execution stay CI-owned.
