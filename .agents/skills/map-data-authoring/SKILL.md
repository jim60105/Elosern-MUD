# Map data authoring

Elosern's static maps live in YAML under `content/maps/`. The game and the
standalone map editor (`tools/map-editor/`) read the **same files**: there is
no Python map table, no generated map source and no database copy to update.
Editing the YAML is the whole change. The parts that make it work are:

- **Identity.** Every object has a stable English slug. Other documents refer to
  objects by slug, never by coordinates or display names.
- **Ownership.** Each relationship is stored once, in exactly one document.
- **Verification.** After every edit, run the check script and fix what it
  reports before you hand the work back.

## Source map

| File | Owns | Reference |
| --- | --- | --- |
| `content/maps/continent.yaml` | frame, mainland polygon, 7 terrain regions, ridge and passes, waterways and fords, forest edge, coastal band, harbour sites | [continent.md](references/continent.md) |
| `content/maps/locations.yaml` | every geographic location (capital, city, town, port, elven village, dungeon): name, prose, cell | [locations-and-districts.md](references/locations-and-districts.md) |
| `content/maps/districts.yaml` | world-map districts and their landmark references | [locations-and-districts.md](references/locations-and-districts.md) |
| `content/maps/settlements/<map_id>.yaml` | one local map: binding to its location, nodes, directed roads, footprint and wilderness gates, city gate | [settlements.md](references/settlements.md) |
| `content/maps/interiors/<interior_id>.yaml` | permanent rooms, connections, links to other interiors, the exterior doorway | [interiors.md](references/interiors.md) |
| `content/map-editor-layouts/<interior_id>.yaml` | editor-only room card positions, with no effect on gameplay | [interiors.md](references/interiors.md) |
| `world/maps/data/district_partition.json` | **generated**, never edit by hand | [verification.md](references/verification.md) |
| `content/map-reference-context.json` | **generated** index of external IDs and incoming references, never edit by hand | [verification.md](references/verification.md) |

Read only the reference file for the domain you are changing. For the exact
type of a field, the machine-readable schema is authoritative:
`uv run --locked --project packages/map-core python -m elosern_map_core schema`.

## Working alongside the editor

The human may have the editor open at `http://127.0.0.1:8765/` while you work.
There is no lock, handoff or turn-taking. The editor watches `content/`,
reloads when files change, and adopts any loadable external change
automatically. Its undo history is cleared when it does. That gives you a few
duties:

- **Do not edit the same document the human is editing.** If both of you save
  one file within about 0.15 s, the editor's save is refused and your bytes
  win. Ask which document they are working in if it is unclear. Assume any
  uncommitted change in `git status` is the human's deliberate editor work:
  build on it and do not revert it.
- **Malformed YAML freezes the editor.** A structure error makes the editor
  keep a stale preview and refuse every write until the files load again. Do
  not leave a half-written multi-file change on disk longer than you need to,
  and always finish with a loadable tree.
- **Never write the generated artifacts by hand.** The partition JSON is
  regenerated by a command (or by the editor's 分區 chip). The reference index
  is regenerated by a game tool. See [verification.md](references/verification.md).
- **OMP context.** The editor's 複製 OMP 脈絡 (Ctrl/⌘+C on a selection) gives you
  qualified IDs such as `settlement_node:capital_altoria:central_plaza`, the
  owning file, coordinates with their unit, and whether the preview was stale.
  Treat this as the selection the user means. Locate the object by its ID in
  the named file.

## Ground rules

These are the rules the editor enforces. Following them keeps your YAML
indistinguishable from editor output:

1. **IDs are permanent.** Never rename an existing slug: node, room, interior,
   settlement, location, district, waterway or site. Other documents and game
   code join on it, for example service places and NPC hosts join interior
   room IDs. New IDs match `^[a-z][a-z0-9_]*$`, and the file stem must equal
   the document's `id`. A room ID must be unique across **all** interiors.
2. **Deletion never cascades.** Before you delete an object, remove every
   reference to it: roads, gates, the city gate, interior exteriors and links,
   and district landmarks. Then check `content/map-reference-context.json` →
   `incoming_references["<qualified id>"]` for external references from quests,
   places or service hosts. Those references live in Python lore you would have
   to change first, and only when the user asks for that. If the index is not
   current, do not delete; ask.
3. **Directions are authored, not computed.** A road's `direction` and a gate's
   `return_direction` are chosen values (`n ne e se s sw w nw`). Moving a node
   never changes them. If a move makes a direction look wrong, ask the user
   before you change it.
4. **Units never mix.** Cells are integer 1 km wilderness indices
   (`cell_x`/`cell_y`, `y` grows **north**). The mainland polygon is integer
   kilometres (`east_km`/`north_km`). Settlement positions and bends are
   integer metres in the local frame (`x_m`/`y_m`, `east_m`/`north_m`).
   Interiors have **no** coordinates, and layout `x`/`y` are only canvas units.
5. **Restricted YAML.** The loader rejects duplicate keys, anchors and aliases,
   merge keys, tags, timestamps, `.inf`/`.nan`, hex, octal and `1_000`
   integers, unknown fields and any type coercion. An integer field never
   takes `true` or `"12"`. Write `version: 1`, `kind`, `id` on every document.
   Nullable fields must still be present: write `scene_archetype:` with an
   empty value, or `null`. Keep the existing comments, and keep multiline prose
   in a block scalar or a plain folded string, as the file already does.
6. **Keep each change inside one owner, where you can.** The editor changes one
   document per operation, and a two-way road writes both directed entries in
   that one settlement file. You may touch several files in one task, but only
   when an invariant below links them.
7. **Stay in scope.** Do not change names, prose, balance, topology or
   population as a side effect. Non-map lore stays in its Python owners: a
   nation's politics, populations, NPCs, shops, quests and the scene/art
   catalogues. The map data only *references* scene archetypes and art keys
   that already exist.

## Cross-file invariants and validation ownership

Core diagnostics check settlement anchor node presence/uniqueness and key match, non-negative node coordinates, footprint mask grammar and 4-connectedness, mask hash and approach cell validity, footprint and gate collisions, point gate counts and entry directions, and interior room ID and doorway uniqueness. A settlement authors **no** world frame and **no** absolute footprint origin: its frame is its location cell plus its unique `anchor_room`, and its mask origin is that cell plus the entry's signed `offset{dx, dy}`.

The remaining game-side cross-file rules are enforced during candidate composition before publication:

| When you change… | Also keep consistent |
| --- | --- |
| a location's `cell` (moving a town on the continent) | nothing else in the settlement document. Every node's world metres, the mask, its midpoint and every gate approach translate by the same delta; the document stays byte-identical. |
| the `anchor_room` node's `x_m`/`y_m` | nothing else. The anchor stays on the location cell's centre and every untouched node's world position shifts by the negative local delta; the location and the mask stay fixed. |
| any node's `x_m`/`y_m` into negative metres | re-origin the whole document: translate every node and road bend by the same delta. The authored pair is the node's grid coordinate, which must stay non-negative, and a pure translation changes no world position or road length. |
| a Voronoi district landmark | ≥ 100 km from every other Voronoi landmark, unique district and landmark names |
| any `scene_archetype` or `nation_key` | must be in the reference index's registered identifier sets |

A valid mask whose bounding-box midpoint differs from its location cell is
reported as `footprint_location_offset` with `severity: warning`. It is
advisory: it never blocks saving, generation or adoption, and nothing
re-centres the mask for you.

Anything that feeds the district partition makes the committed partition
stale. That includes continent terrain, locations, districts and **any**
settlement file. A stale partition is valid, saveable work in progress, but it
is not game-ready until you regenerate the partition.

## Workflow

1. **Orient.** Run `git status`, read the target document, and find the
   objects you will touch by ID. For a coordinate question, read the relevant
   reference file first. The axis directions and the mask row order are easy to
   get backwards. Run the check script once **before** you edit and note what
   it already reports: the committed partition or reference index can already
   be stale, and a contract test can already fail on master. Without a
   baseline you cannot tell your breakage from what you inherited, and you
   cannot compare against a clean tree later because a stale committed
   partition makes the game refuse to load it.
2. **Edit** the YAML directly. Prefer small, surgical edits that keep the
   surrounding comments.
3. **Check** from the repository root:

   ```console
   uv run --locked --project packages/map-core python .agents/skills/map-data-authoring/scripts/check_map_sources.py
   ```

   The script reports the result in three layers:
   - structure errors: the editor freezes, fix these first;
   - core semantic diagnostics plus the game's cross-file rules: these block
     game adoption;
   - partition, elevation and reference-index freshness.

   Exit code 0 means the edit is game-ready as far as static checks can tell. A
   loadable work-in-progress result (exit 1) is acceptable mid-task, but say
   so.
4. **Regenerate derived output** only when the check asks for it, and tell the
   user. For the partition, no game environment is needed:

   ```console
   uv run --locked --project tools/map-editor python .agents/skills/map-data-authoring/scripts/regenerate_partition.py
   ```

   The script refuses to run while other problems remain. If the editor is
   open, the user can press its 分區 chip instead. Do not run both at once.

   For wilderness elevation tiles:

   ```console
   uv run --locked --project tools/map-editor python .agents/skills/map-data-authoring/scripts/regenerate_elevation.py
   ```

   Regenerate **after your last source edit**, then run the check again. The
   partition signature covers every location cell, so even a three-cell nudge
   to one town after regenerating makes the game refuse the whole world in
   every test that loads it. If you change Python lore the index reads (for
   example `ANCHOR_LORE` or a kind enum), regenerate the reference context too
   (`uv run --locked python -m tools.map_reference_context`).
5. **Test** what the change can reach. Static checks never load the game, so a
   new location kind or lore row is only proven by the tests that consume it.
   See [verification.md](references/verification.md#focused-tests) for the
   labels and the test runner's rules.
6. **Report** which documents you changed, each object by qualified ID, the
   check result, and anything left stale or unfinished.

## Seeing a map

When the work needs eyes on the map, capture it instead of guessing from
YAML. `capture_map.py` draws one view — continent, settlement or interior —
from the current disk sources, in a disposable offline browser, and publishes
a lossless image. No editor, game or server is needed. Full parameter, layer
and format reference: [verification.md](references/verification.md#capturing-an-image-of-a-map).
Settlements take their document ID (`content/maps/settlements/<id>.yaml`);
interiors take theirs (`content/maps/interiors/<id>.yaml`); the continent
takes none.

```console
# Once per checkout.
uv sync --locked --project tools/map-editor --group capture
uv run --locked --project tools/map-editor --group capture playwright install chromium
pnpm --dir tools/map-editor/frontend install --frozen-lockfile
pnpm --dir tools/map-editor/frontend run build:capture

# One image: 1280x960 lossless WebP, all layers, whole map.
uv run --locked --no-sync --project tools/map-editor --group capture python \
    .agents/skills/map-data-authoring/scripts/capture_map.py \
    --view continent --output /tmp/continent.webp
```

Every layer is on unless you pass `--hide` (`terrain`, `water`, `ridge`,
`locations`, `footprint`, `partition`, `labels` for the continent; `nodes`,
`roads`, `labels` for a settlement; `rooms`, `connections`, `exterior`,
`labels` for an interior). `--bounds` is in that view's own frame — kilometres,
authored metres, or layout units — and `--format png` is available when your
image tool cannot read WebP. A continent capture with `partition` visible
needs a current partition artefact; regenerate it or pass `--hide partition`.

Then **read the image**. A zero exit status only means the file was written.
Open `image_path` with your image-reading tool and describe what is really
there; if the tool cannot decode WebP, rerun with `--format png` and a `.png`
path rather than converting silently. Capture once at overview size, then a
regional `--bounds` view for small labels. Do not claim token savings from
WebP: bytes and model tokens are different measurements.

## Placing sites

Before you author a new location, harbour site or district landmark cell,
check the candidate cells with `place_sites.py`. It reads the current
continent from disk and, for each site, reports whether the cell is walkable
or waterway, its terrain region and nominal nation, its distance in cells to
the nearest waterway and to the sea, and every pair of sites closer than
`--min-km`. A site with `snap` moves to the nearest walkable, non-water cell
within 2 cells of a waterway (`river`), of the sea (`sea`) or of both
(`both`). The terrain checks are CPU-bound Python, so the script spreads the
sites over a process pool with one worker per CPU (`--jobs` overrides it).

```console
# Candidates: [{"id": "my_port", "cell": [2073, 247], "snap": "sea"}, ...]
uv run --locked --project packages/map-core python \
    .agents/skills/map-data-authoring/scripts/place_sites.py candidates.json \
    --output snapped.json

# Re-check every authored location and harbour site after a terrain edit.
uv run --locked --project packages/map-core python \
    .agents/skills/map-data-authoring/scripts/place_sites.py --locations
```

It never writes map sources; copy the snapped cells into the YAML yourself,
then run the check script. A terrain edit such as a moved river or coast can
strand an existing location, so run `--locations` after one. Exit code 1
means at least one site is not walkable, sits on a waterway or found no cell
to snap to.

`--rivers` checks every waterway's mouth instead: its last route vertex must
be within 2 cells of the sea or of another waterway. The core accepts a river
that simply stops inland, and on the canvas it looks finished, so run this
after any waterway edit and before you put a "river mouth" port on one.

Placement habits that saved rework:

- Snap ports with `sea` and river or ford towns with `river`, then read the
  reported distances. A town on the wrong side of a border river lands in the
  other nation; the `nation` column shows it.
- Keep a location off its harbour site's cell. The harbour site is the
  reserved landing, the town sits a few cells inland, and two markers on one
  cell hide each other.
- Treat the `--min-km` pair list as a review prompt, not an error: twin towns
  across a ford are meant to be close; two unrelated towns 20 km apart
  usually are not.

## Common tasks

These are short recipes. Each reference file has the details.

- **Move a town/village/dungeon on the continent.**
  1. Set `locations.<id>.cell`.
  2. Change nothing else: the settlement's world frame and footprint follow
     the location cell, so the whole town and its wilderness entrances move
     together.
  3. Run the check. The new cells must be walkable land, the footprint must
     not overlap another footprint, and the gate approaches must stay valid.
  4. Regenerate the partition.
- **Re-shape a wilderness footprint.** Set `wilderness_entry.shape` and its
  `offset`; the offset is a signed cell delta from the location cell, and row
  zero is the southern row. The editor's 佔地 tool takes absolute cells and
  saves the converted offset for you.
- **Add a street node and a two-way road.** Add `nodes.<new_id>` with every
  node field. Then append **two** entries to `roads`: A→B with its direction,
  and B→A with the opposite or authored return direction. One node never has
  two outgoing roads in the same direction.
- **Add a shop interior with a door onto a street.** Create
  `interiors/<id>.yaml` with its rooms and `connections`, plus `exterior:
  {settlement, node, room, doorway_key, doorway_aliases}`. Nothing in the
  settlement file changes: the door belongs to the interior.
- **Add a new location without a local map.**
  1. Pick its cell with `place_sites.py` (see *Placing sites* below), so it is
     walkable, off the water and on the right bank or shore.
  2. Add it to `locations.yaml` with a `kind` of `capital`, `city`, `town`,
     `port`, `elven_village` or `dungeon`. A national settlement uses `city`
     (inland, about 25,000 people or more), `town` (smaller) or `port` (its
     role is a sea harbour, whatever its size). Write the ID with the matching
     prefix, such as `port_white_sail` or `town_scarp`.
  3. Add its `ANCHOR_LORE` row in `world/lore/anchors.py` (nation and
     population). Every lore row must join a location and the reverse, so the
     two change together. This is Python lore: do it only when the user asked
     for the location.
  4. A local map is a separate later step: a new `settlements/<map>.yaml` with
     `location_ref: <id>`. Locations never list their maps.
  5. Regenerate the partition and the reference context.

  For many locations at once, write them through the core codec instead of
  hand-typing YAML, so the wrapping and key order match the editor:
  `parse_document` the file, add entries to a thawed copy of
  `parsed.document.data`, build it with `document_from_data`, and write
  `serialize_document(document, parsed.round_trip)` (all in
  `elosern_map_core.codec`). New keys land after the existing ones.
- **Add a location kind.** The kind list is closed and lives in several
  places that must agree; the full list is in
  [locations-and-districts.md](references/locations-and-districts.md#location-kinds).
  Ask first: it is a code change, not map data.
- **Move, extend or add a waterway.** End it in a sea cell (or on another
  waterway), keep it clear of harbour sites, then run `place_sites.py
  --rivers` and `--locations`, because a moved river can swallow a town's cell
  or leave a river port dry. Regenerate the partition and the elevation.
- **Add or move a district.** Edit `districts.yaml`. The landmark is a
  qualified reference, never a coordinate, unless its domain is
  `wilderness_cell`. Then regenerate the partition.

## When to stop and ask

Stop and ask before you:
- rename an ID;
- delete an object that has incoming references;
- change a road or gate direction that the user did not mention;
- edit Python lore to remove an external reference;
- touch a document the user says they have open in the editor;
- do any change whose only route breaks one of the invariants above.
