# 遊戲主持人總覽與工作原則

遊戲主持人的內容工作分為兩類。第一類是不可變的世界資料，例如種族、物品、魔物階級與地點識別；第二類是受驗證的輸入，例如角色匯入檔、任務定義與公會報酬。每次異動都應保留可重現的來源檔，並通過對應測試。

## 權責邊界

`world/lore/` 是世界資料的來源。登錄表使用穩定的 `key` 讓任務、角色卡與規則書相互參照。若要新增任務目標物品、魔物階級或錨點地點，請先在這裡建立可驗證的識別，再由任務引用它。

`world/quests/` 保存任務的定義與執行期。任務進度、失敗狀態與執行期綁定由任務模組處理。`world/rules/` 處理戰鬥、金錢、背包、公會與世界時間。`world/ai/` 只能讀取狀態並提出經過結構驗證的內容建議，不能直接寫入遊戲狀態。

內容撰寫仍提交任務或角色的來源資料，讓載入器與規則 API 套用變更，並透過 git 保存來源。手動修補任務紀錄、金錢、經驗值、背包與戰鬥結果一律使用 GM 主控台，禁止在 Django shell 修補。

主控台的領域操作分別由 `world/rules/gm.py`、`world/maps/gm.py`、`world/quests/gm.py` 與 `world/narrative/gm.py` 負責。原始資料編輯由 `server/console/raw.py` 處理，介面持續顯示「繞過規則層」警告；它能編輯 Evennia 物件的 Attributes、標籤與位置，但不會修復連帶規則狀態，也不能編輯 typeclass 或其他模型。這項指引未新增經驗值或戰鬥結果的領域操作。

伺服器啟動後的第一筆主控台寫入會先存檔。遊戲內 tick 與最近的存檔基準不同時，下一筆寫入也會先存檔；存檔失敗便不執行操作。基準只衡量遊戲內時間，不涵蓋未推進時間的玩家變更。成功的手動存檔會更新基準，復原則使用存檔頁既有的讀檔與重新啟動流程。

主控台自身的時間推進會納入基準，但存檔副本外的玩家時間變更不會被吸收。確認畫面的存檔提示只是預覽，送出時由伺服器重新判定；操作結果會顯示實際存檔編號，即使操作遭拒，已完成的介入前存檔仍保留。原始資料寫入後會重新讀取概要與原始資料，不沿用寫入前的快取；結果提示也會保留。

## 內容撰寫前的檢查

角色、NPC 與匯入資料中的 `age` 和 `apparent_age` 都必須是 `0` 至 `10000` 的整數。兩者分開驗證，任一數值超出範圍都會被拒絕。角色的顯示偽裝數值只影響外觀、鑑定與公會註冊時的展示；戰鬥與規則判定一律使用真實數值。

金錢一律以整數銅幣儲存。任務或商店資料不得使用浮點數，也不要自行換算成銀幣或金幣後寫入狀態。

任務的任意敘事可由導演系統補充，但完成條件、目標數量、地點、時限、報酬與失敗原因必須在確定性資料中定義。內容設計需要先回答玩家進行了哪個可觀測的動作，系統再據此更新進度。

## 目前的主持人作業路徑

角色作業請從 JSON 角色卡開始，先驗證再匯入。任務作業請在 `world/quests/catalog.py` 撰寫不可變的 `QuestDefinition`，並在 `world/rules/rulebook/guild_economy.yaml` 為公會任務設定報酬。伺服器啟動時會依序同步世界資料、地圖、任務執行期與公會經濟資料。

若內容需要尚未存在的機制，例如新的任務目標種類、任務發放來源或 AI 產生任務，請先以 OpenSpec 變更定義行為與驗收情境。不要把未實作的資料欄位放進現有角色 JSON、任務資料類別或規則書。
