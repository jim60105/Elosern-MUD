# 魔物資料模型設計

**日期：**2026-10-05。**狀態：**資料分層與本篇列出的行為邊界已核准，尚未實作。

本設計將魔物資料分為物種、變體、實際個體、地區／據點配置與委託五層，承接 [魔物創作傾向指南](/lore/monster-creation-guidelines)。創作指南負責內容方向，本篇負責身分、資料來源與確定性子系統的責任。

本次核准不包含個別物種、候選評級或能力數值。分級舉例、測試資料與尚未核准的候選，都不能作為正式物種登錄的依據。首批內容仍以低階與中階為範圍。

## 1．現況與設計範圍

現有 `Monster` 與確定性引擎可繼續使用，但層級式資料不足以承載正式物種名錄。這次設計擴充身分與內容資料，不建立第二套魔物引擎。

| 現有資料或流程 | 限制 |
| --- | --- |
| `Monster` 的 `threat_tier`、`loot_table` 與 `behaviour_tree` | 缺少正式物種與變體身分；`behaviour_tree` 實際用作行為設定鍵 |
| `MonsterTier` 的區間與 `example_monsters_zh` | 描述粗略強度及分級舉例，不能代表個別物種 |
| 野外族群從分級示例挑選名稱 | 缺少核准物種、棲地及配置之間的明確關係 |
| 討伐條件使用層級或綁定個體 | 缺少完整的區域、物種與變體條件 |
| 魔物圖片主體使用層級識別 | 尚未連接正式物種的共用圖片身分 |
| 委託定義已有階級 | 缺少評級理由與背景風味文字欄位 |

現行低階與中階的層級建構會將 MP、SP 與 `magic_power` 設為零，物理三軸則採同一區間位置。這些值不能推導正式物種的魔法能力或資源池。現有魔物行為主要選擇傷害技能，純控場與資源型能力也不會因為填入技能鍵就自動可用。

本篇不登錄新技能、不建立生產或掉落系統，也不增加完整生態模擬。候選能力經內容核准後，仍須對接實際可執行的技能與行為契約。

## 2．物種資料

物種是可重用的世界內容，採現有凍結資料與鍵值登錄表的慣例，由 `world/lore/` 提供唯讀來源。

| 資料 | 語意 |
| --- | --- |
| 穩定物種鍵 | 不依賴中文名稱、威脅層級或個體身分的識別碼 |
| 顯示名稱 | 玩家可讀的物種名稱；改名不改變物種身分 |
| 公開描述、外觀與生態 | 可公開呈現的世界內容，符合創作指南 |
| 棲地相容性 | 物種適合的環境，供配置合法性判斷 |
| 作者私有註記 | 區分隱秘真相、作者解釋與尚未證實的猜想，不直接公開 |
| `default_variant_key` | 屬於本物種的預設普通變體，代表物種基準 |
| 物種圖片身分 | 以穩定物種鍵連接共用官方圖片，獨立於實際個體的圖片選擇與幾何設定 |

物種的能力基準由預設變體提供，不在物種與變體各儲存一份。預設變體必須屬於該物種，且屬於普通版本；其他普通職能與較強版本可另定具名變體。

棲地相容性不授權實際生成。適合森林的物種，不會因此出現在所有森林；實際出現位置由配置資料決定。

公開敘述與公開圖片描述只讀取明訂的公開欄位投影，不序列化整份物種資料。作者私有註記不能補作缺少的公開敘述。公開猜想仍須保留來源及不確定性，不能呈現為已知真相。

## 3．變體資料

變體同樣使用唯讀登錄資料。每個變體有穩定鍵與所屬物種鍵，名稱不作為物種或強度判定依據。

| 資料 | 語意 |
| --- | --- |
| 穩定變體鍵與物種鍵 | 明確連接所屬物種，供配置、任務與個體引用 |
| 顯示名稱與描述 | 說明職能、行為或能力差異 |
| 完整基礎能力 | 明訂 HP、MP、SP、物理戰鬥力、敏捷、防禦與魔力，使用字面基礎值 |
| 技能與行為設定 | 引用已核准且可執行的技能鍵、現有行為設定與戰鬥特質 |
| 威脅層級 | 低階、中階等粗略分類，不用來識別物種 |
| 個體危險評級與理由 | 作者指定的公會危險評估，獨立於整份委託的階級 |

每個變體記錄完整戰鬥設定，不建立多層繼承或部分覆寫鏈。技能倍率在解析時套用，不預先合併到基礎能力；變體也不隨玩家等級自動調整。

有魔法風味的名稱或描述，不構成非零魔力、MP 或 SP 的數值依據。這些值必須作為明確的平衡資料核准，不能從目前層級建構的零值或敘述反推。

普通、精英與首領版本維持同一物種身分。較強版本是否可計入一般狩獵，由委託明訂條件決定，不從名稱、公會階級或單一能力值自動推論。

## 4．實際個體

沿用現有 `Monster`，以持久欄位儲存 `species_key`、`variant_key` 及現有的能力、狀態、位置等當前資料。每個個體保有自己的持久身分。

建立個體時，先驗證物種與變體引用及其所屬關係，再由有權管理該流程的確定性子系統套用已核准的基礎戰鬥設定。建立後的生命、資源與狀態仍由現有引擎處理。

威脅層級與評級由變體資料解析，不作為與變體互相矛盾的獨立可編輯真相。修改名稱不改變身分；修改登錄資料也不會靜默重新縮放已存在個體的能力。

個體的死亡計數以持久身分為準，不能以顯示名稱或威脅層級代替。同一死亡事件重複送達，不得重複增加同一委託的進度。

## 5．地區與據點配置

配置引用核准的變體，決定實際位置、數量、容量與群體配置。物種的棲地資料只提供相容性條件。

普通族群使用確定性的區域配置規則；營地、巢穴與首領使用明確的據點配置。地區內可有不同環境及危險區域，不將整個地理區域永久綁定為單一威脅層級。

據點由作者明訂一次性或可恢復。可恢復據點的條件使用遊戲內時間或已核准的確定性條件，不能因玩家重進房間或接取委託就忽略清除狀態。

所有生成與清理都有明確的管理者。野外族群維護只處理自己管理的個體，不刪除或替換委託、劇情及其他據點管理的目標。普通族群的維護規則也不能代替一次性或可恢復據點的生命週期。

## 6．委託資料與目標語意

沿用既有委託系統與公會接取資格判定。作者分別指定委託階級、評級理由及背景風味文字；個體危險評級不會自動成為整份委託的階級。

評級理由說明群體配置、能力或地形造成的風險。背景風味文字說明委託人的動機及當地事件，可離線閱讀。完成條件由結構化目標資料判定，不從背景敘述推測。

### 區域狩獵

條件明訂有效區域、物種、數量與可計入的變體。一般狩獵允許符合條件的較強同物種變體計入，但每隻仍只計一次。明確要求特定變體的委託，維持其限定條件。

可計數的變體與用來保障數量的普通合格變體須明確區分。接取前，必須透過現有族群／據點管理者，提供足額、可到達、存活的普通合格個體。玩家不必等待重生，也不必依靠較強變體完成一般狩獵。

補足目標必須遵守棲地、配置容量、管理權與據點當前狀態，不為補量重建既有合格個體，也不提前恢復已清除據點。無法合法滿足數量條件時，不接受該委託。

補量與委託接取遵守既有全有或全無原則：驗證後才持久化，任何失敗都不能留下半份有效委託或部分無效的目標配置。

### 綁定清剿

清剿只計指定遭遇的綁定個體。其他位置的同物種、普通族群重生個體或據點恢復後的新個體，不會自動替代原綁定目標。

據點是否恢復與委託是否可重新發布須相互一致；新一批目標擁有自己的個體身分，不能重算為舊委託的目標。

## 7．既有子系統與圖片邊界

本設計遵循 [引擎架構設計](/superpowers/specs/2026-07-29-ai-mud-engine-design) 的確定性與生成式邊界。

| 所屬範圍 | 責任 |
| --- | --- |
| `world/lore/` | 提供唯讀物種與變體登錄資料，不直接生成或改變個體 |
| `world/maps/` | 沿用地圖、房間及野外族群的既有管理流程處理其管理範圍 |
| `world/quests/` | 沿用委託生命週期、場景具現化及綁定流程處理其管理範圍 |
| `world/rules/` | 沿用一般動作、戰鬥、能力解析、公會資格與跨系統接取流程 |
| `world/art/` | 解析圖片身分、個人選擇及呈現，不用威脅層級假冒物種 |
| `world/ai/` | 讀取允許的資料並提交合格提案，不直接修改任何遊戲狀態 |

未核准內容不能由 AI 直接建立成物種或個體。對外公開資料與作者私有資料的邊界，也適用於生成式流程。

物種圖片承接 [外部美術與剪影設計](/superpowers/specs/2026-10-05-external-art-assets-and-silhouette-fallbacks-design) 的 `monster/<species-key>/` 身分。官方圖片保持唯讀，實際個體的個人選擇與幾何設定仍獨立。現有美術提案不代表正式物種登錄表已存在，也不能用層級別名滿足此前置條件。

## 8．交付與驗證邊界

本文件是已核准的設計依據，不修改現行主規格或宣告功能已交付。後續實作依專案 OpenSpec 流程，將物種／變體登錄、建構流程、配置生命週期、委託條件與圖片連接各自落實，並更新受影響的呼叫端；不新增舊路徑相容別名。

實作驗證須建立消費者可見的行為證據，至少涵蓋下列邊界：

- 變體必須屬於引用的物種，預設變體必須是該物種的普通基準；名稱與層級不能替代身分。
- 公開呈現不含作者私有註記，不將猜想轉述為已知真相。
- 個體建構使用核准的完整基礎能力，沒有玩家等級縮放或預先套用技能倍率。
- 區域接取時有足額可到達的普通合格目標；不足且無法合法補足時，接取與補量不留下部分狀態。
- 合格的較強同物種個體可計入一般狩獵，但非必要；區域與特定變體限制仍生效。
- 重複死亡事件不重複計數，恢復後的新個體不替換舊清剿綁定身分。
- 普通族群維護不清理其他管理者的目標，不略過據點恢復條件。
- 物種圖片使用真正的物種身分，保持官方資產與個人設定的獨立性。

驗證使用合成物種與隔離的測試資料，不將未核准候選或分級舉例轉成測試所需的正式內容。

### 提案交付

本節於提案產出後追加，不修改上文任何已核准邊界。本設計對應五個 OpenSpec 提案，全部位於 `openspec/changes/`（各自含 proposal、design、delta specs 與 tasks）：

| 提案 | 涵蓋的資料層與行為邊界 |
| --- | --- |
| `openspec/changes/monster-species-registry/` | 物種與變體登錄、身分驗證、公開／私有投影、棲地僅供相容、數值與評級槽位待平衡核准（§2、§3） |
| `openspec/changes/monster-identity-construction/` | 個體建構、由變體解析的層級與評級、無玩家縮放與預併倍率、以持久身分計殺與重複事件去重（§4） |
| `openspec/changes/monster-site-placement/` | 區域普通族群與明訂營地、巢穴、首領據點、擁有權域、一次性與可恢復生命週期（§5） |
| `openspec/changes/monster-quest-objectives/` | 區域狩獵與綁定清剿語意、接取時足額普通合格目標的全有全無補量、階級／評級理由／背景風味分離欄位（§6） |
| `openspec/changes/species-portrait-identity/` | 以穩定物種鍵解析官方圖片身分、禁止層級替代、變體共用物種圖片與個人設定獨立（§7） |

上述八條驗證邊界與提案的對應：邊界一（變體屬於物種、預設為普通變體）由 `monster-species-registry` 驗證；邊界二（公開呈現不含作者私有註記）由 `monster-species-registry` 驗證；邊界三（核准的完整基礎能力、無玩家縮放與預併倍率）由 `monster-identity-construction` 驗證；邊界四（接取時足額可到達普通合格目標、不足時不殘留部分狀態）由 `monster-quest-objectives` 驗證、其合法性以 `monster-site-placement` 的容量、管理權與據點狀態為前提；邊界五（合格較強變體可計入且非必要、區域與特定變體限制生效）由 `monster-quest-objectives` 驗證；邊界六（重複死亡不重複計數、恢復新個體不替換舊綁定）由 `monster-identity-construction` 的去重與 `monster-quest-objectives` 的綁定嚴格性共同驗證；邊界七（普通族群維護不逾越管理域、不略過據點恢復）由 `monster-site-placement` 驗證；邊界八（物種圖片真身分與資產／個人設定獨立）由 `species-portrait-identity` 驗證。

**依賴與外部前置條件。**五提案內部依賴為單鏈：registry → identity-construction → site-placement → quest-objectives；`species-portrait-identity` 另依賴美術提案中的 `official-content-provenance`、`official-artwork-catalog` 與 `official-art-resolution-contracts` 已落地。外部前置條件有三，均未在任何提案中以假實作取代：（一）使用者平衡核准——各變體完整能力數值（HP、MP、SP、物理戰鬥力、敏捷、防禦、魔力）與最終公會危險評級，以及據此發布含數值的正式狩獵委託；在此之前登錄僅含結構與核准敘事，個體數值走既有層級區間暫行規則並記錄來源。（二）特殊能力機制——六項核准能力（風吹落穀、擬燈發光、壓土築埂、接觸吸取魔力、聚霧亂向、敲岩共鳴）需要可執行的技能與行為契約，本波不登錄新技能。（三）官方圖片套裝——六個美術提案（`official-artwork-catalog`、`official-artwork-deployment`、`official-content-provenance`、`builtin-silhouette-stage-fallback`、`official-art-resolution-contracts`、`official-art-personalization`）與其外部的 `monster/<species-key>/` 官方內容包；美術提案本身不以層級別名滿足物種登錄前置。

**共用檔衝突。**`world/lore/sync.py` 與 `world/lore/__init__.py` 由 `monster-species-registry` 與 `monster-site-placement` 相續修改；`world/quests/planner.py` 及其測試由 `monster-identity-construction`（計數身分去重）先行、`monster-quest-objectives`（變體選擇器匹配）其後，`world/quests/runtime.py`（`counted_defeat_ids`）與 `world/quests/compile/` 載體驗證器亦屬此兩提案依序接續的範圍；`world/art/subjects.py`、`world/art/presenter.py`、`world/rules/art_view.py` 為 `species-portrait-identity` 與美術提案共用，須在 `official-content-provenance` 與 `official-art-resolution-contracts` 之後落地；`.github/evennia-shards.json` 為全部提案共用，逐次落地。

**建議平行批次排程。**真正獨立、可立即並行啟動的兩條線：魔物線自 `monster-species-registry` 起，美術線自無依賴的 `official-artwork-catalog` 與 `builtin-silhouette-stage-fallback` 起，兩線檔案互不相犯。有依賴、須依序落地：魔物線四提案依上述單鏈，美術線 `official-artwork-catalog`→`official-content-provenance`→`official-art-resolution-contracts`→`official-art-personalization`（`official-artwork-deployment` 掛在 catalog 之後即可）。無依賴但相互衝突、須序列化：`builtin-silhouette-stage-fallback` 與 `official-art-resolution-contracts` 共用 presenter 與 origin 詞彙（前者先落地建立詞彙，後者再擴展）。兩線收斂點：`species-portrait-identity` 於兩線前置（登錄表與 provenance／resolution 兩提案）都落地後可與 `monster-quest-objectives` 並行；其餘排程以各提案 proposal 的 Batch 節為準。
